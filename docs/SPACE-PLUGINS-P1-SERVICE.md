# P1: жизненный цикл Linux-службы расширений

Продолжение от 30 октября 2026 года к [восстановлению ProcessHost](SPACE-PLUGINS-P1-RECOVERY.md) и [общему P1](SPACE-PLUGINS-P1.md). Реализация находится в `space-server/experiments/extensions`: команда `cmd/p1-supervisor`, профиль `systemd/space-p1-supervisor.service` и аварийный стенд. Рабочая служба Space и её установщики не изменены.

## Владение процессами

Внешней cgroup экспериментальной службы владеет systemd. Он отслеживает основной процесс и завершает весь оставшийся состав группы при аварии или остановке. Внутри выделены `supervisor` для основного процесса и `workers` для ProcessHost. Поэтому ограничения общего хоста распространяются на worker, а служба может включать контроллеры в свободном от процессов родительском каталоге.

Используются `Delegate=memory pids cpu` и `DelegateSubgroup=supervisor`. Последний параметр требует systemd 254 или новее; [описание делегирования](https://www.freedesktop.org/software/systemd/man/255/systemd.resource-control.html). Команда проверяет свой путь в `/proc/self/cgroup`: единая иерархия, подгруппа `supervisor` внутри `.service`. Самостоятельно перемещать процесс из произвольной cgroup она не пытается. Нужны Linux cgroup v2 и root; политика отдельного служебного пользователя остаётся будущей задачей.

## Запуск и готовность

1. Проверить доверенный абсолютный путь к обычному файлу worker.
2. Получить корень делегированной службы, включить контроллеры, создать `workers`.
3. Создать ProcessHost: исключительное владение, восстановление старых распознанных групп, настройка новых квот.
4. Только после успешной инициализации отправить `READY=1` через `NOTIFY_SOCKET`.
5. Ожидать остановки; прикладного RPC/API в этой команде пока нет.

`Type=notify` и `NotifyAccess=main` не позволяют systemd считать службу готовой только по факту создания процесса. Ошибка инициализации или уведомления приводит к ненулевому выходу; перехода к исполнению без ProcessHost нет. `TimeoutStartSec=10s` ограничивает зависший запуск.

## Остановка и перезапуск

| Параметр | Поведение прототипа |
| --- | --- |
| `KillMode=control-group` | Остановка охватывает всю группу службы, включая вложенные группы worker |
| `KillSignal=SIGKILL`, `SendSIGKILL=yes` | Принудительная остановка без периода ожидания добровольного выхода потомков |
| `Restart=on-failure`, `RestartSec=1s` | Автоматический повтор после аварии с паузой в одну секунду |
| `StartLimitIntervalSec=30`, `StartLimitBurst=5` | Ограничение частоты запусков при постоянной ошибке |
| `TimeoutStopSec=2s` | Ограничение стадии остановки службы |
| `MemoryMax=768M`, `MemorySwapMax=0`, `TasksMax=128` | Внешняя граница всей службы, включая supervisor |
| ProcessHost | Прежние 256 МиБ на worker / 512 МиБ суммарно, два вызова и deadline 2 с |

Явный `systemctl stop` не вызывает автоматический перезапуск. При принудительном `SIGKILL` systemd может оставить `failed` / `Result=signal`; критерий остановки — отсутствие MainPID и неизменный счётчик перезапусков, а не обязательный статус inactive. Политика принудительной остановки подходит этому одноразовому прототипу; завершение пользовательских операций и правила повторного выполнения команд потребуются при рабочей интеграции. Не обещается нулевая задержка реакции планировщика или завершение процесса в непрерываемом состоянии ядра. [Условия перезапуска systemd](https://www.freedesktop.org/software/systemd/man/256/systemd.service.html).

Восстановление самого ProcessHost остаётся защитой на новом запуске. Завершение дерева при смерти supervisor теперь выполняет внешний менеджер, а не отложенная функция погибшего Go-процесса.

## Проверки GitHub CI

Отдельное задание `linux-service` использует настоящий системный systemd Ubuntu runner. Оно устанавливает профиль только в `/run/systemd/system`, бинарники стенда — в `/opt/space-p1`; после проверки останавливает службу и удаляет временный unit. Пользовательская машина не меняется.

| Сценарий | Критерий |
| --- | --- |
| Настоящий `p1-supervisor` | Запуск до active/READY, существующая группа workers, явная остановка без перезапуска |
| Авария до создания ProcessHost | Служба остаётся activating до SIGKILL, затем перезапускается и выполняет echo WASM |
| Авария после создания хоста, до READY | Не публикуется ложная готовность; очистка и успешный повтор |
| Авария при работающих worker и потомке | Подтверждены минимум три процесса; убийство только supervisor приводит к завершению всего старого дерева |
| Постоянно неверный путь worker | Служба не готова, повторные отказы останавливаются политикой start-limit |

В трёх аварийных сценариях стенд фиксирует PID и время создания старых процессов. Он проверяет их исчезновение **до** нового MainPID, в состоянии `auto-restart`, затем ровно один перезапуск, новый PID, настоящий echo WASM и отсутствие старых call-групп. Метрики очистки и готовности измеряются раздельно. Для каждого сценария явная остановка дополнительно проверяется на отсутствие повторного запуска.

Барьеры аварий и длинный запрос давления находятся только в тестовом executable, собранном с race detector; они не добавляют скрытых команд в `p1-supervisor` или настоящий worker. Тестовый executable использует те же функции создания serviceHost и уведомления, что команда. Обычный запуск реальной команды проверяется отдельно. Полная матрица ABI, строгого IPC и ограничений Linux/Windows повторяется.

[Итоговый CI 40977537700](https://github.com/space-protocol-project/space-server/actions/runs/40977537700) успешен для `5d5cf9493c33948fd54bef1bf459db278cf019c3`: все семь заданий. Стенд systemd 255.4-1ubuntu8.18 подтвердил пять сценариев.

| Стадия аварии | Старых процессов | Завершение старого дерева | Готовность нового экземпляра |
| --- | --- | --- | --- |
| До создания хоста | 1 | 0,076 мс | 1146,701 мс |
| До READY | 1 | 0,088 мс | 1290,027 мс |
| Worker и потомок работают | 3 | 20,214 мс | 1245,735 мс |

В каждом аварийном сценарии произошёл ровно один перезапуск и прошёл настоящий echo WASM. Измерение начинается перед SIGKILL; опрос процессов имеет шаг 20 мс, а готовность включает RestartSec=1s. Это единичные синтетические замеры runner, не гарантии производственной задержки. При неверном worker счётчик NRestarts достиг 5, служба осталась failed без MainPID и новых попыток за дополнительные 2,2 с; Result сохранился exit-code. При явной остановке подтверждено отсутствие повторного запуска, несмотря на диагностический failed/signal от SIGKILL.

Первый [прогон 40977024623](https://github.com/space-protocol-project/space-server/actions/runs/40977024623) остановился на неверном ожидании inactive после принудительного stop. Второй [прогон 40977279987](https://github.com/space-protocol-project/space-server/actions/runs/40977279987) подтвердил все три аварии, но обнаружил неверное ожидание Result=start-limit-hit: systemd сохраняет exit-code. Исправлены только ожидания стенда; итог проверяет отсутствие процессов, готовность, число перезапусков и устойчивое конечное состояние. Профиль службы не ослаблялся.

[Исходные результаты, журнал systemd и метаданные](p1-results/2026-10-30-service), [SHA256SUMS](p1-results/2026-10-30-service/SHA256SUMS) сохранены. Локальные сборки и тесты не запускались. Документационный коммит после CI не меняет проверенный код.
