# P1: транзакционный исполнитель мутаций

Статус: экспериментальный исполнитель проверен в GitHub CI на разрешённой ветке codex/p1-mutations-ci и перенесён в main. Рабочий сервер его не включает; P1 целиком не закрыт. Предыдущий подтверждённый срез: [сессии и ACL](SPACE-PLUGINS-P1-CORE.md).

## Область изменения

Добавлен отдельно вызываемый NewExtensionP1MutationService. Штатный сервер его не регистрирует и не вызывает. Прежний конструктор New сохраняет запрет мутаций и stateless acknowledge. Новый конструктор связывает единственную демонстрационную команду acknowledge с эффектом MUTATION; клиент не может заменить эффект на NONE и обойти запись.

Прототип создаёт таблицы extension_p1_meta/instances/data/receipts/outbox в текущей схеме Store. Не используется общая фиксированная схема между разными Store. Рабочий список миграций не меняется, версия ядра остаётся 46. Создание таблиц — явное действие экспериментального конструктора, а не побочный эффект запуска обычного сервера. Переход к рабочим миграциям остаётся открытым; [согласованное копирование и восстановление таблиц](SPACE-PLUGINS-P1-BACKUP.md) проверено отдельным срезом P1.

Привязка installation/instance/channel и список событий задаются доверенным кодом. Хеш включает WASM, ограниченный manifest и отсортированный список разрешённых событий. Повторный конструктор не обновляет пакет и не перепривязывает канал: несовпадение сохранённой привязки запрещает запуск. Полноценное обновление/удаление экземпляра не реализовано.

## Путь команды

1. Проверяются действующий context с токеном, effect=MUTATION, ASCII-ключ повторов 16–128 символов, диапазон ревизии и ограниченный JSON. Рендерер/dispatcher сохраняют ограничения предыдущего P1; payload демонстрации остаётся пустым объектом.
2. В пределах executor разрешены два запроса. Отдельное соединение держит session advisory lock по установке, экземпляру, principal, команде и ключу. Это сериализует одинаковые запросы между процессами; во время WASM транзакция БД не открыта. Соединение освобождает блокировку даже при отмене; при ошибке очистки оно удаляется из пула.
3. Короткая транзакция проверяет настоящую сессию/ACL и сохранённую привязку. Квитанция с тем же digest возвращает прежний результат с replayed=true без WASM. Иной digest даёт конфликт; прежняя ревизия нового запроса также даёт конфликт. Digest учитывает пакет, ABI и детерминированный protobuf запроса с точными байтами payload.
4. WASM возвращает ограниченный конверт ui_api/document/plan. Проверяются общий размер 16 КиБ, JSON, поля конверта, версия документа, protobuf-план без неизвестных полей, ожидаемая ревизия, 1–32 операции, отсутствие повторных ключей, допустимые put/delete и максимум 16 разрешённых событий. Ключ — непрозрачная UTF-8 строка 1–256 байт без управляющих символов. SQL и выбор чужих таблиц недоступны.
5. В новой короткой транзакции повторно проверяются сессия, ACL, полный снимок доступа, привязка пакета и ожидаемая ревизия. Применяются операции, квоты, события, квитанция и увеличение ревизии. Всё завершается одним commit.
6. Непосредственно перед commit сессия проверяется по clock_timestamp(), включая сроки grant/родителя/pairing; проверка не полагается только на время начала транзакции. Потеря ответа после commit обрабатывается повтором с прежним ключом. Автоматического повторного исполнения при неоднозначном результате commit нет.

## Порядок между commit и отзывом

Табличные SHARE-блокировки заменены блокировками связанных строк. Порядок: сопряжения текущего и родительского grants (по ID) → principal → текущий и родительский grants (по ID) → текущая сессия → членство → настройки пространства → канал → instance. Первые строки удерживаются FOR SHARE; изменение состояния удерживает канал и instance FOR UPDATE. Правила channel_access защищены существующей границей ядра: изменение ACL требует блокировки строки канала.

Строки членства и настроек закрепляются до вычисления роли: membership сначала читает owner_id, поэтому более поздней блокировки настроек было бы недостаточно для согласованной проверки. Глобальные изменения настроек по-прежнему согласуются через общую строку space_settings; две команды одного канала также могут ждать друг друга. Несвязанный logout больше не должен ждать записи расширения.

Граница опирается на инварианты ядра: grant_id сессии и parent_grant_id после создания неизменяемы; approval создаёт новый grant и связывает его с pairing в одной транзакции. Привязка нового pairing к уже существующему grant через API не поддерживается. Если это изменится, потребуется защита от появления новых связанных строк между чтением и блокировкой. Произвольные изменения SQL в обход ядра не входят в контракт.

Отзыв либо становится виден до проверки и запрещает мутацию, либо ждёт защищённую транзакцию. Сроки проверяются повторно по clock_timestamp() перед commit. WASM работает вне транзакции. lock_timeout остаётся 1 секундой, statement_timeout — 1,5 секунды; бюджет запроса — 5 секунд. Deadlock и конфликт блокировок дают отказ без частичного commit; отсутствие deadlock со всеми операциями ядра не обещается.

## Квоты и сохранность

На экземпляр: максимум 256 ключей и 1 МиБ суммарных байтов ключей/значений, 1024 квитанции и 4096 событий outbox. Квоты проверяются под блокировкой строки instance внутри транзакции. Превышение после применения плана откатывает и данные, и события, и квитанцию, и ревизию. Переполнение bigint запрещено.

Сейчас квитанции и события не очищаются, поэтому старый ключ не начинает исполняться заново после истечения времени. Ограничение ёмкости запрещает новые команды; уже сохранённый результат может быть повторно выдан только при действующем доступе. Политика удаления полного ответа через 30 суток, компактных маркеров и удаления instance ещё не реализована.

Outbox записывается атомарно и получает устойчивые event_id. После добавления восстановления новые ID случайные: откат ревизии к старой копии не повторяет ID утраченной ветви; сохранённые ID остаются неизменными. В следующем срезе добавлен [внутренний прототип доставки и подтверждения](SPACE-PLUGINS-P1-OUTBOX.md): аренда, курсор, повтор и идемпотентный получатель. Рабочая рассылка клиентам не подключена, exactly-once внешнего эффекта не обещается. Данные текущих Чатов, Комнат, Обсуждений и Ленты не записываются этим исполнителем.

## Проверки GitHub CI

- повтор и новое открытие Store после моделируемой потери первого ответа (ответ отбрасывается; реальный разрыв сети и SIGKILL процесса этим тестом не имитируются); конфликт другого payload и устаревшей ревизии;
- два конкурентных одинаковых RPC с одним вызовом WASM и одной записью; разные ключи при общей ожидаемой ревизии дают ровно один commit; отмена во время WASM освобождает ключ для последующего запроса;
- отзыв членства во время гостя, logout перед повторной выдачей квитанции;
- SQL-барьер в outbox: logout обязан ждать защищённый commit, последующий повтор запрещён;
- принудительная ошибка outbox после применения данных и превышение квоты ключей: полный откат; заполнение квот квитанций и событий запрещает новую запись;
- trap, недопустимый план, неизвестные/повторные поля, неверные операции и события;
- независимость экземпляров;
- настоящий WASM с планом, повтор без повторной записи, очистка cgroup;
- весь Go набор обычно и с -race, vet, mod verify, govulncheck.

## Стенд аварийного восстановления записи

Добавлен Linux-стенд с отдельным процессом тестового сервера: настоящий Store, транзакционный executor, авторизация и gRPC. Процесс запускается из того же тестового бинарного файла, открывает существующую изолированную схему PostgreSQL и регистрирует только экспериментальный API. Гостевой план фиксирован; число его вызовов сохраняется в отдельном файле с fsync. Это проверка восстановления записи, а не совместная авария WASM worker и сервера.

Три детерминированные точки отказа:

1. **SIGKILL до commit.** SQL-барьер удерживает вставку outbox после применения данных. Родитель действительно завершает процесс сигналом SIGKILL (сигнал проверяется через статус процесса). PostgreSQL откатывает оборванную транзакцию: ревизия, данные, квитанция и outbox остаются пустыми. Новый процесс повторяет команду с прежним ключом, выполняет план заново и создаёт ровно одну запись каждого типа.
2. **SIGKILL после commit до ответа.** Тестовый interceptor удерживает ответ после возврата обработчика. Родитель проверяет сохранённые данные и завершает процесс. После нового открытия Store повтор выдаёт прежнюю квитанцию с replayed=true; повторного вызова гостя нет.
3. **Обрыв соединения после commit.** В той же точке родитель закрывает клиентское gRPC-соединение. Первый RPC завершается ошибкой; сервер остаётся живым. Новый клиент получает квитанцию с replayed=true без повторной записи и вызова гостя. Это реальный обрыв соединения, а не отбрасывание уже полученного успешного ответа; потеря отдельных пакетов или сбой маршрутизатора не моделируются.

После каждого восстановления проверяются значение данных, ревизия, единственная квитанция и событие, совпадение ответа с сохранённым protobuf и неизменность ID события после повторной выдачи. Отозванная через Logout сессия больше не получает квитанцию. До commit ожидаются два вызова гостевого плана (оборванный и новый), после commit — один на оба запроса.

PostgreSQL при этих авариях продолжает работать. Сбой самого PostgreSQL, отключение питания, отказ диска, совместный SIGKILL сервера с живым WASM worker и неоднозначность соединения сервер → PostgreSQL во время COMMIT требуют отдельных сценариев. Штатный сервер не включает экспериментальный API.
