# Проверка восстановления и перезапуска

Дата: 8 октября 2026 года. Выполняйте на отдельном тестовом пространстве. Не удаляйте единственную рабочую идентичность ради проверки.

## Автоматическая проверка

GitHub CI проверяет реальную `/space` в одноразовом Chromium: сохранение CryptoKey в IndexedDB, полное закрытие браузера, вход с прежним профилем, восстановление QR PNG в пустом профиле, неверный пароль без изменения vault и повторный вход восстановленного устройства после ещё одного перезапуска.

Тест Dart запускает новый процесс с сериализованной рабочей записью, проверяет прежние principal, owner и grant, читает сообщения. Этот Dart-сценарий проверяет формат и перезапуск процесса. Реальный системный плагин Windows проверяется отдельной нативной сборкой, описанной ниже. Production-клиент продолжает использовать только secure storage; файловый vault существует исключительно в тестовом временном каталоге.

## Ручная проверка Windows secure storage

1. Поднимите отдельный сервер с отдельной тестовой базой. Не используйте рабочую базу с единственным owner.
2. Подключитесь в Windows-приложении. Запишите principal ID и текущий grant ID из раздела идентичности.
3. Сохраните recovery PNG и JSON. Пароль сохраните отдельно.
4. Закройте приложение полностью. Запустите его снова и подключитесь к прежнему адресу.
5. Сверьте principal и grant: оба должны остаться прежними. Проверьте чтение/отправку согласно роли.
6. Для чистого восстановления используйте другой тестовый Windows-профиль или отдельный компьютер: там не должно быть прежнего vault. Простая распаковка EXE в новую папку не создаёт чистое хранилище пользователя.
7. Откройте PNG с неправильным паролем. Должна появиться ошибка; идентичность не должна сохраниться или заменить существующую.
8. Повторите с правильным паролем. Principal и членство должны сохраниться, grant/device key — стать новыми.
9. Полностью закройте и вновь откройте восстановленное приложение. Проверьте прежний восстановленный grant и успешный вход.
10. В тестовом пространстве отзовите старый рабочий grant и проверьте отказ старому устройству. Не отзывайте последний путь управления.

Повторите с delegated-card браузера: восстановленный Windows-профиль должен хранить только рабочий секрет; подпись для другого устройства потребует повторного открытия карточки. Исходная Flutter root-card возвращает root authority — это другое свойство карточки, а не ошибка теста.

## Ручная проверка браузера

Используйте отдельный тестовый профиль браузера. Сначала войдите, сохраните карточку, закройте все окна профиля и запустите его снова. Затем восстановите PNG в другом пустом профиле. Отдельно проверьте блокировку после отзыва recovery grant: она должна распространяться на восстановленные и сопряжённые дочерние устройства.

Перезагрузка страницы проверяет потерю состояния вкладки, но не заменяет полный перезапуск браузера. Приватный режим может удалить профиль после закрытия; его поведение не следует считать постоянным vault.

## Как записать результат

| Проверка | Ожидаемый результат | Фактический результат |
|---|---|---|
| Windows исходный профиль после перезапуска | Тот же principal/grant | Заполнить вручную |
| Пустой профиль + неверный пароль | Ошибка, vault не изменён | Заполнить вручную |
| Пустой профиль + PNG | Тот же principal, новый device/grant | Заполнить вручную |
| Восстановленный профиль после перезапуска | Тот же новый grant, успешный вход | Заполнить вручную |
| Отзыв device | Его вход и чтение запрещены | Заполнить вручную |
| Отзыв recovery | Все зависимые devices запрещены | Заполнить вручную |

Укажите версию клиента, ОС, server ID, дату и ошибки. Не прикладывайте пароль, seeds, access token, полный код приглашения или рабочую recovery-карточку. Даже тестовый отчёт должен различать автоматические результаты CI и фактически выполненный ручной сценарий.

## Что остаётся после этих проверок

Ротация root, перенос identity между origin, recovery server backups и переход на новый master-seed профиль — отдельные задачи. [Предложение безопасной ротации](adr/023-restart-and-root-rotation.md) объясняет зависимость от постоянного principal ID. Эти проверки не доказывают защиту от компрометации ОС или возможность полного обнуления управляемой памяти.

## Выполненная нативная проверка Windows

8 октября 2026 года отдельная Windows release-сборка `tool/native_vault_drill.dart` прошла три независимых запуска процесса: запись device-only ключей через настоящий `SecureIdentityVault`, чтение с совпадающим digest после перезапуска и удаление собственного тестового слота. Проверка использует случайный namespace-origin `space-vault-drill:<nonce>`, который никогда не служит адресом подключения. Пользовательские HTTP-origin записи не затрагиваются. Отчёт содержит только digest и флаги результата, без seeds или токенов.

Повтор:

```powershell
cd client
flutter build windows --release --target tool/native_vault_drill.dart
./tool/native_vault_drill.ps1
flutter build windows --release --target lib/main.dart
```

Тестовая точка входа не включается в обычное приложение. После теста нужно пересобрать `lib/main.dart`; проверочный EXE не следует упаковывать как пользовательскую сборку. Этот сценарий добавлен отдельным Windows-job в CI. Он проверяет реальный плагин и границу процесса на одной ОС-профиле; восстановление в другом Windows-профиле и перенос на другой компьютер остаются отдельными ручными сценариями.
