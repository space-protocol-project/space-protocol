# P1 / E01: жизненный цикл, сессии ядра и граница COMMIT

Статус на 1 ноября 2026 года: интеграция прошла GitHub CI. Продолжение [кандидата жизненного цикла](SPACE-PLUGINS-P1-LIFECYCLE.md). Это явно создаваемая управляющая оболочка экспериментального сервиса, а не публичный реестр расширений.

Дополнение: [постоянный реестр и восстановление состояния](SPACE-PLUGINS-P1-REGISTRY.md) заменяет описанные ниже ограничения хранения только в памяти. Результаты этого отчёта относятся к предыдущему SHA; новые результаты приведены отдельно.
## Подключение к ядру

`Store.NewExtensionP1ManagedService` объединяет координатор установки, существующий dispatcher и транзакционный исполнитель. Query, Execute и получение контекста новой команды проходят через оболочку, затем через прежние gRPC, сессии/ACL и WASM. Метод сверки квитанции не запускает гостя и остаётся доступным при выключении, карантине и удалении кода; действующие сессия и ACL исполнения по-прежнему обязательны.

Управление выполняет доверенный Go-адаптер `Change`: он принимает токен, поколение оболочки, installation, action и ожидаемую ревизию. `authn.AuthorizeCall` повторно проверяет настоящий Bearer token через ядро. Actor, роль `owner`, результаты проверки прав и свидетельства пакета не принимаются из клиентского объекта. Новый protobuf/Connect RPC управления и Flutter UI этим изменением не вводятся.

В одной транзакции управления выполняются:

1. Блокировки полномочий в прежнем порядке ядра: pairing → principal → grants → session → membership → settings.
2. Проверка текущей сессии, включая запрет push-only и подмены actor.
3. `managementRole(..., ownerOnly=true)`: действующий владелец с разрешением устройства `space.manage`. Участник или администратор не получает право менять lifecycle через обычный доступ к каналу.
4. Проверка `manage` для всех каналов установки в стабильном порядке.
5. Проверка перехода/ревизии, запись аудита и повторная проверка сессии по текущему времени перед COMMIT.

Аудит владельца хранится в существующей `admin_audit`: principal, `extension.p1.lifecycle/<generation>/<installation>/<action>` и новая ревизия. Обычная ошибка SQL до COMMIT оставляет состояние и активные вызовы без изменения.

## Подключённые операции

| Источник | Операции | Поведение |
| --- | --- | --- |
| Владелец с действующей сессией | enable, disable, remove | Проверки ядра, аудит в SQL и переход под общим барьером |
| Доверенное ядро — держатель Go-объекта | quarantine, finish_disable | Тот же барьер и координатор; клиент не может выбрать роль system |
| Пока не подключены | verify, install, begin_upgrade, finish_upgrade, fail_upgrade, recover | Отказ `FailedPrecondition`; внешние свидетельства доверия/копии/миграции не принимаются |

Включается только неизменный пакет из заранее заданной привязки P1, который принял существующий конструктор сервиса. Флаги кандидата `package_verified`, `compatible`, `grants_approved` относятся к этой доверенной привязке и версии экспериментального ABI; они не доказывают криптографическую проверку издателя E04. Новый digest и расширение разрешений этим методом не устанавливаются.

`remove` переводит установку в логическое состояние removed и запрещает запуск кода. Физическое удаление файлов пакета, выгрузка общего runtime и очистка данных здесь не выполняются.

Системные переходы пока выполняются в памяти; постоянный системный аудит без пользовательского principal требует отдельного реестра. Он не имитируется записью от имени владельца. Отказ БД не должен мешать ядру держать карантин закрытым.

## Активные вызовы и транзакции

Для каждой установки существует отдельный отменяемый барьер. Его получают новый допуск, переход lifecycle и финальная SQL-транзакция мутации. WASM исполняется вне барьера COMMIT; disable/quarantine могут отменить длительный вызов. После отмены вызов остаётся активным до фактического выхода из RPC, и `finish_disable` не может преждевременно объявить его завершённым.

Порядок захвата для управляющего перехода и COMMIT одинаков: барьер установки → блокировки сессии/полномочий ядра → каналы/данные → COMMIT. У мутации барьер удерживается до окончания COMMIT либо ROLLBACK. Ключ идемпотентности и прежние SQL-блокировки сохраняются.

- Если disable/quarantine получили барьер первыми, они отменяют контексты активных вызовов. Мутация не может войти в финальную транзакцию с отменённым контекстом; данных, квитанции и outbox не появляется.
- Если финальная транзакция получила барьер первой, переход ждёт её завершения. Уже сохранённый результат не откатывается из-за последующего выключения. Просроченное ожидание управления не меняет состояние и не оставляет аудит успешного перехода.
- Поздний `Canceled` клиенту не доказывает откат: COMMIT мог предшествовать отмене. Для выяснения результата применяется прежняя сверка квитанции.
- Другие установки имеют собственные барьеры. Все экземпляры одной установки разделяют состояние допуска.

После успешного COMMIT аудита переход в памяти применяется даже при отключении клиента. Если подтверждение COMMIT аудита потеряно, исход не объявляется откатом: оболочка помечается неисправной, отменяет активные вызовы и запрещает новый допуск/COMMIT/управление с `Unavailable`. Восстановление такой оболочки не выполняется скрытым повтором команды.

## Повторное создание и границы владения

Новая оболочка всегда создаёт установки в `disabled`, ревизия 1. Случайное 128-битное поколение меняется при пересоздании; прежний запрос управления с прежним поколением отклоняется, даже если численная ревизия совпала. Действующий владелец должен явно включить установку с новым поколением.

В одном `Store` второй владелец managed-сервиса запрещён. Межпроцессное владение и согласование нескольких независимых `Store` этим прототипом не реализованы: такой запуск не поддерживается. Прежний конструктор без lifecycle сохранён для старых изолированных стендов; он не должен регистрироваться как альтернативный сетевой путь к той же managed-установке.

Формат экспериментальных данных остаётся v3, схема рабочего ядра — 46. Состояния lifecycle не добавляются в backup/restore: после пересоздания вход закрыт, данные, квитанции и outbox сохраняются. Постоянный реестр, восстановление точного состояния/ревизии и распределённый барьер остаются задачами дальнейшей интеграции. Планировщик фоновых заданий, подписки и доставка outbox к этой оболочке пока не подключены; её учёт активных вызовов ограничен query, Execute и выдачей контекста команды.

## Проверки и результаты

GitHub CI проверяет действующие и отозванные сессии, роль владельца и scope, изменение ACL участника до COMMIT, отмену query/мутации, карантин, незавершённый drain, изоляцию установок, конфликт ревизии, SQL-отказ аудита, потерю подтверждения COMMIT аудита, новую оболочку и прежнее поколение. SQL-барьеры задают порядок гонок. Для отзыва сессии используется Logout; изменение владельца и scope в тестах задаётся контролируемой транзакцией БД, поскольку публичного RPC передачи владельца нет.

Путь команды дополнительно проверяется с настоящим изолированным WASM. Прогон включает полные обычные/race-тесты ядра, прежние проверки доступа, истории, квитанций, outbox, backup/restore, аварий БД/worker, vet, mod verify и govulncheck. Первый завершённый прогон [41312288898](https://github.com/space-protocol-project/space-server/actions/runs/41312288898) обнаружил ошибку стенда: повторный INSERT аудита шёл через подготовленный statement, и посредник не видел SQL в кадре Bind. Для отдельного теста потери подтверждения включён `simple_protocol`, чтобы выбирать нужную транзакцию по SQL-тексту; рабочая конфигурация pgx не меняется. Проверка по-прежнему требует реального скрытого `CommandComplete COMMIT` и ответа Internal. Предварительный прогон 41312163533 отменён при добавлении поколения в аудит и не является приёмкой. Повторный [CI 41312556474](https://github.com/space-protocol-project/space-server/actions/runs/41312556474) завершён с `conclusion=success`; задачи `core` и `database-faults` успешны. Локальные сборки и тесты не запускались.

### Подтверждённые результаты

- Проверенная ревизия сервера: `098eeba67df7dfc7f44cdd8e69c5f4ba59646102`; общие сценарии протокола закреплены на `a720dd0c0f4c00684d22f39b703b20f545ce85c7`. Последующие изменения документации не меняют проверенный код.
- Целевые lifecycle-тесты: 80 успешных результатов в пяти повторениях с `-race`; пять пропусков — один WASM-тест в каждом повторении до подготовки изоляции. Он успешно выполнен отдельно в задаче с настоящим worker.
- Координатор и 41 общий сценарий: 25 race-повторений, 1200 успешных результатов без пропусков.
- Обычный и race-прогон всего ядра: по 627 успешных результатов и 16 штатных пропусков. Пропуски относятся к отдельно подготавливаемым окружениям резервного копирования, сети, bundled PostgreSQL, baseline, аварий БД и изолированного WASM; это не новая полная приёмка всех этих окружений.
- Привилегированный прогон P1: 110 успешных результатов без пропусков, включая `TestExtensionP1LifecycleRealWASM`; повторные аварии worker — 20 результатов. Корневая cgroup удалена.
- Проверки аварий PostgreSQL — 25 результатов без пропусков. Проверки доступа — 65, порядка блокировок — 110, backup — 39, истории — 30, окна повторов — 20, outbox — 60; все успешны. Остальные целевые результаты приведены в сводке.
- `go vet`, `go mod verify`, `govulncheck` вызываемого кода и проверки демонстрационного WASM успешны. `go.mod`/`go.sum` после CI совпадают с репозиторием.
- [Сводка и исходные журналы](p1-results/2026-11-01-lifecycle-core/summary.json), включая неуспешный и отменённый предварительные прогоны, сохранены с [SHA-256](p1-results/2026-11-01-lifecycle-core/SHA256SUMS).

E01 целиком остаётся открытым: публичные административные RPC, полный manifest/ABI, contributions, доверие пакету и миграции, постоянный реестр и системный аудит ещё не приняты. Это не завершение 0.9.0.
