# P1 E03 Windows: сеть после Winsock и временный профиль

Статус: E03 Windows принят в границах прототипа 11 ноября 2026 года. Полный профильный GitHub CI успешен. macOS остаётся отложенной по решению пользователя; P1 целиком и релиз 0.9.0 не объявляются завершёнными.

## Сеть

Раньше нулевой набор capabilities не позволял запустить Winsock: `WSAStartup=10107`, последующие операции возвращали `10093`. Это наблюдение сохраняется отдельно и больше не подменяет проверку сетевого запрета.

Диагностический тест создаёт тот же LPAC, добавляя только `registryRead`. Это внутренний параметр тестового стенда, не настройка пакета и не изменение обычного конструктора: `NewWindowsRestrictedHost` по-прежнему выдаёт ноль capabilities. Сетевые capabilities, исключения loopback и правила брандмауэра не добавляются. До запуска проверяются SID контейнера, точный набор capabilities и отсутствие доступа через `ALL APPLICATION PACKAGES`.

Проверяются TCP/UDP × IPv4/IPv6. Положительный контроль тем же executable без LPAC должен успешно выполнить `WSAStartup`, создать сокет, обменяться данными с доступным echo endpoint и привязать локальный порт. В диагностическом LPAC требуется успешный `WSAStartup`, затем `WSAEACCES=10013` непосредственно при создании сокета, а также при попытках обмена и bind. Отказ уже на `socket` не зависит от наличия маршрута или доступности удалённого сервера. Это не измерение конкретного WFP-фильтра и не тест внешнего IPv6-маршрута.

Основание диагностического профиля — [описание AppContainer/LPAC Microsoft](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer) и [пример SandboxSecurityTools](https://github.com/microsoft/SandboxSecurityTools/blob/main/LaunchAppContainer/README.md). `registryRead` расширяет доступ к системному реестру, поэтому не включается в обычный хост ради удобства тестов. Сетевой результат на этом более разрешительном профиле хранится отдельно от результата профиля с нулевыми capabilities.

## Диск

Гостю не требуется прямое файловое хранилище: WASM работает с данными через проверяемый API хоста. Вместо разрешённой записи с недоказанной квотой профиль становится доступным гостю только для чтения. Это не NTFS-квота на суммарные записи всей ОС и не квота будущего API хранения.

После создания собственного случайного AppContainer и до запуска первого worker хост получает [GetAppContainerFolderPath](https://learn.microsoft.com/en-us/windows/win32/api/userenv/nf-userenv-getappcontainerfolderpath), проверяет ожидаемый путь `LOCALAPPDATA/Packages/<имя>/AC` и защищает всё дерево родительского профиля. Каталог снимка executable получает ту же защиту. Исходный executable и чужие профили не изменяются.

Перед изменением ACL проверяется всё дерево: не более 1024 элементов, без reparse points. Затем устанавливается защищённая DACL: SID гостя запрещены запись/добавление данных, изменение атрибутов, удаление и создание ссылок через запись в каталог, `WRITE_DAC` и `WRITE_OWNER`; владелец не получает неявный обход через изменение DACL благодаря `OWNER RIGHTS`. Доверенный supervisor и SYSTEM сохраняют доступ для подготовки и очистки. Новые файлы доверенного supervisor наследуют ограничения гостя. Ошибка подготовки не допускает запуска и вызывает штатную очистку через журнал.

Матрица проверяет чтение, запись, добавление 1 МиБ, усечение, создание файла/каталога, удаление, переименование, hard link и изменение DACL файла/каталога. Обычный контрольный процесс выполняет эти операции успешно в отдельном тестовом каталоге. Ограниченный worker читает контрольный файл, остальные операции должны завершиться `ERROR_ACCESS_DENIED=5`; supervisor повторно проверяет содержимое и состав каталогов. Отдельно проверяются корень профиля, `AC`, каталог executable, вложенные каталоги и разделение двух профилей. После закрытия профиль удаляется, соседний продолжает работать.

Запись в собственное хранилище реестра проверена через [GetAppContainerRegistryLocation](https://learn.microsoft.com/en-us/windows/win32/api/userenv/nf-userenv-getappcontainerregistrylocation) отдельно от файловых операций: в обычном профиле без capabilities запросы `KEY_SET_VALUE`, `KEY_CREATE_SUB_KEY` и `WRITE_DAC` получают `ERROR_ACCESS_DENIED=5`. Запрет файла сам по себе не засчитывался за запрет этих возможностей. Диагностический профиль с `registryRead` не используется как доказательство дисковой границы обычного хоста.

Буфер заменён выровненным, путь проверяется по ожидаемой структуре; проверки не отключались. Первоначальные отказы и промежуточный успешный целевой прогон не считаются итоговой приёмкой.

## Границы

Проверяется исследовательский LPAC-хост на Windows Server 2025 x64 в GitHub CI. Рабочий broker, обновления/подпись executable, установщик, длительная нагрузка и матрица поддерживаемых настольных версий остаются P3. Ресурсный `NewProcessHost` не превращается автоматически в LPAC-хост. Уже принятая UI-матрица E06 использовала ресурсный профиль и не является доказательством этих границ. macOS в этом workflow не запускается; завершение всей P1 требует итоговой сверки E01–E07.
