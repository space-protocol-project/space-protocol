## Рабочая интеграция

В оболочке приложения доступны «Разделы пространства» и кнопка «Все разделы»
в группе чатов. Диалог получает `ListBuiltinSections` с текущей серверной
сессией, а при выборе вызывает `OpenBuiltinSection`. После успешной проверки
открывается существующий экран нужного чата, комнаты, обсуждения или ленты.
Перед получением списка и открытием синхронизируется прежний каталог каналов
SpaceSession: новая комната из реестра должна сразу появиться и в существующем
экране комнат. Экран повторно получает данные через прежний API, поэтому первая страница
`OpenBuiltinSection` используется для проверки открытия, а не как отдельный
кеш пользовательского содержимого.

`BuiltinNavigationCubit` управляет загрузкой, открытием, ошибками и поздними
ответами. Состояние описано Freezed, исходник и результат генерации сохранены
вместе. Смена поколения, закрытие Cubit и сигнал закрытия серверной сессии
не позволяют позднему ответу вернуть скрытые данные. Оболочка дополнительно
сверяет сессию перед переходом; асинхронный выбор чата сверяет текущий контроллер.

Нужен сервер с `BuiltinExtensionService`; выпущенные runtime не обновлялись.
При отсутствии метода новый диалог сообщает о недоступности.

Существующие экраны и их прикладные контроллеры сохраняются. Это первый рабочий
переход через реестр, а не замена всей навигации и «Обзора» на contributions.
Прежние пункты навигации, поиск и страницы содержимого продолжают работать.

## Транспорт команд

После успешного получения реестра `ConnectBuiltinTransport` подключает
маршрутизацию команд к `RpcConnection` конкретной `SpaceSession`. До этого
старые пути остаются прежними. Соединение другого пространства или пользователя
не использует эту таблицу. Отдельного глобального кеша нет.

Фиксированная клиентская таблица содержит те же 26 типов, что серверная.
`channel_id` извлекается из типизированного запроса, включая вложенные
update/delete/reaction. По каналу выбирается полученный от сервера экземпляр;
тип адаптера обязан совпасть. Неизвестные таблице общие операции остаются на
прежнем RPC. Для известной команды отсутствие экземпляра вызывает обновление
реестра и затем ошибку, если канал по-прежнему отсутствует.

Команда передаётся в `ExecuteBuiltinCommand`, ответ проверяется по точному
protobuf type URL и распаковывается в ожидаемый прежним экраном тип. Нет второго
SQL writer или новой прикладной очереди. После включения нового пути его ошибка
не вызывает автоматической отправки той же записи в старый RPC.

Снимок реестра проверяет связь instance/installation/plugin/view/channel,
версию `legacy.p2`, доступность чтения и отсутствие повторов каналов. Объекты
замораживаются. Сервер остаётся окончательным источником решения о правах и
повторно проверяет сессию/ACL при каждой операции; клиентский список не является
разрешением на запись. Метаданные авторизации передаются штатным способом
через закреплённое соединение приложения.

Для завершения своей голосовой сессии сохраняется ранее полученная связь
экземпляра с комнатой: обновление списка после отзыва чтения не должно мешать
`LeaveVoiceRoom`. Использовать её для входа или изменения комнаты нельзя.
Владельца соединения и действительность сессии проверяет сервер.

## Повторы и неопределённый результат

- На один вызов транспорта допускается максимум две отправки.
- Повтор разрешён только при `Unavailable`/`DeadlineExceeded` и прежнем ключе
  идемпотентности: создание/изменение/удаление/реакция чата, публикация MLS,
  создание/ответ темы, публикация/комментарий ленты.
- Оба запроса используют один замороженный снимок байтов, instance и ключа.
  Смена допуска между попытками останавливает повтор.
- Отказ ACL, отозванная сессия, неправильный запрос и операции без ключа не
  повторяются автоматически. В частности, вход в голосовую комнату не стал
  идемпотентным.
- После исчерпания попыток исходная ошибка возвращается прежнему контроллеру.
  Транспорт не выдаёт сетевой сбой за подтверждённое отсутствие записи.
  Уже существующие прикладные очереди сохраняют свою политику повторов с тем
  же ключом; две попытки — предел одного вызова транспорта, а не всей очереди.

## Проверки и границы

Workflow `plugin-p2-client.yml` содержит:

1. Анализ Flutter и тесты Cubit/виджета/повторов, регрессию оболочки и RPC
   на Linux и Windows.
2. Проверку COG всего рукописного Dart без изменения порога или исключений.
3. Linux-стенд настоящего Go-ядра с обнаружением гонок, PostgreSQL 17.11,
   реальной сессией и HTTP Connect. После фиксации первой записи стенд теряет
   ответ; повтор должен вернуть ту же запись. Отдельно проверяются запрет записи
   читателю, скрытие по ACL, восстановление чтения и отзыв сессии.

Временные допуски создаются только для стенда. Файл подключения с токеном не
публикуется среди артефактов. Артефакты содержат результаты, журналы и ревизии.

Windows в этом workflow проверяет Flutter-тесты, а не установленное приложение
с настоящим сервером. Нативная многоплатформенная приёмка всего пользовательского
пути, четыре пары старого/нового клиента и сервера, полноценный «Обзор» на
contributions, паритет последующих страниц/общих служб и архивная совместимость
остаются открытыми. Наличие меню и успешного RPC не закрывает P2 целиком.

`TestBuiltinClientFixture`; рабочие обработчики записи не менялись.
Локальные `go test ./...`, `go vet ./...`, `go mod verify` и `govulncheck`
успешны; локальные пропуски PostgreSQL не засчитываются как приёмка.
Изменённых собственных Dart-пакетов нет; зависимости и версии SDK не менялись.

Предварительные попытки сохранены отдельно:

  отсутствовали пакеты GTK/X11/Xi. Добавлена штатная установка подписанных
  пакетов через существующий сценарий проекта.

  Предварительная сборка перенесена перед созданием временной сессии.
  Тайм-аут самой проверки, права доступа и срок действия допуска не ослаблялись.

- CI 43085569805: клиентские наборы Linux/Windows и COG прошли. Реальный RPC
  корректно отказал в первой записи из-за ошибки исходного ACL тестового

  рабочая авторизация не менялась.
