# P1: проверка ограничений памяти macOS

Исследовательский этап от 30 октября 2026 года. [Общий P1](SPACE-PLUGINS-P1.md), [Linux](SPACE-PLUGINS-P1-ISOLATION.md), [Windows](SPACE-PLUGINS-P1-WINDOWS-LAUNCH.md). Стенд находится в `space-server/experiments/extensions/macos`; он не является защищённым launcher. macOS ProcessHost по-прежнему возвращает `ErrIsolation`.

## Вопрос и критерий

Нужна принудительная граница ОС для совокупной памяти компилятора и всех worker. Ограничение линейной памяти WASM, GOMEMLIMIT, сумма зарезервированных слотов и периодическое чтение RSS сами по себе не выполняют это требование. Должен существовать механизм, который ограничивает расход без сотрудничества кода расширения и без своевременной реакции supervisor.

Проверяются два направления: нативные resource limits и отдельная виртуальная машина. Успешный исследовательский workflow означает, что получены и проверены измерения, а не что защита macOS реализована.

## Нативный стенд

Проверяются фиксированные пределы 64, 256 и 512 МиБ, а также исходное виртуальное пространство плюс 64 МиБ (`baseline`). Увеличение виртуального предела не приводит к выделению соответствующего объёма физической памяти. Каждый процесс выделяет максимум 96 МиБ, либо два дочерних процесса — по 48 МиБ. Стенд не пытается исчерпать память runner.

| Сценарий | Действие и наблюдение |
| --- | --- |
| `as` | Установить soft/hard RLIMIT_AS для каждого исследуемого предела, прочитать значение обратно, запросить и заполнить mmap 96 МиБ |
| `data` | Повторить с RLIMIT_DATA; проверить, ограничивает ли лимит data segment анонимное отображение |
| `aggregate` | Два дочерних процесса независимо получают RLIMIT_AS=64 МиБ, затем в отдельном прогоне baseline+64 МиБ и выделяют по 48 МиБ; оба удерживают память до разрешения выхода от родителя |

Все страницы заполняются псевдослучайными данными через volatile-записи. Сохраняются errno установки лимита и mmap, фактически выделенные байты и resident_size из Mach task_info. Сумма resident_size — сумма снимков двух дочерних процессов, удерживающих буферы на барьере; это не атомарный снимок всей системы. Успешный mmap отдельно не считается доказательством физического потребления.

Отказ setrlimit означает, что конкретное значение не удалось установить; это не доказательство отсутствия механизма для всех значений. Отказ mmap записывается отдельно от завершения процесса. Компиляция выполняется clang с `-Wall -Wextra -Werror`. Длительность ограничена alarm и внешним timeout; все дочерние процессы ожидаются. Сами измерения не меняют публичный режим запуска расширений.

В [заголовках Apple RLIMIT_RSS является псевдонимом RLIMIT_AS](https://github.com/apple/darwin-xnu/blob/main/bsd/sys/resource.h); стенд проверяет равенство в установленном SDK. Актуальная публичная [реализация XNU](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_resource.c) передаёт RLIMIT_AS и RLIMIT_DATA в Mach VM, а [vm_map](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/vm/vm_map.c) отклоняет новый предел ниже текущего размера карты. Это объяснение согласуется с измерениями, но исходники main не объявляются точным исходным кодом версии ядра runner. Архивное описание RSS как предпочтения вытеснения не используется как доказательство поведения современной macOS.

Ни наследование per-process лимитов, ни одинаковый запас адресного пространства у двух детей не превращают их в общий бюджет дерева. `baseline+64 МиБ` — исследовательский предел виртуального пространства, а не жёсткая квота RSS 64 МиБ. Отдельно сохраняются исходные virtual_size и resident_size, чтобы не смешивать эти величины.

## Virtualization.framework

Отдельная Swift-программа с ad-hoc подписью и entitlement `com.apple.security.virtualization` читает `VZVirtualMachine.isSupported` и допустимый диапазон guest memory. Подпись проверяется codesign. [Apple определяет isSupported как доступность виртуализации на конкретной машине](https://developer.apple.com/documentation/virtualization/vzvirtualmachine/issupported); это ещё не успешный запуск Linux guest.

Настройка VM `memorySize` задаёт физическую память, которую видит гостевая ОС. Она не равна общему RSS процесса Virtualization.framework и не доказывает потолок всех расходов хоста. Поэтому даже положительная доступность API не закрывает требование общего бюджета. Для следующего прототипа нужны загрузка Linux, cgroup v2 внутри гостя, измерение расходов VMM снаружи, защищённый обмен, отказ/перезапуск и подписанная упаковка.

CI выполняется на `macos-15` (ARM64) и `macos-15-intel`. Доступность аппаратной виртуализации зависит от runner; [GitHub указывает ограничения nested virtualization для ARM64 macOS runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners). Результат одного runner нельзя переносить на все физические Mac. Проверка не создаёт VM и не загружает образ Linux.

## Результаты

[Итоговый CI 41012479894](https://github.com/space-protocol-project/space-server/actions/runs/41012479894) завершился успешно: все девять заданий для `b4671beace6440d2f22d0ed305d0a74a6970006d`. Повторно прошли ABI на трёх ОС, изоляция Linux/Windows и аварийные сценарии systemd. Локальные сборки, тесты и обращения к пользовательскому Mac не выполнялись.

| Измерение | ARM64, macOS 15.8.2 / 24H232 | Intel, macOS 15.7.9 / 24G830 |
| --- | --- | --- |
| Исходное virtual_size, одиночный процесс | 420 447 207 424 байта | 34 939 760 640 байт |
| Исходное resident_size, `as` / 64 МиБ | 1 163 264 байта | 544 768 байт |
| RLIMIT_AS и RLIMIT_DATA: фиксированные 64/256/512 МиБ | setrlimit: EINVAL (22), не установлены | setrlimit: EINVAL (22), не установлены |
| Те же лимиты baseline+64 МиБ; mmap 96 МиБ | Лимит установлен, mmap: ENOMEM (12) | Лимит установлен, mmap: ENOMEM (12) |
| Два ребёнка с индивидуальным baseline+64 МиБ | Оба выделили и заполнили по 48 МиБ | Оба выделили и заполнили по 48 МиБ |
| Сумма снимков resident_size двух детей | 102 596 608 байт | 101 462 016 байт |
| Virtualization.framework isSupported | false | true |
| Диапазон guest RAM, сообщённый API | 4 МиБ — 7 ГиБ | 4 МиБ — 14 ГиБ |

Нативный механизм действительно ограничивает новые отображения: нельзя трактовать EINVAL фиксированных пределов как отсутствие RLIMIT вообще. Однако проверенные индивидуальные пределы виртуального пространства не дают требуемую общую квоту физической памяти дерева. Эти измерения не доказывают невозможность любого другого нативного решения.

Оба задания подтвердили `TestDarwinIsolationRejectsValidPaths`: защищённый ProcessHost не создаётся даже с корректными путями. Доступность Virtualization.framework на Intel позволяет перейти к отдельному прототипу загрузки Linux; готовность гостя и квот этим прогоном не проверялась. На данном ARM64 runner API недоступен.

## Решение и следующие критерии

До доказанной границы macOS не получает запасной запуск недоверенного WASM в основном процессе или в процессе только с мониторингом RSS. Добавлен тест с существующим исполняемым файлом и корректным абсолютным каталогом: NewProcessHost обязан вернуть ErrIsolation, чтобы успешные ABI-тесты не маскировали отсутствие изоляции.

Следующий кандидат — Linux guest через Virtualization.framework, но выбор пока не принят как готовая архитектура. Приёмка требует:

- доказать общую и индивидуальную квоту на реальном компиляторе и двух worker внутри гостя;
- определить отдельно бюджет guest RAM и расходы VMM/supervisor на macOS, не подменяя один другим;
- проверить смерть supervisor/VM, отсутствие оставшихся процессов и восстановление;
- иметь воспроизводимый GitHub CI на поддерживающем виртуализацию runner;
- решить подпись, entitlement, обновление и целостность гостевого образа.

Платформенная готовность P1 и локальные недоверенные расширения macOS остаются открытыми. Текущие встроенные функции и подключение приложения к отдельному серверу не меняются. Исследование не объявляет поддержку macOS завершённой и не меняет самостоятельно сроки выпуска 0.9.0.
