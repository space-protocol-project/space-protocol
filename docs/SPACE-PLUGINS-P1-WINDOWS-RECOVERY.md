# P1/E03: восстановление Windows LPAC после аварии supervisor

Продолжение [LPAC-прототипа](SPACE-PLUGINS-P1-WINDOWS-LPAC.md), 6 ноября 2026 года. `NewWindowsRestrictedHost` получает постоянный каталог состояния и восстанавливает незавершённую установку временного профиля перед созданием следующего. Рабочее приложение на этот конструктор пока не переключено; E03/P1 остаются открытыми, выпуск отложен.

## Владение каталогом и журнал

На всё время жизни хоста открывается `lpac.lock` через `CreateFile` с нулевым share mode. Второй supervisor не может открыть тот же файл, в том числе до запуска первого worker. Закрытие процесса освобождает handle средствами ОС. Пустой lock-файл остаётся на диске и не означает, что каталог занят; владение определяется открытым handle, а не PID или наличием файла.

До `CreateAppContainerProfile` записывается и синхронизируется `lpac-state.json`. Поля в порядке `version`, `root`, `id`: версия 1, SHA-256 нормализованного абсолютного пути корня и 16 случайных байтов в виде 32 строчных hex-символов. При чтении требуется точное совпадение с JSON-сериализацией структуры; размер не более 512 байт. Неизвестная версия, другой корень, лишние/повторяющиеся поля, некорректный ID и частичная запись запрещают запуск с сохранением журнала.

В журнале нет произвольных путей удаления и имён профилей. Из проверенных полей выводятся имя `Space.P1.<первые 16 символов root>.<id>`, каталог `lpac-<id>` и имя общего Job `Local\<имя профиля>`. Корень, lock-файл, журнал и удаляемый каталог снимка не должны быть reparse points. Корень должен принадлежать доверенному supervisor; защита от другого вредоносного процесса с той же учётной записью не заявляется. Лексические альтернативы одного пути не считаются автоматически совместимым идентификатором корня.

## Восстановление и штатное закрытие

После получения lock проверяется старый журнал. Если существует именованный Job, он открывается с правами query/terminate; старое дерево завершается и ожидается нулевое число активных процессов. Ошибка открытия, кроме отсутствующего Job, запрещает дальнейшую очистку. Новый хост получает такое же ограничение ресурсов, как раньше: 512 МиБ общего committed memory, 256 МиБ на вызов, CPU cap, ограничения процессов и kill-on-close.

Затем последовательно удаляются профиль через `DeleteAppContainerProfile`, собственный `worker.exe`, его каталог и журнал. Удаление каталога **не рекурсивное**: посторонний файл приводит к ошибке, сохраняется вместе с журналом и требует явного разбора. После удаления журнала можно создавать новое намерение и новый профиль. Штатный `Close` использует ту же уборку после остановки Job.

По [контракту Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/userenv/nf-userenv-deleteappcontainerprofile) удаление отсутствующего профиля успешно, а после неудачного удаления операцию следует повторить. Поэтому авария между удалением профиля и удалением журнала допускает повтор. Ошибка уборки не стирает журнал. Живой хост сохраняет lock для повторного `Close`; неудачный конструктор освобождает владение, оставляя журнал для следующей попытки.

| Точка аварии | Состояние при следующем запуске |
| --- | --- |
| После синхронизации намерения | Удаление отсутствующих профиля/снимка, новое намерение |
| После создания профиля | Удаление профиля, новое намерение |
| После копирования executable | Удаление профиля и собственной копии |
| Во время работы worker и потомка | Завершение старого дерева, уборка профиля/снимка, новый WASM-вызов |
| После удаления профиля до уборки снимка/журнала | Идемпотентное завершение уборки |
| Повреждённый журнал | Отказ без исправления или удаления журнала |
| Посторонний файл в снимке | Отказ от рекурсивного удаления; повтор после разбора файла |

## Приёмка GitHub CI

Пять сценариев запускают отдельный настоящий supervisor и завершают его через `Process.Kill` без `defer Close`. Стадии подготовки используют те же внутренние операции, что конструктор; рабочий сценарий вызывает полный `NewWindowsRestrictedHost` и создаёт настоящего потомка. До аварии проверяется отказ второму владельцу. После неё новый конструктор восстанавливает тот же корень; старые handles процессов должны сигнализировать завершение, прежний снимок должен исчезнуть, прежнее имя профиля должно снова допускать создание. Настоящий каталог профиля, полученный через `GetAppContainerFolderPath` и содержащий контрольный файл, должен отсутствовать. После контрольной проверки это имя удаляется.

Каждый сценарий завершается новым настоящим echo WASM, пустым Job, штатным закрытием и отсутствием журнала. Отдельно проверяются сохранение повреждённого журнала после двух попыток и повтор закрытия после постороннего файла. Журнал другого корня и символическая ссылка вместо журнала отклоняются; исходный хост остаётся работоспособным, внешний файл сохраняется. Прежние проверки LPAC, Job Objects, Linux и macOS повторяются полной матрицей P1.

## Границы

- Проверяется аварийное завершение процесса, а не потеря питания, диска или несинхронизированных записей файловой системы. `Sync` журнала не объявляется доказательством физической долговечности всех операций Windows.
- Проверяется Windows Server 2025 x64, та же учётная запись и сессия входа. Полный reboot, смена пользователя/сессии и восстановление из архивной копии требуют отдельной матрицы.
- Старые профили прежнего прототипа, созданные без журнала, автоматически не перечисляются и не удаляются. Нельзя безопасно объявить любой профиль с похожим именем собственностью текущего хоста.
- Удаляется временное хранилище sandbox-профиля, а не пользовательские данные расширений. Постоянные данные должны оставаться за доверенным broker API; квота диска профиля ещё открыта.
- Сетевая граница Winsock, расширенная матрица реестра/IPC, упаковка и включение в рабочее приложение остаются незавершёнными.
