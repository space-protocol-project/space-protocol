# P1/E03: восстановление Windows LPAC после аварии supervisor

Продолжение [LPAC-прототипа](SPACE-PLUGINS-P1-WINDOWS-LPAC.md), 6 ноября 2026 года. `NewWindowsRestrictedHost` получает постоянный каталог состояния и восстанавливает незавершённую установку временного профиля перед созданием следующего. Рабочее приложение на этот конструктор пока не переключено; E03/P1 остаются открытыми, выпуск отложен.

## Владение каталогом и журнал

На всё время жизни хоста открывается `lpac.lock` через `CreateFile` с нулевым share mode. Второй supervisor не может открыть тот же файл, в том числе до запуска первого worker. Закрытие процесса освобождает handle средствами ОС. Пустой lock-файл остаётся на диске и не означает, что каталог занят; владение определяется открытым handle, а не PID или наличием файла.

До `CreateAppContainerProfile` записывается и синхронизируется `lpac-state.json`. Поля в порядке `version`, `root`, `id`: версия 1, SHA-256 нормализованного абсолютного пути корня и 16 случайных байтов в виде 32 строчных hex-символов. При чтении требуется точное совпадение с JSON-сериализацией структуры; размер не более 512 байт. Неизвестная версия, другой корень, лишние/повторяющиеся поля, некорректный ID и частичная запись запрещают запуск с сохранением журнала.

В журнале нет произвольных путей удаления и имён профилей. Из проверенных полей выводятся имя `Space.P1.<первые 16 символов root>.<id>`, каталог `lpac-<id>` и имя общего Job `Local\<имя профиля>`. Корень, lock-файл, журнал и удаляемый каталог снимка не должны быть reparse points. Корень должен принадлежать доверенному supervisor; защита от другого вредоносного процесса с той же учётной записью не заявляется. Лексические альтернативы одного пути не считаются автоматически совместимым идентификатором корня.

## Восстановление и штатное закрытие

После получения lock проверяется старый журнал. Если существует именованный Job, он открывается с правами query/terminate; старое дерево завершается и ожидается нулевое число активных процессов. Ошибка открытия, кроме отсутствующего Job, запрещает дальнейшую очистку. Новый хост получает такое же ограничение ресурсов, как раньше: 512 МиБ общего committed memory, 256 МиБ на вызов, CPU cap, ограничения процессов и kill-on-close.

Затем последовательно удаляются профиль через `DeleteAppContainerProfile`, собственный `worker.exe`, его каталог и журнал. Удаление каталога **не рекурсивное**: посторонний файл приводит к ошибке, сохраняется вместе с журналом и требует явного разбора. После удаления журнала можно создавать новое намерение и новый профиль. Штатный `Close` использует ту же уборку после остановки Job.

По [контракту Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/userenv/nf-userenv-deleteappcontainerprofile) удаление отсутствующего профиля успешно, а после неудачного удаления операцию следует повторить. Поэтому авария между удалением профиля и удалением журнала допускает повтор. Ошибка уборки не стирает журнал. Живой хост сохраняет lock для повторного `Close`; неудачный конструктор освобождает владение, оставляя журнал для следующей попытки.

| Точка аварии | Состояние при следующем запуске |
| --- | --- |
| После синхронизации намерения | Удаление отсутствующих профиля/снимка, новое намерение |
| После создания профиля | Удаление профиля, новое намерение |
| После копирования executable | Удаление профиля и собственной копии |
| Во время работы настоящего worker (уточнено ниже) | Завершение старого дерева, уборка профиля/снимка, новый WASM-вызов |
| После удаления профиля до уборки снимка/журнала | Идемпотентное завершение уборки |
| Повреждённый журнал | Отказ без исправления или удаления журнала |
| Посторонний файл в снимке | Отказ от рекурсивного удаления; повтор после разбора файла |

## Приёмка GitHub CI

Пять сценариев запускают отдельный настоящий supervisor и завершают его через `Process.Kill` без `defer Close`. Стадии подготовки используют те же внутренние операции, что конструктор; рабочий сценарий вызывает полный `NewWindowsRestrictedHost` и удерживает настоящий работающий worker. Прежнее утверждение о создании потомка отозвано по результатам уточнения ниже. До аварии проверяется отказ второму владельцу. После неё новый конструктор восстанавливает тот же корень; старые handles процессов должны сигнализировать завершение, прежний снимок должен исчезнуть, прежнее имя профиля должно снова допускать создание. Настоящий каталог профиля, полученный через `GetAppContainerFolderPath` и содержащий контрольный файл, должен отсутствовать. После контрольной проверки это имя удаляется.

Каждый сценарий завершается новым настоящим echo WASM, пустым Job, штатным закрытием и отсутствием журнала. Отдельно проверяются сохранение повреждённого журнала после двух попыток и повтор закрытия после постороннего файла. Журнал другого корня и символическая ссылка вместо журнала отклоняются; исходный хост остаётся работоспособным, внешний файл сохраняется. Прежние проверки LPAC, Job Objects, Linux и macOS повторяются полной матрицей P1.

## Границы

- Проверяется аварийное завершение процесса, а не потеря питания, диска или несинхронизированных записей файловой системы. `Sync` журнала не объявляется доказательством физической долговечности всех операций Windows.
- Проверяется Windows Server 2025 x64, та же учётная запись и сессия входа. Полный reboot, смена пользователя/сессии и восстановление из архивной копии требуют отдельной матрицы.
- Старые профили прежнего прототипа, созданные без журнала, автоматически не перечисляются и не удаляются. Нельзя безопасно объявить любой профиль с похожим именем собственностью текущего хоста.
- Удаляется временное хранилище sandbox-профиля, а не пользовательские данные расширений. Постоянные данные должны оставаться за доверенным broker API; квота диска профиля ещё открыта.
- [Базовая матрица реестра/IPC и сетевых операций](SPACE-PLUGINS-P1-WINDOWS-RESOURCES.md) принята следующим срезом. Сетевой фильтр, наследование handles, межпрофильный доступ, упаковка и включение в рабочее приложение остаются незавершёнными.

## Уточнение аварийного сценария: PID, NUL и conhost

Проверки 6 ноября 2026 года обнаружили недостаток прежней приёмки `running`: два PID в Job не гарантируют наличия worker и его настоящего потомка. Один из процессов мог быть системным `conhost.exe`; кроме того, результат фонового `h.run` игнорировался. Поэтому прежний успешный прогон сам по себе не доказывал эту часть сценария.

- [42172763706](https://github.com/space-protocol-project/space-server/actions/runs/42172763706): удержание handles и проверка живого состояния выявили досрочное завершение с кодом 3 в 11 из 25 циклов. Это код отказа запуска потомка в тестовом p1-pressure.
- [42173042856](https://github.com/space-protocol-project/space-server/actions/runs/42173042856): вывод результата фонового вызова установил конкретную ошибку `child_start_error=open NUL: Access is denied.`. Неуказанный stdin заставлял Go открывать NUL внутри LPAC. Потомку теперь передаётся уже разрешённый stdin; права профиля не расширяются.
- [42173409750](https://github.com/space-protocol-project/space-server/actions/runs/42173409750): обязательная проверка QueryFullProcessImageName обнаружила conhost вместо ожидаемого worker.exe. Тестовый потомок теперь создаётся с CREATE_NO_WINDOW, однако [42173975760](https://github.com/space-protocol-project/space-server/actions/runs/42173975760) показал, что это не исключает вспомогательный conhost из Job. Промежуточное ожидание стало выбирать два процесса по полному пути staged worker.exe, не по общему числу PID. Этот диагностический прогон остановился по прежнему общему тайм-ауту; тайм-аут не увеличивался.

[42174489372](https://github.com/space-protocol-project/space-server/actions/runs/42174489372) установил следующий отказ: после устранения NUL, fork/exec staged worker.exe получает Access is denied. Существующий LPAC-профиль не позволяет этому probe создать настоящий дочерний worker. Защита не ослаблялась ради воспроизведения дерева. TestWindowsRestrictedTree заменён явной проверкой отказа child spawn: ErrWorker и числовой ERROR_ACCESS_DENIED (5), затем пустой Job. Это измеренный отказ конкретного пути запуска, а не доказательство универсального запрета всех способов создания процессов.

Итоговый аварийный сценарий запускает один настоящий worker с запросом hang и находит его по полному пути executable. Исчезновение вспомогательного PID при опросе допускается только с ERROR_INVALID_PARAMETER и лишь до выбора настоящего worker; общий предел ожидания — 5 секунд. Ошибки открытия выбранного worker, его досрочное завершение и отсутствие worker приводят к провалу без повторного аварийного цикла. Остановка дерева настоящих потомков остаётся отдельной проверкой прежнего Job-профиля; она не объявляется принятым LPAC-сценарием.

Перед публикацией PID helper открывает handles SYNCHRONIZE/PROCESS_QUERY_LIMITED_INFORMATION и удерживает их до своей аварийной смерти. Проверяются живое состояние и полный путь каждого worker. Родитель открывает собственные handles и повторно требует живое состояние до остановки supervisor. После аварии по тем же handles проверяется завершение. Досрочно завершившийся процесс не засчитывается как успешно остановленный аварией. Диагностика сохраняет PID, wait status, exit code и результат фонового h.run.

Отдельный контроль завершает процесс при удержанном handle: объект остаётся доступен по PID, но WaitForSingleObject показывает завершение. Это соответствует [жизненному циклу объектов Windows](https://learn.microsoft.com/en-us/windows/win32/procthread/terminating-a-process). Контроль не объявляет любое наличие handle доказательством работающего процесса.

В Linux диагностический прогон также выявил гонку приёмки: файл барьера появился раньше, чем systemd обработал READY=1. Перед внедрением аварии теперь ожидается требуемое ActiveState через существующее ограниченное по времени ожидание. Проверки завершения дерева, RestartSec, числа перезапусков и готовности нового supervisor сохранены.

Итоговая [полная матрица 42174994308](https://github.com/space-protocol-project/space-server/actions/runs/42174994308) успешна для `b6c6db88ccd6262f24d60d32ba38bf08445db734`: **9/9 заданий**, Go test/vet/mod verify/govulncheck, race на трёх ОС, Linux isolation/systemd и macOS probes. Все **25/25 дополнительных аварийных циклов running** прошли без повторов, как и пять базовых стадий. Каждый цикл завершился очисткой прежнего профиля и снимка, новым успешным echo WASM и пустым Job.

В Windows — **57 результатов pass LPAC**, **18 прежнего Job-профиля**, два ожидаемых helper-пропуска; числа включают родительские и дочерние записи Go test. Контроль удержанного завершённого процесса получил exit code 1 и signaled handle. Отдельная попытка запуска потомка из LPAC вернула ровно код 5. Это корректирует прежнюю приёмку: доказаны восстановление настоящего worker и конкретный отказ child spawn, а не остановка настоящего LPAC-потомка.

[Исходные результаты, systemd и диагностические прогоны](p1-results/2026-11-06-windows-lpac-recovery-stability/) сохранены с [SHA256SUMS](p1-results/2026-11-06-windows-lpac-recovery-stability/SHA256SUMS). Итоговая приёмка — один полный прогон на финальном коммите, без повторов отдельных упавших заданий. Диагностические прогоны с ошибками и тайм-аутами приёмкой не считаются. P1/E03 остаются открытыми; рабочая политика запуска и квоты не меняются.
