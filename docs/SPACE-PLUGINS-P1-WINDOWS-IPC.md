# P1/E03: межпрофильные границы именованных IPC-объектов Windows

6 ноября 2026 года. Продолжение [файловых границ LPAC](SPACE-PLUGINS-P1-WINDOWS-HANDLES.md). Проверяется отдельный прототип `NewWindowsRestrictedHost` в Windows CI. Рабочий broker приложения и сервера не подключается, capabilities и политика запуска не расширяются.

## Объекты и права

Тестовый supervisor создаёт по одному manual-reset event и именованному duplex pipe для каждого из двух разных package SID. Имена случайны, ресурсы принадлежат только этому тесту. DACL разрешает полный доступ текущему пользователю и SYSTEM, а одному package SID — только нужные права:

- event: EVENT_MODIFY_STATE и SYNCHRONIZE;
- pipe: FILE_READ_DATA, FILE_WRITE_DATA, FILE_READ_ATTRIBUTES и SYNCHRONIZE, без FILE_CREATE_PIPE_INSTANCE.

Event создаётся с явным Global-именем. Pipe supervisor создаёт по полному адресу `\\.\pipe\Sessions\<session>\AppContainerNamedObjects\<SID>\<name>`. Относительная часть получается через [GetAppContainerNamedObjectPath](https://learn.microsoft.com/en-us/windows/win32/api/securityappcontainer/nf-securityappcontainer-getappcontainernamedobjectpath), сессия — через ProcessIdToSessionId. Свой LPAC-клиент использует `\\.\pipe\LOCAL\<name>`, а чужой профиль получает явный адрес целевого объекта. Успех/отказ относится одновременно к этому пути и ACL, не к одному лишь DACL в отрыве от пространства имён.

Pipe создаётся как первая и единственная инстанция, с PIPE_REJECT_REMOTE_CLIENTS. Перед каждой проверкой он пересоздаётся: отказ не может объясняться занятостью предыдущим клиентом. Event сбрасывается перед вызовом, после него supervisor проверяет реальное signaled-состояние.

Оба объекта имеют low integrity label с NO_WRITE_UP. Иначе отказ записи мог бы исходить из MIC даже для своего package SID; это не проверяло бы разделение профилей. Основания: [Mandatory Integrity Control](https://learn.microsoft.com/en-us/windows/win32/secauthz/mandatory-integrity-control) и [права named pipe](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights). Правила применены только к созданным тестом объектам, не к пользовательским каталогам или системным объектам.

## Сценарии

Один и тот же нативный `p1-rights` выполняет OpenEvent/SetEvent и CreateFile для duplex-доступа к pipe. Для своего профиля обе операции обязаны завершиться успешно. Чужому SID событие должно вернуть ровно ERROR_ACCESS_DENIED (5). Для pipe отдельно различаются ERROR_ACCESS_DENIED (5) и ERROR_FILE_NOT_FOUND (2): второй означает недоступность чужого имени и не объявляется доказательством отказа DACL. Занятость канала, тайм-ауты и любые другие причины не принимаются. Исходные числовые коды сохраняются в журнале; скрытие имени дополнительно помечается pipe_namespace_hidden=true, dacl_denial_proven=false.

1. Обычный NewProcessHost успешно открывает оба комплекта объектов тем же executable. Затем A обращается к объектам A; B обращается к объектам B — положительные контроли.
2. A обращается к объектам B; B обращается к объектам A — отказы, чужое событие остаётся несигнализированным. Затем каждый повторно успешно использует свои объекты.
3. Хост A закрывается; B повторно успешно использует свои объекты.
4. Создаётся новый хост C с новым SID; доступ к сохранившемуся тестовому объекту старого A и объекту B должен быть запрещён.

После каждого probe Job пуст, активные вызовы и резервирование равны нулю. Объекты создаёт и удаляет supervisor; закрытие LPAC-профиля не объявляется автоматическим удалением чужих handles supervisor.

## Дополнение: обмен, проверка клиента и отмена

Следующий срез добавляет настоящий обмен четырьмя байтами `ping`/`pong` через профильный named pipe. Это нативный исследовательский probe, не транспорт рабочих команд и не новая версия ABI.

До чтения запроса и ответа supervisor получает PID через [GetNamedPipeClientProcessId](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getnamedpipeclientprocessid), открывает handle процесса, проверяет принадлежность Job этого хоста и выполняет существующую проверку LPAC-токена: AppContainer, точный package SID, отсутствие capabilities и отказ ALL_APPLICATION_PACKAGES при AccessCheck. Тот же подключённый клиент должен быть отвергнут проверкой другого хоста. PID не берётся из сообщения клиента.

Сервер использует [overlapped I/O](https://learn.microsoft.com/en-us/windows/win32/ipc/synchronous-and-overlapped-input-and-output) с отдельным manual-reset event для каждой операции. Ожидание ограничено пятью секундами; при превышении вызывается CancelIoEx и ожидается завершение операции перед освобождением OVERLAPPED и буфера. Общий deadline worker — десять секунд. Клиент выполняет прямые Win32 ReadFile/WriteFile и открывает канал с SECURITY_SQOS_PRESENT/SECURITY_IDENTIFICATION; он не запрашивает режим impersonation.

Пять сценариев: успешный обмен A, успешный обмен B, отмена A после чтения его запроса, новый успешный обмен A, продолжение работы B. Перед отменой сервер начинает второе чтение и требует ERROR_IO_PENDING: проверяется действительно незавершённый I/O. Клиенту ответ не отправляется; supervisor требует context.Canceled, ERROR_BROKEN_PIPE без новых байтов, пустой Job и отсутствие активных вызовов/резервирования. Успешный обмен требует точных четырёх байтов в обе стороны и положительной квитанции probe через отдельный stdout.

В [42178766293](https://github.com/space-protocol-project/space-server/actions/runs/42178766293) обмен и отмена прошли, но повторное соединение после отмены не установилось. [42179049950](https://github.com/space-protocol-project/space-server/actions/runs/42179049950) подтвердил это с незавершённым чтением. В [42179203139](https://github.com/space-protocol-project/space-server/actions/runs/42179203139) сохранён точный ответ нового worker: FILE_NOT_FOUND (2), а не ошибка LPAC-токена.

Порядок тестового запуска изменён: createContained создаёт приостановленный процесс в обоих Job, проверяется LPAC-токен, затем создаётся серверный pipe в новом пространстве контейнера и выполняется ResumeThread. Используются существующие launcher и exchangeProcess; обычный конструктор и рабочий транспорт приложения не меняются. Временные handles, каналы и Job закрываются после подтверждённого завершения обмена. Для будущего broker эта последовательность является требованием подготовки endpoint, а не разрешением повторять неудачные команды.

## Дополнение: проверка сервера до отправки запроса

Доверенный тестовый supervisor передаёт клиенту через отдельный stdin параметры endpoint: имя, ожидаемые PID и Windows session ID сервера, случайное 128-битное значение на один вызов. Эти параметры не получаются от самого pipe-сервера или из сообщений расширения. Это контракт исследовательского запуска, не публичный ABI и не рабочая выдача разрешений.

После открытия канала клиент вызывает [GetNamedPipeServerProcessId](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getnamedpipeserverprocessid) и [GetNamedPipeServerSessionId](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getnamedpipeserversessionid), сравнивает результаты с доверенными параметрами и читает 16 байтов подтверждения сервера. Значение сравнивается через constant-time comparison. Только после всех проверок отправляется `ping`. Нулевой ожидаемый PID, неверная длина подтверждения и несовпадение значений приводят к отказу.

Supervisor, как в предыдущем срезе, сначала проверяет PID/Job/LPAC-токен подключённого клиента, затем отправляет подтверждение и принимает запрос. Обычные сценарии обмена, отмены и восстановления повторяются с этим порядком. Время жизни supervisor охватывает весь вызов; при его смерти Job должен завершать worker. PID не является постоянной идентичностью сервера между перезапусками.

Отрицательные проверки:

- Настоящий сервер отправляет 16 байтов с изменённым первым байтом. Клиент возвращает ERROR_ACCESS_DENIED; сервер наблюдает закрытие pipe и ноль байтов запроса.
- Доверенный тестовый запуск намеренно содержит неверную session ID. Клиент отклоняет сервер до чтения подтверждения и отправки запроса.
- Отдельный обычный процесс создаёт pipe в правильном пространстве профиля с разрешающей DACL. Его PID отличается от ожидаемого supervisor. Клиент обязан отклонить его, а подставной сервер — подтвердить отсутствие данных запроса. Проверка не сводится к невозможности открыть endpoint.
- Пока подставной сервер держит имя, создание ещё одной инстанции с FILE_FLAG_FIRST_PIPE_INSTANCE должно вернуть ровно ERROR_ACCESS_DENIED. Только этот тест использует два слота: тот же второй экземпляр без FIRST_PIPE_INSTANCE обязан успешно создаться и сразу закрывается до подключения клиента. Это отделяет защиту имени от исчерпания числа экземпляров. Обычные fixture сохраняют один слот. Новый сервер не присоединяется к занятому имени молча.

Этот прогон не считается приёмкой: добавлен контроль со свободным вторым слотом. [Полная матрица 42183072720](https://github.com/space-protocol-project/space-server/actions/runs/42183072720) успешна для `8a7aee988afaf9f632250a9e9b5225030285d7d7`: **9/9 заданий**, test/vet/mod verify/govulncheck, race на трёх ОС, Linux isolation/systemd и macOS probes. Прежние обмен/отмена/повторное соединение прошли с проверкой сервера до запроса.

Отрицательные сценарии неверной сессии, неверного подтверждения и настоящего подставного процесса успешны: ERROR_ACCESS_DENIED у клиента и ровно ноль байтов запроса у сервера. В подставном сценарии PID сервера 2932 отличался от ожидаемого 1764. FIRST_PIPE_INSTANCE отклонён с кодом 5; второй слот без этого флага успешно открыт и закрыт до клиентского подключения. Секреты реального пользователя в тестах не используются.

## Дополнение: отключение отдельного канала без остановки worker

Нативный прототип проверяет транспортный механизм отзыва через [DisconnectNamedPipe](https://learn.microsoft.com/en-us/windows/win32/api/namedpipeapi/nf-namedpipeapi-disconnectnamedpipe). Один LPAC-процесс открывает два независимых endpoint своего профиля: канал данных и контрольный канал. Оба проходят проверку PID/Job/LPAC на сервере и PID/session/случайного подтверждения на клиенте. Сначала канал данных успешно выполняет ping/pong: проверяется отзыв ранее работавшего доступа, а не исходный запрет открытия.

После подключения контрольного канала supervisor отключает только серверный экземпляр канала данных. DACL не меняется, Job не завершается. Ответ контрольного канала служит барьером: проверки старого handle начинаются после успешного DisconnectNamedPipe. Клиент проверяет чтение, запись и новый CreateFile к отозванному endpoint, затем выполняет ещё один ping/pong по контрольному каналу. Supervisor повторно проверяет PID/Job/LPAC контрольного соединения и требует, чтобы handle процесса оставался несигнальным. Итоговый ответ содержит тот же PID; после штатного выхода проверяется пустой Job.

Два сценария: отключение без непрочитанных данных и отключение после записи четырёх байтов ответа в буфер канала. Во втором случае клиент до барьера занят контрольным каналом и не читает канал данных. После отключения чтение должно вернуть ошибку и ноль байтов: ранее буферизованный ответ не доставляется. Уже прочитанные клиентом данные отозвать невозможно.

Отключённый серверный handle сохраняется до завершения сценария, ConnectNamedPipe повторно не вызывается. Поэтому ожидаемый отказ нового CreateFile — PIPE_BUSY, а не ACCESS_DENIED. Это состояние закрытого для новых подключений экземпляра, не постоянный запрет имени: повторная выдача доступа, смена поколения и защита от повторного открытия после пересоздания endpoint требуют управляющего broker.
