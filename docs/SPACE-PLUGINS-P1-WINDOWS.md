# P1: изоляция WASM на Windows

Продолжение от 30 октября 2026 года. [Контракты P1](SPACE-PLUGINS-P1.md), [предыдущий Linux-профиль](SPACE-PLUGINS-P1-ISOLATION.md), [TODO](../TODO.md). Реализация остаётся в `space-server/experiments/extensions`, без подключения к рабочему серверу.

## Граница процесса

Для Windows добавлен `ProcessHost` на Job Objects. Один экземпляр принадлежит всему серверу; два параллельных вызова используют общий бюджет. Конструктор получает доверенные абсолютные пути к рабочему каталогу и бинарнику worker. Эти пути не берутся из manifest расширения. Для macOS защищённый запуск по-прежнему возвращает `ErrIsolation`.

Worker создаётся с `CREATE_SUSPENDED` и `CREATE_NO_WINDOW`. Пока основной поток приостановлен, supervisor назначает процесс сначала в общий Job Object, затем во вложенный Job конкретного вызова. Только после двух успешных назначений вызывается `ResumeThread`. Если назначение или возобновление невозможно, процесс принудительно завершается и ожидается; исполнения без ограничений в качестве запасного варианта нет.

Компиляция и выполнение остаются в одноразовом worker; в основной процесс готовый объект wazero не возвращается. Между запросами скомпилированный код не сохраняется. ABI, проверка JSON и ограничения линейной памяти не менялись.

## Параметры Windows-профиля

| Ресурс | Ограничение |
| --- | --- |
| Worker и его потомки | Вложенный Job: committed memory до 256 МиБ |
| Все worker общего ProcessHost | Родительский Job: committed memory до 512 МиБ |
| Admission | Два вызова по 256 МиБ зарезервированного бюджета; третьему отказ без очереди |
| CPU | Общий Job: hard cap 50% процессорного времени, предоставляемого Windows; это не эквивалент одного ядра на всех машинах |
| Число процессов | До 64 на общий Job и вложенный Job; потоки этим счётчиком не ограничиваются |
| Полный запрос | Deadline 2 с либо более ранняя отмена; внутренний deadline WASM 100 мс сохраняется |
| IPC | Вход WASM 64 КиБ / JSON 16 КиБ, stdout 16 КиБ, stderr 4 КиБ |
| Окружение | GOMAXPROCS, GOMEMLIMIT и добавляемый Go системный SystemRoot; остальные переменные не наследуются |

Используются именно `JOB_OBJECT_LIMIT_JOB_MEMORY`, а не мягкие ограничения working set. [Windows определяет этот лимит через committed memory](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_extended_limit_information). Его нельзя напрямую сопоставлять с RSS, working set или учитываемой памятью Linux cgroup. Windows может отклонить запрос выделения памяти; это не та же модель, что Linux OOM-kill всей группы.

`ProcessStats.PeakBytes` на Windows — `PeakJobMemoryUsed` общей группы; `OSProcesses` — число активных процессов по данным ОС. Текущее потребление, `OOMKills` и число периодов throttling этим профилем не измеряются: нули в соответствующих полях не означают доказанный нулевой расход/отсутствие ограничений. CPUUsec получается из времени user/kernel группы. Применение CPU-политики проверяется чтением настроек Job, а не выдуманным счётчиком throttling.

## Очистка и границы доверия

Оба Job имеют `KILL_ON_JOB_CLOSE`, без разрешения breakaway; их handles не передаются worker. Вызов отменяется через `TerminateJobObject`, охватывающий дерево процессов. Дополнительный `Process.Kill` закрывает окно отмены до назначения приостановленного процесса в Job. После Wait повторно прекращаются оставшиеся потомки, и проверяется, что ActiveProcesses стал нулём. Если очистку подтвердить не удалось, новые вызовы запрещаются.

Превышение stdout/stderr немедленно останавливает Job: большой аварийный вывод не должен задерживать завершение до общего deadline. Close сначала запрещает новые запросы; при активных вызовах возвращает ErrQuota и требует отмены/завершения их контекстов перед повторным Close.

Процесс работает под той же Windows-учётной записью, что supervisor. Restricted token, AppContainer и ограничения доступа к файловой системе/сети здесь не реализованы. Это профиль изоляции ресурсов и аварий, а не полная защита от эксплуатации уязвимости нативного компилятора. Рабочее подключение требует отдельной политики запуска и прав.

`KILL_ON_JOB_CLOSE` обеспечивает завершение назначенных процессов при закрытии последних handles. Однако авария supervisor между созданием приостановленного процесса и назначением Job ещё требует отдельного решения и теста восстановления. Текущий тест отказа назначения не заменяет тест смерти supervisor. Существующие ограничения внешнего Job среды запуска также могут привести к отказу; они не обходятся.

## Проверки CI

В `plugin-p1.yml` добавлена отдельная задача `windows-isolation` на Windows Server 2025 x64. Worker собирается обычным Go, supervisor и тесты — с `-race`. Старые задачи Linux cgroup и трёхплатформенный ABI запускаются вместе с ней. В общей матрице выполняются go test, go test -race, vet, mod verify и govulncheck. Локальные сборки и тесты не запускались.

| Сценарий | Проверяемый результат |
| --- | --- |
| Настоящий WASM | Compiler/interpreter, свежие globals, memory.grow, Core start, host calls, циклы, неверные указатели/JSON/импорты, нормальный вызов после ошибок |
| Настройки ОС | Чтение memory limit, active-process limit, CPU hard cap и kill-on-close непосредственно из Job |
| Отказ памяти | Стенд последовательно вызывает VirtualAlloc с MEM_COMMIT/MEM_RESERVE; получает код отказа памяти до запрошенных 384 МиБ |
| Общая память | Два процесса удерживают по 64 МиБ и синхронизируются событиями Windows. Затем каждый запрашивает 208 МиБ при временном общем лимите 256 МиБ; хотя бы один получает отказ VirtualAlloc |
| Ошибки worker | Go allocation pressure, зависание, CPU-нагрузка, отдельный потомок, неограниченный вывод и panic; после отказов нормальный WASM снова работает |
| Admission | Два реально существующих процесса, отказ третьему, отмена, освобождение резерва и запрет новых вызовов после Close |
| Ошибка назначения Job | Неверный Job handle; специальный worker не успевает создать контрольный файл, процессов в Job не остаётся |
| Окружение | Тестовый секрет не наследуется; остаются только три разрешённые переменные |

Прямой тест VirtualAlloc добавлен отдельно от Go allocation pressure: реакция Go на нехватку памяти и диагностический вывод не должны подменять подтверждение отказа ОС. Чтение peak общей группы также не является заменой этому тесту. Аварийные режимы находятся только в `cmd/p1-pressure`; настоящий WASM worker не предоставляет их расширениям.

Итоговый [CI 40967502375](https://github.com/space-protocol-project/space-server/actions/runs/40967502375) завершился успешно для `ba813abc944ca0a9d5602fe8fb9260b04770a566`: все шесть заданий, включая Linux isolation и три платформы ABI. Windows isolation: 8 верхнеуровневых тестов и 6 подтестов (14 результатов pass, без пропусков), 10,198 с для пакета с race detector.

Наблюдаемый peak родительского Job в нативных тестах — 282 537 984 байта для одного worker и 279 384 064 байта для общей квоты. Эти значения сохранены без подгонки: peak родительского Job не используется как доказательство точного потолка дочернего Job. Отказ проверяется непосредственно результатом VirtualAlloc и чтением настроенного лимита; причина расхождения peak и лимита отдельно не установлена.

[Исходные журналы и метаданные](p1-results/2026-10-30-windows), [SHA256SUMS](p1-results/2026-10-30-windows/SHA256SUMS) закрепляют результаты. Первый [прогон 40966262933](https://github.com/space-protocol-project/space-server/actions/runs/40966262933) выявил ошибочное сравнение родительского peak с дочерним лимитом и неоднозначный сценарий давления Go. Добавлены прямые проверки VirtualAlloc и немедленная остановка при переполнении вывода. Второй [прогон 40967118580](https://github.com/space-protocol-project/space-server/actions/runs/40967118580) подтвердил одиночный отказ памяти, но выявил совпадение имён событий стенда; имена заменены случайными. Итоговый прогон повторил все проверки успешно. Автоматические полные сборки неизменённого рабочего сервера остановлены; приёмка относится к отдельному модулю прототипа. Последующий документационный коммит не меняет проверенный код.
