# P1: изоляция компилятора и общие квоты памяти

Продолжение P1 от 30 октября 2026 года. [Первый прототип](SPACE-PLUGINS-P1.md), [план](../TODO.md). Рабочий сервер по-прежнему не импортирует экспериментальный модуль; установка пользовательских расширений ещё недоступна.

## Решение

В `space-server/experiments/extensions` добавлен `ProcessHost`. Компиляция и исполнение выполняются в отдельном одноразовом `p1-worker`, который получает один ограниченный запрос через stdin и возвращает JSON через stdout. В основной процесс не возвращается объект `wazero.CompiledModule`, и повторной компиляции там нет. Прежний внутрипроцессный хост переименован в закрытый `localHost`; он используется worker и тестами ABI.

Профиль изоляции реализован для **Linux с cgroup v2**. На дату исходного прогона Windows/macOS `NewProcessHost` возвращал `ErrIsolation` (позднее добавлен [Windows-профиль](SPACE-PLUGINS-P1-WINDOWS.md)): старые ABI-тесты на этих ОС не означают наличие защиты процесса. Перехода к исполнению в основном процессе при отказе нет.

Один `ProcessHost` должен принадлежать всему серверу и обслуживать все пространства и расширения. Создание отдельного хоста для каждого плагина создаст независимые бюджеты и нарушит этот контракт интеграции. Подключение общего экземпляра к рабочему серверу — будущая задача, сейчас проверяется его API.

## Ограничения

| Ресурс | Значение и механизм |
| --- | --- |
| Память одного worker и его потомков | `memory.max = 268435456` — 256 МиБ |
| Общая память всех активных worker одного ProcessHost | Родительская cgroup: `memory.max = 536870912` — 512 МиБ |
| Swap | `memory.swap.max = 0` на обоих уровнях |
| Одновременные запросы | Не более двух; каждый заранее резервирует 256 МиБ. Третий получает `ErrQuota`, очереди нет |
| CPU | `cpu.max = 100000 100000` на обоих уровнях; все worker вместе делят пропускную способность одного CPU |
| Потоки/процессы | `pids.max = 64` на обоих уровнях, включая потомков |
| Полный запрос | Deadline 2 секунды либо более ранняя отмена вызывающего кода; включает запуск, компиляцию и выполнение |
| Выполнение WASM | Сохраняется внутренний deadline 100 мс, включая Core start / alloc / handle / free |
| Вход | WASM до 64 КиБ, JSON до 16 КиБ; IPC после base64 ограничен 128 КиБ |
| Выход | stdout до 16 КиБ; stderr до 4 КиБ, наружу его содержимое не возвращается |
| Кеш между запросами | Отключён: сохраняемый объём скомпилированного кода между вызовами равен нулю |

Это лимиты экспериментального профиля, не рекомендуемые производственные размеры. Цена отказа от общего кеша — компиляция на каждом запросе. Кеш можно вернуть только вместе с измеряемой байтовой квотой и безопасной границей загрузки; повторно компилировать модуль в основном процессе ради кеширования нельзя.

Резервирование происходит **до** сериализации и запуска worker, поэтому память IPC не растёт пропорционально числу ожидающих запросов. Квота освобождается после завершения процесса и очистки cgroup. Сам вызывающий сервер, его БД, исходные буферы вызывающего кода и прочие функции не находятся под этим лимитом; передаваемые WASM/JSON проверяются по длине. `GOMEMLIMIT=64MiB` помогает сборщику мусора внутри worker, но защитной границей служит cgroup, а не эта подсказка Go.

`memory.current` / `memory.peak` отражают память, учитываемую cgroup, включая соответствующие расходы ядра, а не сумму RSS из `/proc`. Разделяемые страницы учитываются по правилам ядра. `memory.max` может кратковременно превышаться при обработке выделения/OOM; нельзя обещать строгое равенство peak пределу в каждом отсчёте. В отчёт сохраняются реальные peak и счётчик `oom_kill`, без подмены их зарезервированным бюджетом. [Семантика cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html).

## Запуск и завершение

1. Администратор предоставляет выделенный корень cgroup v2 с memory/cpu/pids и доверенный абсолютный путь к worker. Прототип требует привилегированного supervisor; root и путь к бинарнику не берутся из manifest.
2. До старта дочернего процесса создаются и настраиваются родительская и дочерняя cgroup. Проверяется доступность `cgroup.kill`. Если это невозможно, вызов отклоняется.
3. `UseCgroupFD` помещает процесс в cgroup при создании, до исполнения пользовательского кода. Схема «сначала запустить, потом переместить PID» не используется. [Реализация запуска в Go](https://github.com/golang/go/blob/go1.27.3/src/syscall/exec_linux.go).
4. Worker запускается под UID/GID 65534, без дополнительных групп. Рабочий каталог `/`; окружение содержит только GOMAXPROCS/GOMEMLIMIT. Секреты окружения supervisor не наследуются. Каталоги управления cgroup принадлежат привилегированному supervisor.
5. На отмене используется `cgroup.kill`, охватывающий дерево процессов; затем процесс ожидается через `Wait`. `WaitDelay` ограничивает ожидание зависших pipe. На обычном завершении также уничтожаются оставшиеся потомки.
6. После завершения удаляется дочерняя cgroup. Если очистка не удалась, хост закрывает admission и возвращает `ErrIsolation`, вместо повторного использования сомнительной квоты. Для удаления cgroup предусмотрено до одной секунды; поэтому возврат из вызова не является real-time гарантией ровно 2 секунд.

`Close` запрещает новые запросы. Если ещё есть активные вызовы, возвращается `ErrQuota`; владелец отменяет их контексты, дожидается завершения и повторяет Close. Автоматического незаметного обрыва чужих запросов при Close нет.

Это **изоляция ресурсов и аварий компилятора**, а не полный системный sandbox против эксплуатации уязвимости нативного компилятора. WASI по-прежнему отсутствует, но у процесса не добавлены seccomp, файловые и сетевые namespaces. UID 65534 выбран для стенда; для эксплуатации необходим выделенный служебный пользователь, неизменяемый worker, отдельный launcher/service и политика его прав. Позднее добавлено [восстановление оставшихся cgroup при новом запуске](SPACE-PLUGINS-P1-RECOVERY.md). Немедленная очистка при смерти supervisor и автоматический перезапуск требуют интеграции с управляющей службой. Эти ограничения не закрываются успешным тестом остановки потомков по тайм-ауту.

## Проверки GitHub CI

Workflow `space-server/.github/workflows/plugin-p1.yml` включает отдельную обязательную задачу `isolation` на Ubuntu 24.04. Worker и инструмент отказов собираются в CI; тестовый supervisor собирается с `-race`. При отсутствии cgroup v2 или привилегий задача падает, а не выдаёт успешный пропуск. Обычная матрица Linux/Windows/macOS сохраняет `go test`, `go test -race`, `go vet`, `go mod verify`, `govulncheck` и проверку отказа без поддерживаемой границы ОС.

| Проверка | Что подтверждается |
| --- | --- |
| `CompileAndRecover` | Настоящие WASM-модули: compiler/interpreter, свежие globals, memory.grow, запрет host calls в Core start, циклы, указатели, неизвестный импорт, некорректный бинарник; нормальный запрос после ошибок |
| `Pressure/memory` | Непрерывно используемый буфер 384 МиБ превышает лимит worker 256 МиБ; наблюдается OOM, supervisor сохраняется |
| `Pressure/hang`, `Pressure/cpu` | Worker, не реагирующий на отмену, завершается по внешнему deadline; CPU-счётчики подтверждают использование и throttling |
| `Pressure/child` | Worker с отдельным дочерним процессом завершается вместе с потомком, cgroup удаляется |
| `Pressure/output`, `Pressure/crash` | Неограниченный вывод и panic не раздувают буферы supervisor; следующая команда работает |
| `SharedQuota` | Два реально запущенных worker, резерв 512 МиБ, отказ третьему; отмена, освобождение резерва и закрытие admission |
| `KernelAggregateLimit` | Отдельная аварийная инъекция обходит admission: два worker по 200 МиБ каждый при индивидуальном лимите 256 МиБ и временном общем лимите 256 МиБ. OOM доказывает самостоятельную общую защиту ядра ОС |
| `IdentityAndEnvironment` | UID 65534 и ровно две разрешённые переменные окружения; тестовый секрет не наследуется |
| `RejectBeforeLaunch` | Неверные размеры, дубли ключей JSON и уже отменённый context отклоняются до запуска |

Инструмент `cmd/p1-pressure` намеренно вызывает отказы процесса и используется только стендом; эти режимы не доступны через пользовательский запрос настоящему worker. Они моделируют в том числе зависание или лишнее выделение памяти при компиляции, но не являются коллекцией реальных уязвимостей wazero. Задержки и память нормального синтетического echo не характеризуют будущие Чаты или Комнаты.

[Итоговый CI 40964744920](https://github.com/space-protocol-project/space-server/actions/runs/40964744920) завершён с `conclusion=success`; проверенная ревизия `8cc8c9439b8bdf127560ac5a51e02726f5be1c6a`. Успешны все пять задач: fixtures, три платформы и isolation. В задаче isolation — шесть верхнеуровневых тестов и шесть сценариев Pressure, без пропусков. Дата отчёта — 30 октября по Москве; время GitHub приведено в UTC и относится к 29 октября.

| Измерение итогового прогона | Наблюдение |
| --- | --- |
| Настоящий WASM, CompileAndRecover | cgroup peak 3 899 392 байта, OOM 0; это синтетический стенд, не профиль реального расширения |
| Превышение памяти worker | peak 268 451 840 байт; `oom_kill = 2`; сценарий отказа и проверки восстановления — 228 мс |

Счётчики `oom_kill` приведены как значения ядра, без трактовки их как числа пользовательских вызовов. Небольшое превышение peak над memory.max в первом сценарии сохранено в результатах, а не скрыто округлением.

[Исходные результаты и метаданные CI](p1-results/2026-10-30) включают журнал изоляции, JSONL трёх платформ и полный SHA; [SHA256SUMS](p1-results/2026-10-30/SHA256SUMS) фиксирует их байты. Первичный [прогон 40963659856](https://github.com/space-protocol-project/space-server/actions/runs/40963659856) также успешен; итоговый дополнительно проверяет два реально работающих процесса, закрытие admission, отказ до запуска и неинициализированный ProcessHost на трёх ОС. Лишние автоматические полные прогоны неизменённого рабочего сервера остановлены. Локальные сборки и тесты не запускались; последующий документационный коммит не меняет проверенный код.

## Что остаётся в P1

- Защищённый механизм запуска macOS, включая упаковку и подпись. Windows-профиль реализован позднее: [результаты и оставшиеся границы](SPACE-PLUGINS-P1-WINDOWS.md).
- Интеграция единого ProcessHost/launcher в жизненный цикл сервера, выделенный пользователь, автоматическое восстановление службой после смерти supervisor и системная политика файлов/сети. Восстановление cgroup при новом запуске реализовано отдельно.
- Решение о производительных квотах на реальных пакетах. Постоянный кеш выключен; его внедрение требует отдельной проверки размера и владения ресурсами.
- Полные схемы, SDK, API, доверие издателям и подписи пакетов из общего плана P1. Перенос четырёх рабочих функций в этот шаг не входит.
