# P1 / E01: публичный API реестра установок и журнала аудита

Статус на 1 ноября 2026 года: публичный API прототипа P1 проверен в GitHub CI. Продолжение [постоянного реестра](SPACE-PLUGINS-P1-REGISTRY.md), [аудита](SPACE-PLUGINS-P1-LIFECYCLE-AUDIT.md) и [межплатформенного восстановления](SPACE-PLUGINS-P1-REGISTRY-TRANSFER.md). Полный E01 остаётся открытым.

## Контракт и подключение

В экспериментальном `space.v1.ExtensionP1Service` добавлены четыре сетевых RPC. Контракт находится в `protocol/proto/space/v1/extensions_p1.proto`; Go/gRPC, Connect-Go, Dart/Connect и OpenAPI получены существующим генератором в GitHub CI. Стабильная capability v1 пока не объявляется.

| RPC | Назначение | Ограничения |
| --- | --- | --- |
| `ListExtensionInstallations` | Список установок текущей managed-оболочки | Порядок по ID; 50 элементов по умолчанию, максимум 100; продолжение связано с поколением |
| `GetExtensionInstallation` | Состояние, ревизия, поколение и SHA-256 привязки | Только известная управляемая установка; чужие/неизвестные ID не раскрываются |
| `ChangeExtensionInstallation` | `enable`, `disable`, `remove` | Обязательны текущее поколение и ожидаемая ревизия; системные действия запрещены |
| `ListExtensionInstallationAudit` | Аудит одной установки по возрастанию ревизии | Максимум 100 записей; обязательное поколение и закреплённая верхняя ревизия при продолжении |

`ExtensionP1ManagedService` реализует gRPC-контракт. `transport.NewExtensionP1Handler` предоставляет Connect-маршрут поверх доверенного gRPC-клиента; регистрация требует interceptor сессий ядра на стороне gRPC. В сетевом стенде регистрируются настоящие gRPC и HTTP Connect, а не вызываются только внутренние методы Go. Входное тело Connect ограничено 20 КиБ. Этот конструктор не включается автоматически в рабочий сервер: подключение установщика, загрузки пакетов и рабочего runtime относится к последующим этапам.

`disable` переводит установку в `disabling` и отменяет активные вызовы по существующим правилам координатора. Завершение `finish_disable` выполняет ядро; в стенде оно вызывается явно, рабочий фоновый исполнитель завершений ещё не подключён. `remove` переводит выключенную или карантинную установку в `removed`, сохраняя реестр, аудит и ранее записанные данные/квитанции; очистка пакета и его данных требует отдельной политики.

## Сессии и ACL

Каждый сетевой запрос требует действующий Bearer token. Истёкшая или отозванная сессия, смена `auth_epoch`, недействительный grant и push-only сессия не проходят interceptor. Чтение дополнительно повторно аутентифицирует входящий token; изменение использует существующий `Change`, повторно проверяющий token.

Все четыре операции требуют `space.manage` и текущего владельца пространства. Обычный участник и администратор без статуса владельца не получают управление или журнал. Проверяется `manage` для всех каналов установки через существующий ACL ядра. Права владельца и администратора на канал вычисляются штатным ядром; новый API не вводит собственных исключений и не принимает роль/автора от клиента. Отключение базового сервиса каналов запрещает доступ к связанным установкам согласно текущему прототипу.

Транзакция чтения использует тот же порядок блокировок полномочий, что и мутации: pairing, principal, grants, session, membership, settings, channels. Реестр читается с `FOR SHARE`; сессия проверяется по фактическому времени перед завершением транзакции. Отзыв полномочий, успевший зафиксироваться до этой границы, приводит к отказу без частичного ответа. Старое поколение managed-оболочки не может читать реестр, включая пустую страницу после последнего ID.

Изменение сохраняет уже проверенный барьер активных вызовов и COMMIT: состояние, ревизия и запись аудита фиксируются атомарно. Системные `quarantine` и `finish_disable` доступны только доверенному ядру. Клиент не может выдать себя за `system`, передать новый digest пакета или выполнить миграцию. Повтор изменения с прежней ревизией возвращает `Aborted`; при потере ответа клиент перечитывает состояние и аудит, а не повторяет переход с автоматически заменённой ревизией.

## Страницы и поколения

Список установок использует `after_installation_id` и текущее поколение. Начальная страница возвращает поколение, последующие обязаны его передавать. Список охватывает статические привязки managed-сервиса, включая удалённые установки; изменение состава пакетов этим API не реализуется. Страницы списка не объявляются единым снимком состояний: между запросами состояние может измениться, каждый ответ содержит актуальную ревизию.

Аудит возвращает исторические поколение, автора, principal, действие, прежнее и новое состояния, ревизию и время UTC RFC3339Nano. Начальные записи `checkpoint` не выдаются за реальные действия пользователя. В первой странице `through_revision=0` закрепляет текущую ревизию установки. Далее клиент передаёт возвращённую верхнюю границу и `next_after_revision`. Новые переходы остаются за пределами этого диапазона. Нулевая следующая ревизия означает конец. Смена поколения при перезапуске/восстановлении требует начать чтение заново; прежние записи аудита сохраняются.

Неверный размер страницы, некорректный ID/курсор и неизвестное действие возвращают `InvalidArgument`; старое поколение — `FailedPrecondition`; устаревшая ревизия изменения — `Aborted`. Ответы не содержат текста SQL или внутренних ошибок базы. Неуспешное чтение не возвращает накопленную часть страницы.

Целевой серверный набор выполняет пять race-повторений и запрещает пропуски. Проверяются четыре RPC для анонимного запроса, неверного token, участника, администратора, блокировки, ограниченного scope, истечения, отзыва, смены эпохи и push-only. Дополнительно проверяются переходы и авторство аудита, чтение закреплённого диапазона при новых переходах, страницы списка, отсечение старой оболочки, недопустимые действия/курсоры, Connect и ограничение тела. Для каждого RPC воспроизводится отзыв сессии/владельца/scope и отключение каналов на транзакционной границе.

Первый прогон [41329699311](https://github.com/space-protocol-project/space-server/actions/runs/41329699311) обнаружил неверный код ошибки чтения неизвестной установки: общий внутренний helper возвращал `Unauthenticated` вместо `PermissionDenied`. Коды отказа согласованы для чтения, изменения и аудита неизвестной установки без ослабления проверки доступа. Этот прогон сохранён как диагностический и не считается приёмкой.

## Что остаётся

Публичный API этого блока управляет статическими установками прототипа P1. Создание установок из подписанного пакета или Git, обновление/откат, миграции, рабочая регистрация сервиса и административный интерфейс приложения остаются отдельными задачами. Общая приёмка E01 и P1 не закрывается. Flutter-проверка подтверждает совместимость сгенерированного клиента и существующего UI-прототипа, но не наличие готового экрана управления установками.
