# P1: единый снимок допуска, COMMIT и отправка Connect-ответа

6 ноября 2026 года. Продолжение [снимка ядра перед возвратом результата](SPACE-PLUGINS-P1-DELIVERY-CORE.md). Реализация включается явно через `ExtensionP1ManagedService.NewDeliveryHandler`; рабочий сервер автоматически её не подключает.

## Один снимок на трёх границах

Доверенный begin фиксирует Principal/AccessStamp, установку, постоянные generation/revision и вид доступа. Backend управляемой мутации теперь требует этот же снимок внутри транзакции, после текущей авторизации и до применения операций, квитанции и outbox. Отсутствующий снимок, другой instance, read вместо write, изменённые права или реестр отвергаются. Неуправляемый экспериментальный backend сохраняет прежний контракт.

Это закрывает промежуток между допуском оболочки и собственным допуском backend: если ACL отозван и восстановлен между ними, свежая авторизация backend больше не позволяет старому вызову выполнить COMMIT. Проверка перед возвратом результата сохраняется.

## Прямой HTTP-путь

Прежний `transport.NewExtensionP1Handler` — мост во внутренний gRPC. Возврат из его RPC не совпадает с отправкой HTTP-байтов, поэтому этот мост не получает новую гарантию автоматически. Новый обработчик вызывает управляемую службу напрямую, используя Connect unary с protobuf или JSON. gRPC, gRPC-Web и streaming отклоняются; сетевые проверки этого среза выполняются на HTTP/1.1 loopback, без заявления о приёмке TLS/HTTP/2 или обратных прокси.

Для QueryExtension, ExecuteExtensionCommand и GetExtensionMutationContext ответ сначала сериализуется в буфер до 128 KiB. Ни заголовки успешного ответа, ни тело не передаются наружу на этом этапе. Исходный снимок сохраняется во внутреннем контексте и не берётся из заголовков клиента. Перед отправкой новая транзакция повторно читает сессию/ACL и реестр, сравнивает исходный снимок и удерживает SQL-блокировки до Write и [ResponseController.Flush](https://pkg.go.dev/net/http#ResponseController.Flush). Устанавливается двухсекундный срок записи через [SetWriteDeadline](https://pkg.go.dev/net/http#ResponseController.SetWriteDeadline). Неподдерживаемый контроль записи приводит к отказу до успешного ответа.

Порядок определяется конфликтующими SQL-блокировками:

- Если отзыв зафиксирован первым, проверка снимка не проходит и подготовленный документ не передаётся writer.
- Если отправка получила блокировки первой, отзыв ждёт завершения записи/Flush и освобождения транзакции. Уже отправленные данные отозвать нельзя.

Это последовательность относительно фиксации отзыва, не обещание отменить уже начатую запись в момент нажатия кнопки. Flush подтверждает передачу данным HTTP-транспортом, а не обработку клиентом; один из тестов дополнительно читает настоящий ответ клиентом до разрешения ожидающему отзыву завершиться. Внешние middleware не должны буферизовать запись за пределами этого барьера. Лимит 128 KiB относится к одному ответу, не является новой глобальной квотой памяти.

После ошибки или короткой записи уже начавшийся ответ обрывается через ErrAbortHandler; к нему не дописывается JSON ошибки. Транзакция освобождается с отдельным ограниченным контекстом очистки. До начала записи ошибки возвращаются в формате Connect. Для успешно исполненной команды поздний отказ отправки сохраняет Unavailable/delivery_not_confirmed и неопределённый исход, как в предыдущем срезе. Ошибка переполнения буфера команды также не объявляет откат.

Остальные методы (Reconcile и управление реестром/аудитом) доступны через прямой обработчик с прежней собственной авторизацией. Транспортный барьер данного среза относится только к трём перечисленным методам. Проверка естественного истечения срока сессии производится при авторизации; это не гарантия отзыва уже отправленных байтов при смене времени во время записи.

## Сценарии CI

- Старый снимок допуска, отзыв и восстановление ACL, свежая авторизация backend: Runtime вызывается, но COMMIT отклоняется; данные, квитанция и outbox не появляются.
- Connect-ответ уже подготовлен; до записи завершается отзыв ACL, logout или изменение ревизии установки. Клиент получает ошибку без документа. Для скрытого ACL ожидается NotFound, для logout — Unauthenticated, для ревизии — FailedPrecondition.
- Ответ реально записан и прочитан Connect-клиентом, но транзакция отправки ещё удерживается тестовым барьером. Изменение ACL наблюдается в pg_stat_activity как ожидающее SQL-блокировку; после снятия барьера отзыв завершается.
- Мутация зафиксирована, HTTP-ответ подготовлен, затем ревизия установки изменена до отправки. Ответ скрывается с Unavailable, Reconcile через тот же HTTP-обработчик подтверждает квитанцию; Runtime вызван один раз, данные/квитанция/outbox остаются в одном экземпляре.

Новые инъекции используют настоящую PostgreSQL и HTTP-соединение с управляемым тестовым Runtime; настоящий изолированный WASM проверяется регрессионными сценариями workflow. Помощник сверки квитанций перенесён из Linux-only теста в переносимый файл: локальная компиляция Windows выявила прежнюю зависимость общих тестов от Linux-файла. Локальные проверки без тестовой БД подтверждают компиляцию/анализ, а не приёмку гонок.

Первый [прогон 42204320791](https://github.com/space-protocol-project/space-server/actions/runs/42204320791) остановился на неверном ожидании кода скрытого ACL: ядро корректно возвращает NotFound. Ожидание уточнено без изменения политики доступа. Итоговая приёмка приведена ниже.

P1 остаётся открытым. Обычный gRPC-мост, TLS/HTTP/2, интеграция в рабочий сервер и клиент, а также перенос этого барьера на нативный LPAC-транспорт не считаются закрытыми данным срезом.
