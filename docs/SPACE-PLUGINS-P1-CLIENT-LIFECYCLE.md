# P1: полный жизненный цикл локального экземпляра

Кандидат контракта от 3 ноября 2026 года. Продолжает [локальные установки и разрешения](SPACE-PLUGINS-P1-CLIENT-LOCAL.md) и [события каталогов](SPACE-PLUGINS-P1-CATALOG-EVENTS.md). Добавлены [запись жизненного цикла](extensions/p1/client-lifecycle.schema.json), [команда](extensions/p1/client-lifecycle-command.schema.json), примеры JSON и чистая модель `tools/client_lifecycle_model.py`. Рабочего установщика, транзакционной локальной БД и WASM-мигратора этот срез не реализует.

## Область и совместимость

Единица управления — экземпляр установки на конкретном устройстве и в конкретном локальном профиле. Команда содержит полную привязку, поколение и ожидаемую ревизию. Ядро выводит полномочия из действующей локальной сессии; поля `authorized`, `active_calls`, результаты проверки пакета/копии и подтверждения пользователя не принимаются от гостя. Они существуют только как доверенные входы проверочной модели.

Новая запись `space.client.lifecycle.p1` описывает управляющий журнал; прежний `space.client.installation.p1` остаётся ограниченным представлением для доступа к каталогам. Только стабильные состояния disabled/enabled/removed преобразуются в это представление; все промежуточные состояния запрещают новые гостевые вызовы. Не следует передавать новый журнал прежнему валидатору установки. Координация нескольких локальных экземпляров одной транзакцией требует отдельного группового контракта.

## Переходы

| Команда | Исходное состояние | Результат |
| --- | --- | --- |
| install | absent | disabled после проверки пакета |
| enable | disabled | enabled после проверки пакета и актуального согласия |
| disable | enabled | draining: закрыть вход и отменить активные вызовы |
| drained | draining | disabled только при нуле активных вызовов |
| prepare | disabled | updating либо ready для обновления только кода |
| advance | updating | Зафиксировать следующий результат миграции и курсор; после последнего шага ready |
| publish | ready | Атомарно заменить пакет/данные/схему, записать историю, перейти в disabled |
| abort | updating/ready | Удалить промежуточную подготовку, оставить рабочую версию, disabled |
| quarantine | Любое рабочее/промежуточное состояние | quarantined, отменить вызовы и закрыть доступ |
| recover | quarantined | После проверки пакета и копии отбросить подготовку, disabled |
| remove | disabled | removed, данные сохраняются |
| purge | removed | Удалить данные экземпляра только после отдельного подтверждения |
| reopen | Любое состояние после install | Новое поколение; enabled/draining становятся disabled; курсор миграции сохраняется |
| restore | Любое состояние после install | Проверенная восстановленная запись, новое поколение; активное состояние не возобновляется автоматически |

Запись absent — зарезервированный кандидат установщика, а не работающий экземпляр. Поля пакета и данных здесь описывают проверяемый кандидат. Install не включает расширение автоматически. Removed — необратимая запись удаления; повторная установка использует новый идентификатор, не оживляет прежние разрешения. Purge не удаляет игры или другие пользовательские файлы устройства. Его логический результат моделируется флагом `data_present=false`; физическая очистка, криптографическое уничтожение и правила сохранения истории требуют реализации отдельно.

Каждый успешный переход увеличивает ревизию и эпоху разрешений, выдаёт новое случайное поколение. Это намеренно строгий вариант P1: старые grants, курсоры, дескрипторы и ответы после перехода недействительны. При enable новое согласие и grants нового поколения должны фиксироваться согласованно; сама смена состояния не выдаёт файловые права. После промежуточных шагов миграции рабочий доступ не нужен. Сохранение согласия между безопасными переходами в этом кандидате не оптимизировано.

Все действия, кроме disable/quarantine, требуют завершения активных вызовов. Команды drained/reopen/restore/advance/publish — операции доверенного ядра; разрешение пользователя в модели означает уже проверенную служебную или пользовательскую авторизацию, а не возможность гостя вызвать системный переход. Переполнение ревизий даёт отказ. Неверная привязка — StaleBinding; устаревшая ревизия — Conflict; недопустимый переход — FailedPrecondition; активные вызовы — Busy. Ошибка не меняет запись.

## Обновление

План содержит уникальный `plan_id`, digest исходного и целевого пакетов, исходную/целевую схемы, ревизию данных, digest checkpoint и число шагов 0–32. Исходная версия, схема и ревизия должны точно совпасть с рабочими. Одинаковые digest пакетов запрещены. Шаг повышает схему на единицу; ноль шагов допускает только обновление кода без изменения схемы. Целевой пакет и checkpoint проверяет доверенное ядро до подготовки и повторно перед публикацией. Идентификатор уже опубликованного плана нельзя использовать снова.

Рабочие `package_digest`, `schema`, `data_digest` и `data_revision` не меняются при prepare/advance. Результаты миграции сохраняются как staged_digest с курсором; фактические неизменяемые blobs должны принадлежать хранилищу ядра. Гость не может подставить digest результата в управляющую команду: в модели это доверенный результат исполнителя. Точный список модулей/их digest и проверка исполнения остаются в будущей интеграции с WASM-мигратором, не подтверждаются одним счётчиком шагов.

Публикация одним COMMIT меняет пакет, схему, данные, поколение, эпоху разрешений, историю и состояние. В модели история — список опубликованных plan_id с пределом 128; это защита от повтора и ограничение размера, не полноценный архив артефактов. При заполнении подготовка запрещена. Правила очистки истории и ограничения дискового хранилища предстоит принять отдельно. Новые разрешения не наследуются от старого пакета и требуют согласия перед publish и enable.

Abort безопасен только до публикации: рабочие данные ещё не затронуты. После публикации откат означает отдельное обновление либо явное восстановление проверенной копии; нельзя просто переключить старый пакет поверх новых данных. Quarantine сохраняет журнал для разбора. Recover в этом кандидате отменяет незавершённую подготовку, не запускает её автоматически.

## Сбои, повтор и восстановление

Каждая команда фиксирует один атомарный переход. При сбое до COMMIT сохраняется прежняя запись, после COMMIT — следующая целиком. Потерянное подтверждение означает UnknownOutcome. Повтор той же команды со старым поколением/ревизией не исполняется: вызывающий читает текущую запись, при необходимости открывает новую оболочку и формирует новую команду. История показывает, был ли опубликован план.

Перезапуск меняет поколение и эпоху разрешений, но сохраняет рабочую пару пакет/данные, опубликованную историю и курсор подготовки. Миграция продолжается с последнего зафиксированного шага. Незавершённый шаг может быть вычислен повторно только как чистое преобразование без внешних эффектов. Гостевые вызовы до enable запрещены.

Restore применяется **к проверенной записи выбранной копии** в изолированном хранилище. До публикации хост проверяет целостность blobs, пакетов, схем, истории, курсора и принадлежность локальному владельцу. Модель принимает результат этих проверок как `checkpoint_valid`; она не читает архив и не доказывает согласованность внешних blobs. Неполная/чужая копия не публикуется. Новое поколение генерируется на восстанавливающем устройстве и не берётся из копии. Локальные дескрипторы и разрешения доступа к каталогам не восстанавливаются из резервной копии. При смене устройства/профиля требуется отдельная явная привязка владельца, не простое редактирование идентификатора гостем.

Уже завершённые до сбоя файловые чтения не отменяются задним числом. Новый контекст не принимает старые события и не запускает автоматически отменённые операции. Восстановление старой копии не позволяет повторить старую управляющую команду благодаря новому поколению; это не доказательство долговечной дедупликации произвольных внешних эффектов.

## Проверки и границы

`tools/check_client_lifecycle.py` проверяет схемы, полный путь install→enable→disable→update→publish→remove→purge, чужие привязки, отказы полномочий, повтор команды, неверные планы, ожидание активных вызовов, abort/quarantine/recover, обновление только кода и restore. Для каждой команды основного пути моделируются обе стороны COMMIT и повторное открытие сохранённой записи.

Это детерминированный выбор старого/нового снимка в памяти, не аварийное завершение приложения, потеря питания, отказ диска или проверка SQL-транзакции. Нативные сбои, миграции WASM, реальное хранение и платформенная изоляция ещё предстоят. Полный E01/P1 остаётся открытым.
