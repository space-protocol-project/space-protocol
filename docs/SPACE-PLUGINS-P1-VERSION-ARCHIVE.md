# P1 / E01: архивное восстановление истории пакетов и схем

Статус на 2 ноября 2026 года: архивный подэтап принят в GitHub CI на Linux, Windows и macOS. Продолжение [последовательных обновлений](SPACE-PLUGINS-P1-VERSION-HISTORY.md) и [межплатформенного переноса реестра](SPACE-PLUGINS-P1-REGISTRY-TRANSFER.md). E01 целиком остаётся открытым.

## Стенд и состояния

Workflow `plugin-p1-version-transfer.yml` собирает домашний runtime PostgreSQL 17.11 на Ubuntu 22.04, Windows 2025 и macOS 15. Исходные состояния истории создаются на Linux: начальная команда через тестовый адаптер записывает данные, квитанцию и три события; затем настоящий изолированный ProcessHost исполняет WASM-миграции. Исходный пакет до первой публикации использует прежнюю тестовую регистрацию; все публикуемые целевые пакеты и модули миграций — настоящие WASM-байты.

| Вариант | Опубликованная история | Текущий план |
| --- | --- | --- |
| `published` | 1 → 2 → 3, две записи | Второе обновление опубликовано |
| `pending` | 1 → 2, одна запись | Переход 2 → 3 подготовлен, шаг ещё не исполнен |
| `ready` | 1 → 2, одна запись | Шаг 2 → 3 исполнен, результат сохранён, рабочим остаётся пакет схемы 2 |

Linux формирует исходные ZIP штатным `ExportPortable`. Каждая из трёх ОС импортирует их в новую базу, сверяет состояние и самостоятельно выполняет `ExportPortable` / `pg_dump` своим runtime. Таким образом в матрице переноса участвуют ZIP, действительно созданные на каждой исходной ОС, включая Windows-дампы. Общий источник данных Linux не выдаётся за исполнение WASM на Windows или macOS.

На каждой ОС все три состояния дополнительно проходят локальный цикл физической копии `CreateBackup` / `RestoreBackup` и ZIP `ExportPortable` / `ImportPortable`. Физические файлы PostgreSQL между разными ОС не переносятся.

Задания импорта проверяют все шесть направлений Linux ↔ Windows ↔ macOS. Каждый из трёх вариантов повторяется три раза с `-race`: 6 × 3 × 3 = 54 конечных сценария переноса. Принимающий runtime всегда собран для своей ОС. SHA-256 ZIP сверяется до и после импорта; служебные метаданные связывают архив с исходной ОС и точным коммитом сервера.

## Проверяемая сохранность

Снимок сравнивает полные строки истории, включая бинарное содержимое записи, digest, автора, поколение, номер и версии схем. Сохраняются рабочий план, курсор шагов, исходный и итоговый документы, целевая регистрация, модули, рабочие данные, ревизии, квитанции, outbox и аудит жизненного цикла. Сравнение выполняется до и после открытия управляемой службы. У реестра исключается только текущее поколение, которое обязано измениться; исторические поколения в аудите и записи версии сравниваются точно.

Идентичность пространства и доступ устройства сохраняются. ZIP не переносит исходную сессию; физическая копия сохраняет действующие сессии по существующему контракту полного восстановления. Тест проверяет оба поведения отдельно и в обоих случаях дополнительно выполняет повторный вход устройства через ядро. Старое управляющее поколение и команда со старой историей отклоняются. Квитанция прежнего пакета сохраняется побайтно, но API сверки возвращает `AlreadyExists`: digest команды включает пакет, поэтому новый пакет не выдаёт старую квитанцию за свой результат. Импорт и открытие службы не исполняют гостевой код.

Подтверждённый курсор доставки сохраняется. Старые токены подтверждения и аренды отклоняются, неподтверждённое событие выдаётся с новой арендой и увеличенной попыткой, после него доступно следующее событие.

Для ZIP из Windows и macOS на Linux отдельно проверяется продолжение после восстановления: готовый план публикуется, подготовленный план исполняется настоящим ProcessHost и публикуется, уже опубликованный план допускает повтор без новой записи истории. Первая версия, квитанции и outbox сохраняются. Все шесть сочетаний источника/состояния повторяются три раза, итого 18 конечных проверок. Это явный вызов доверенного ядра со свежими тестовыми свидетельствами; автоматический запуск миграции при импорте не добавлен.

## Повреждённые архивы

Для физических копий и ZIP на каждой ОС создаются три дефекта: неверный digest первой записи истории, удаление первой записи и потеря модуля текущего плана. После изменения пересчитываются внешние контрольные суммы. Отказ поэтому проверяет внутреннюю согласованность, а не только повреждение контейнера.

Восстановление обязано завершиться ошибкой до публикации каталога назначения и удалить свои временные данные. Исходные корректный и повреждённый архивы остаются неизменными. Всего — 3 ОС × 2 формата × 3 дефекта = 18 конечных отказных сценариев.

## Уточнения тестового стенда

Предварительный запуск [41494267618](https://github.com/space-protocol-project/space-server/actions/runs/41494267618) успешно собрал три runtime, но выявил ошибку тестового исполнителя: повторное открытие управляющей службы на одном объекте Store (`lifecycle_already_owned`). Тест исправлен: после публикации используется новое хранилище, как при перезапуске. Проверка владения ядра сохранена.

Следующая архивная проверка выявила неверное ожидание старого теста: квитанция предыдущего пакета сохраняется, но API нового пакета правильно отклоняет её по digest. Тест проверяет сохранность записи и этот отказ; рабочий контракт ядра не изменялся.

Прогон [41500025511](https://github.com/space-protocol-project/space-server/actions/runs/41500025511) также выявил различие физических и ZIP-копий: физическое восстановление сохраняет действующие сессии, ZIP их исключает. Ожидания разделены по формату; правила сессий не менялись.

В прогоне [41503541188](https://github.com/space-protocol-project/space-server/actions/runs/41503541188) Windows выполнил все архивные тесты, но служебный скрипт не смог вывести русскую строку в CP1252. Для его вывода явно задан UTF-8.

В текущем архивном запуске экспортное задание macOS было отменено GitHub без назначенного runner и без выполнения шагов. Повтор незавершённых заданий сохранил успешные результаты остальных ОС. Позднее импорт macOS также переназначен из очереди; исходный коммит и готовые артефакты при этих повторах не менялись.

Временные ZIP и случайные ключи/токены создаются только для CI, передаются между заданиями с ранее согласованным сроком хранения один день. Постоянный отчёт содержит только журналы проверок, сведения о запусках и контрольные суммы результатов, без файлов тестовых ключей и архивов пространства. Runtime также хранится один день и передаётся только между заданиями одной ОС.

## Границы

Проверяется прототип одной установки/instance и документа до 16 КиБ. Этот блок не подтверждает многокомпонентные обновления, downgrade, автоматическую очистку истории, установку из Git или доверие к издателям. WASM-возобновление после переноса подтверждается только на Linux; на Windows/macOS проверяются архивы, база, метаданные API и отсутствие гостевых вызовов при импорте. Аварийное завершение PostgreSQL и обрыв процесса посреди самого импорта здесь не моделируются; отказ до публикации проверяется на некорректных данных.

Рабочие Чаты, Комнаты, Обсуждения и Лента не переключаются на расширения. Этот подэтап не является готовностью E01/P1 или выпуском 0.9.0.
