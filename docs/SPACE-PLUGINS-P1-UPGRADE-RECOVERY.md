# P1 / E01: постоянный план и восстановление подготовки миграции

Статус на 2 ноября 2026 года: подэтап принят в GitHub CI на Ubuntu 24.04 с PostgreSQL 17.11. Продолжение [плана обновления](SPACE-PLUGINS-P1-UPGRADE-PLAN.md). Проверены сохранение и возобновление подготовки результата; публикация нового пакета и перенос рабочих данных пока не подключены. E01 в целом остаётся открытым.

## Постоянные данные

Явно включаемая `ExtensionP1ManagedService` создаёт дополнительное хранилище `upgrade_version=1` в экспериментальной PostgreSQL. Версии рабочего runtime и основной схемы БД не меняются. Старые хранилища без этого дополнения читаются проверкой резервных копий; отсутствующая часть нового формата запрещает открытие и восстановление.

`extension_p1_upgrade_jobs` хранит одну незавершённую публикацию на установку: полный неизменяемый план, digest, instance, исходный документ из проверенной копии, текущий документ, номер следующего шага и автора подготовки. `extension_p1_upgrade_steps` хранит по одной записи на завершённый шаг: порядковый номер, digest кода шага, SHA-256 входа, выходной документ, поколение исполнителя и автора операции. Первичные и внешние ключи запрещают повтор записи и потерю связи с установкой.

Все документы проходят общий строгий разбор JSON P1: до 16 КиБ, без повторяющихся ключей и дополнительного документа. План содержит до 32 шагов; журнал сохраняет промежуточные выходы, чтобы проверить последовательность и последний результат. При открытии и проверке копии сверяются digest плана, порядок шагов, хеши входов, итоговый документ и курсор. Повреждение не исправляется угадыванием и не приводит к запуску миграции с нуля.

## Доверенный интерфейс ядра

Методы находятся в Go-оболочке сервера; новых RPC нет.

| Метод | Назначение |
| --- | --- |
| `PrepareUpgrade` | Проверить реальную исходную привязку и свидетельства, сохранить план и начальный документ |
| `ReadUpgrade` | Прочитать и проверить план, текущий результат и `NextStep` |
| `AdvanceUpgrade` | Проверить digest и ожидаемый курсор, вычислить и атомарно зафиксировать один шаг |
| `ResumeUpgrade` | Продолжить с сохранённого курсора до готового результата, заново запросив свидетельства перед каждым шагом |

Сессия, роль владельца, `space.manage` и права управления каналом проверяются ядром при каждой операции. Проверки полномочий, поколение и строка установки удерживаются до COMMIT. Истечение сессии повторно проверяется перед фиксацией. Конкурирующий вызов со старым курсором получает `Aborted`, а не повторно исполняет уже зафиксированный шаг.

`PrepareUpgrade` допускается только для `disabled` без активных вызовов. В текущем прототипе установка должна иметь ровно один instance. Идентичность пространства, пакет и ревизия данных читаются из БД. Поскольку у P1 пока нет рабочего каталога версий схем, исходную версию схемы и подлинность содержимого резервной копии подтверждает доверенное ядро. Свидетельства из прошлого блока не превращаются в клиентские сертификаты.

Пока существует запись подготовки, `enable` и `remove` запрещены, в том числе через публичный API реестра. Состояние lifecycle остаётся `disabled`, его ревизия не меняется: подготовка ещё не является публикацией обновления. Карантин разрешён как аварийная остановка, сохраняет журнал и запрещает продолжение. Отдельный журнал шагов не подменяет исторический аудит переходов lifecycle.

## Транзакция и восстановление

Шаг получает копию текущего документа и возвращает новый JSON. Это доверенный чистый Go-преобразователь: интерфейс не передаёт ему SQL-транзакцию или доступ гостя к сети. Результат шага, его запись в журнале и продвижение `NextStep` фиксируются одной транзакцией PostgreSQL. Рабочие данные, квитанции команд и outbox не изменяются.

После перезапуска создаётся новое поколение управляющей оболочки. Исходное поколение внутри неизменяемого плана сохраняется; новое поколение проверяется отдельно по текущему реестру. Старый процесс теряет право продолжать. `ResumeUpgrade` читает подтверждённый курсор и перед каждым следующим шагом вызывает доверенный адаптер повторной проверки пакета, разрешений и копии.

| Момент сбоя | Сохранённое состояние | Продолжение |
| --- | --- | --- |
| План ещё не зафиксирован | Плана нет | Повторная подготовка после чтения состояния |
| План сохранён, шаг не начат | `NextStep=0`, исходный документ | Первый шаг |
| Процесс завершён во время вычисления | Последний подтверждённый документ и прежний курсор | Повтор вычисления незавершённого шага |
| Ошибка JSON, SQL или истечение сессии | Откат всего шага | Исправление причины и повтор с того же курсора |
| COMMIT не дошёл до БД | Прежний курсор | Повтор шага после открытия новой оболочки |
| COMMIT выполнен, подтверждение потеряно | Новый курсор и запись шага | Следующий шаг; завершённый не повторяется |
| Все шаги зафиксированы | `Ready=true` | Ожидание отдельного этапа публикации; автоматического включения нет |

При ошибке COMMIT текущая оболочка закрывает допуск, поскольку не может достоверно решить, выполнилась ли транзакция. Она не пытается компенсировать результат или повторять шаг вслепую. После открытия новой оболочки источником истины служит журнал PostgreSQL.

Гарантия относится к атомарной фиксации результата, а не к однократному вычислению: незавершённый чистый шаг может вычисляться снова. Внешние эффекты внутри преобразователя недопустимы. Тайм-аут операции — пять секунд, адаптер обязан соблюдать контекст; это не изоляция произвольного Go-кода. Настоящий WASM-исполнитель с квотами остаётся следующим подключением.

## Оставшиеся границы

Этот блок не публикует результат, не меняет рабочий пакет и не запускает произвольные SQL-миграции. Нет фонового автоматического возобновления без доверенного адаптера и актуальной сессии владельца. Требуются интеграция WASM-преобразования, каталог версий схем, многокомпонентные установки, согласованная подготовка полного набора данных из копии, атомарное переключение пакета/данных и аудит публикации. Также остаются отмена подготовки и правила очистки промежуточных результатов; этот прототип их не удаляет.

Проверка согласованности резервной копии учитывает новый журнал. Отдельная межплатформенная ZIP-приёмка именно нового формата и аварийный перезапуск самого PostgreSQL этим прогоном не подтверждаются. E01 и P1 в целом остаются открытыми.
