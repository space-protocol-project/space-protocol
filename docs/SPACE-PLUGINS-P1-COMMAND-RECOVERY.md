# P1 / E02: авария клиента и восстановление сессии на Linux

Статус на 1 ноября 2026 года: нативная приёмка Linux завершена успешно в GitHub CI. Продолжение [клиентского исполнителя команд](SPACE-PLUGINS-P1-COMMANDS.md). Этот блок не закрывает весь [E02/P1](SPACE-PLUGINS-P1-EXIT.md).

## Изменения исполнителя

После асинхронного чтения журнала `ExtensionCommandCubit` повторно проверяет отмену и привязку пользователя/назначения перед запросом контекста или сверкой. Смена пользователя и отмена во время чтения не должны приводить к сетевой отправке.

Отказ `Unauthenticated` при сверке теперь возвращает `reauthenticate` с сохранением неопределённости. После явного входа того же principal вызывается сверка исходного снимка; она не создаёт новую команду, ключ, историю или окно повторов. При отмене либо смене привязки остаётся `stop`.

## Нативный стенд

Собирается настоящий Flutter Linux debug-клиент с `PlatformKeyStorage`. Каждый запуск имеет отдельную D-Bus-сессию и новый GNOME Keyring/Secret Service; последовательные процессы используют один зашифрованный профиль внутри временного каталога GitHub runner. Файловая имитация `SecureKeyStorage` не используется.

Стенд независимо читает запись через `secret-tool`, сравнивает её с результатом `PlatformKeyStorage`, проверяет зашифрованный файл GNOME Keyring и SHA-256 снимка. В журнал доказательств не записываются содержимое секрета, токен сессии или профиль keyring. Контрольные файлы содержат PID, этап, результат и хеш; в снимке нет токена сессии. Payload команды — пустой JSON-объект с 12 000 пробелами между скобками, допустимый текущим контрактом demo, чтобы проверка не ограничивалась крошечной записью.

Контроллер проверяет принадлежность PID созданной группе и завершает её через SIGKILL вместе с Secret Service. Проверяется фактический сигнал завершения. Затем стартует новый Flutter-процесс и новый Secret Service, читающий прежний профиль с диска. Это холодное восстановление, а не повторное создание Cubit в одном процессе.

| Точка SIGKILL | Ожидаемый результат после запуска |
| --- | --- |
| До вызова записи журнала | Снимка нет, Execute не вызывался, данные/квитанции/outbox пусты |
| После завершённой записи, до Execute | Снимок читается без изменения; сверка возвращает UNKNOWN, эффект не исполняется |
| После настоящего commit, до ответа клиенту | Снимок читается без изменения; сверка подтверждает сохранённую квитанцию; эффект выполнен один раз |

Серверный путь использует тестовый Connect-мост, настоящий gRPC, сессии/ACL и PostgreSQL. После commit мост удерживает ответ до прекращения запроса. Прикладной WASM-обработчик заменён счётчиком и детерминированным планом изменений; изоляция WASM не является предметом этого нативного прогона. Рабочий публичный Connect-транспорт этим мостом не вводится.

## Вход и текущие права

Для двух сценариев с сохранённым снимком выполняются четыре холодных запуска:

1. Прежняя сессия отзывается через настоящий `Logout`; её токен приводит к `reauthenticate`. Это проверка отозванной сессии, не ожидание её естественного срока истечения.
2. Сервер выдаёт новую сессию тому же principal через challenge/signature `auth.login`. При подменённой клиентской привязке пользователя Cubit останавливается без RPC.
3. Отзыв права записи через `UpdateChannelAccess` запрещает сверку квитанции, не удаляя снимок.
4. После восстановления прав новый токен позволяет сверить исходный запрос. Для копии до Execute остаётся UNKNOWN, для сохранённого commit получается CONFIRMED.

Хеш снимка должен совпадать с хешем до SIGKILL и во всех повторных запусках. Серверные счётчики проверяют отсутствие нового запроса контекста и повторного Execute при восстановлении. Вход организует контроллер стенда; пользовательский экран входа и действия человека не проверяются.

## Оставшиеся границы

- Windows, macOS, Android и iOS для нового журнала этим запуском не принимаются. Прежняя приёмка других системных хранилищ не переносится автоматически на команды расширений.
- Прерывание внутри незавершённого системного вызова записи, потеря питания и отказ диска не проверены. Здесь проверяются границы до записи и после подтверждённой записи.
- Повторный вход и отказ прав проверяются протокольно; нативный пользовательский интерфейс восстановления ещё не подключён.
- Сохраняются требования единственного владельца журнала, рабочей интеграции P2/P3 и остальные критерии E01–E07. Совместная авария клиента и PostgreSQL с неопределённым COMMIT проверена отдельным дополнением ниже.
