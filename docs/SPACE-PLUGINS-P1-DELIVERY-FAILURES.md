# P1: отмена потока и освобождение блокировок доставки

6 ноября 2026 года. Продолжение [TLS/HTTP2-матрицы](SPACE-PLUGINS-P1-DELIVERY-TLS.md) для прямого `ExtensionP1ManagedService.NewDeliveryHandler`.

## Проверяемый порядок

Стенд использует настоящие PostgreSQL, TLS-соединение и Connect-клиент. Тестовый Runtime возвращает документ; обработчик захватывает SQL-блокировки снимка допуска перед записью. Обёртка writer отправляет один байт тела и делает настоящий Flush, затем удерживает продолжение записи. Клиент подтверждает чтение байтов. Неполный документ не может считаться успешным ответом.

После этого запускается отзыв ACL. Тест требует наблюдать ожидание блокировки в pg_stat_activity, затем вызывает сетевой сбой. Проверяются ошибка клиента без результата, завершение обработчика и успешное завершение ожидавшего отзыва. Следующий запрос отвергается с NotFound; после новой выдачи доступа тот же сервер возвращает полный корректный документ. Проверки ограничены по времени, поэтому зависшая транзакция не может считаться успехом.

## Сценарии

| Сценарий | Инъекция | Проверяемая граница |
| --- | --- | --- |
| TLS HTTP/2, отмена потока | Отмена контекста настоящего клиентского RPC после чтения префикса | Отмена достигает контекста серверного запроса; прерванная запись освобождает SQL-блокировки |
| TLS HTTP/1.1, разрыв соединения | Закрытие активного TCP/TLS-соединения тестовым сервером | Клиент не принимает неполный ответ; отмена серверного контекста завершает удерживаемую запись |
| TLS HTTP/2, разрыв соединения | Закрытие активного TCP/TLS-соединения тестовым сервером | Ошибка соединения освобождает блокировки, следующие запросы обслуживаются |
| TLS HTTP/2, короткая запись | Writer возвращает число записанных байтов меньше длины тела без ошибки | Защита от short write обрывает поток; обработчик не дописывает успешный ответ |
| TLS HTTP/2, ошибка записи | Writer возвращает io.ErrClosedPipe после отправки префикса | Аварийный путь после заголовков освобождает транзакцию и обрывает ответ |

Для отмены и разрыва обёртка ожидает реальную отмену контекста HTTP-запроса и возвращает её ошибку. Это детерминированная проверка очистки транзакции на границе записи, не измерение поведения забитого TCP-буфера. Short write и ErrClosedPipe вводятся явно; они не выдаются за непредсказуемые ошибки ОС. Все ответы идут через настоящее сетевое соединение, а отзыв — через API ядра.

## Приёмка

Workflow требует все пять подслучаев по пять раз под race detector, отсутствие skip/fail в Delivery-выборке и повтор всех подслучаев на изолированном этапе. Прежняя транспортная матрица, COMMIT, квитанции, WASM и аварии PostgreSQL сохраняются.

[Полный GitHub CI 42211232840](https://github.com/space-protocol-project/space-server/actions/runs/42211232840) успешен для `e2535610b2844d1627f98e43fe264ffdb6c1d5cc`: **2/2 задания**, core и database-faults. Все пять новых сценариев прошли по пять раз под race detector и по одному разу в изолированной выборке. Delivery — 181 запись pass без skip/fail; изолированный этап — 272 pass без skip/fail. Общие test/race — по 814 pass и 83 ожидаемых skip специальных стендов; worker-crash — 21 pass, аварии PostgreSQL — 26 pass. Числа включают родительские тесты и итоги пакетов, а не только независимые сценарии.

Прошли vet, mod verify и govulncheck. Полный workflow успешен с первой попытки. Утечек SQL-блокировок и принятия неполного ответа в этой матрице не обнаружено; исправление рабочей логики не потребовалось. Локальные Windows test/vet подтвердили компиляцию и анализ, но без тестовой БД не являются приёмкой сетевых сценариев. Group/Publish/Versions сохраняют отдельные стенды и не переаттестуются этим отчётом.

[Исходные журналы и метаданные](p1-results/2026-11-06-delivery-failures/) сохранены без изменения байтов; [SHA256SUMS](p1-results/2026-11-06-delivery-failures/SHA256SUMS) фиксирует их целостность.

## Границы результата

Уже отправленный префикс не отзывается; клиент не получает успешный документ. Этот срез не проверяет медленного получателя с заполненным TCP-буфером, HTTP/2 flow-control exhaustion, независимость параллельных потоков одного соединения или поведение внешнего middleware. Проверка после сбоя подтверждает работоспособность того же сервера, но не требует повторного использования того же TCP-соединения.

Прямой обработчик остаётся экспериментальным. Рабочее подключение, прежний gRPC-мост и нативный LPAC-транспорт открыты; P1/E03 целиком не закрыты.
