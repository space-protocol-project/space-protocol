# P1. Вход в Windows из установщика и системных уведомлений

Продолжение [проверки первого запуска Windows](SPACE-PLUGINS-P1-WINDOWS-STARTUP.md). Срез проверяет установленное приложение, возврат фокуса и явную разблокировку локального профиля через рабочий диалог и `LocalSessionCubit`.

## Изменение обработки активации

Раньше `NotificationActivation::Forward` восстанавливал окно только при повторном запуске без токена. Для уведомления он лишь передавал токен через `WM_COPYDATA`. Дальнейшая активация зависела от успешного открытия цели в Dart. Удалённая или недоступная цель могла оставить приложение свёрнутым.

Теперь после принятой передачи токена нативный runner возвращает окно. Повторный запуск без токена использует тот же обработчик. `SW_RESTORE` применяется только к свёрнутому окну, поэтому повторный запуск не снимает максимизацию. Перед пересылкой второй процесс вызывает `AllowSetForegroundWindow` для PID первого процесса, найденного по совпадению полного пути исполняемого файла. Общий доступ `ASFW_ANY` не используется. [Правила передачи права фокуса Windows](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-allowsetforegroundwindow).

Возврат окна не выдаёт локальную сессию. Потеря фокуса блокирует профиль, а новая разблокировка требует успешной проверки пароля. Токен уведомления остаётся одноразовой ссылкой на сохранённую цель и не заменяет проверку прав на чат или возможностей расширения.

## Нативный стенд GitHub CI

Workflow `plugin-p1-windows-launch.yml` собирает release-вариант SpaceApp с отдельной точкой входа `windows_launch_probe.dart` и упаковывает его штатным `packaging/windows.iss`. Тестовая версия 0.9.0 существует только на runner и не публикуется как выпуск. Windows runner, регистрация URL-протокола, обработка уведомлений, хранилище DPAPI, управление окном и диалог пароля используются из рабочего приложения. В отличие от предыдущего стенда, выполняются также `DesktopWindowState.initialize` и `restore`.

Автоматизация проходит настоящий мастер Inno Setup и нажимает «Finish» с запуском программы. Для уведомлений используется `SystemNotifications.show`, нативный Windows Toast и нажатие карточки через UI Automation. Тестовая цель принадлежит несуществующему серверу, что дополнительно проверяет независимость активации окна от успешной навигации.

Сценарии проверяют запуск после установки, возврат к свёрнутому процессу, запуск нового процесса из оставшейся карточки, сохранение максимизации при повторном запуске и `/RELAUNCH` после повторной установки. Стенд сверяет PID, настоящее foreground-окно Windows, состояние Flutter и блокировку Cubit. После первого создания профиля повторные входы сначала отклоняют неверный пароль, затем принимают правильный. Flutter-поля заполняются программно. Системные карточки и мастер установки управляются через настоящие элементы интерфейса ОС.

Профиль, данные приложения и установка размещаются в отдельном каталоге runner. При существующей регистрации Space сценарий отказывается продолжать. По завершении останавливаются только процессы из каталога стенда и запускается штатное удаление установки. В артефакты не включаются пароль и записи защищённого хранилища.

Неуспешные прогоны не засчитываются как нативная приёмка.

## Границы

Проверка относится к Windows 2025 runner и установленной сборке с тестовой точкой входа. Она не проверяет подключение к реальному серверу или открытие конкретного сообщения после проверки серверного ACL. Подпись установщика, SmartScreen, перезагрузка ОС и другие пользовательские конфигурации Windows требуют отдельной проверки.
