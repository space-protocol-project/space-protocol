# P1: барьер доставки по TLS и HTTP/2

6 ноября 2026 года. Продолжение [единого снимка допуска, COMMIT и Connect-отправки](SPACE-PLUGINS-P1-DELIVERY-WIRE.md).

## Область проверки

Прямой `ExtensionP1ManagedService.NewDeliveryHandler` проверяется в трёх режимах: HTTP/1.1 без TLS, TLS HTTP/1.1 и TLS HTTP/2. Каждый запрос проверяет фактический `ProtoMajor` и наличие TLS на сервере. Поэтому откат HTTP/2 на HTTP/1.1 приводит к ошибке теста. Используется настоящий loopback TCP/TLS, PostgreSQL и Connect-клиент; Runtime новых гонок управляемый тестовый. Регрессионные проверки изолированного WASM остаются отдельной частью того же workflow.

Стенд создаётся через [httptest.Server](https://pkg.go.dev/net/http/httptest#Server), клиент доверяет тестовому сертификату сервера. Отключение проверки сертификата не используется. Это проверка штатного транспорта Go и барьера, а не развёртывания сертификатов, внешнего прокси или производственной конфигурации TLS.

## Матрица гонок

Для каждого транспорта выполняются:

- Подготовленный ответ Query, затем завершённый отзыв ACL, logout либо изменение ревизии установки. Успешный документ не возвращается; проверяются точные коды NotFound, Unauthenticated и FailedPrecondition.
- Запись ответа до отзыва ACL. Клиент получает байты тела; запрос изменения ACL наблюдается ожидающим SQL-блокировку. После завершения защищённой записи и Flush отзыв завершается, клиент проверяет полный документ.
- Команда уже прошла COMMIT, её ответ подготовлен, но перед записью изменена ревизия установки. Клиент получает Unavailable; Reconcile через тот же TLS/HTTP-обработчик подтверждает квитанцию. Runtime вызван один раз, данные, квитанция и outbox сохраняются без дубликатов.

HTTP/2 разделяет получение тела и завершение потока. Тест отправки наблюдает чтение байтов клиентом, затем освобождает намеренно удерживаемую транзакцию и проверяет полный результат RPC. Он не требует завершения RPC до END_STREAM. В HTTP/1.1 используется тот же порядок проверки. Наблюдатель не заменяет сеть и не подставляет ответ.

Матрица повторяется пять раз под race detector. Workflow требует наличия всех девяти транспортных подгрупп, а также отсутствия skip/fail в выбранных Delivery-тестах. Те же подгруппы обязательны в изолированном этапе. Старые сценарии снимка допуска и COMMIT сохраняются.

## Приёмка и ограничения

[Полный GitHub CI 42207970851](https://github.com/space-protocol-project/space-server/actions/runs/42207970851) успешен для `172559de5eeb2de5820f20792366592f442f6074`: **2/2 задания**, core и database-faults. Все девять транспортных подгрупп прошли по пять раз с race detector и по одному разу в изолированном этапе. Delivery: 151 запись pass без skip/fail; изолированный этап: 266 pass без skip/fail. Общие test/race дали по 808 pass и 83 ожидаемых skip для специальных стендов. Worker-crash: 21 pass, аварии PostgreSQL: 26 pass. Эти числа включают родительские тесты и итоги пакетов, а не только независимые сценарии.

Также прошли vet, mod verify и govulncheck. Прогон завершён целиком с первой попытки. Group/Publish/Versions сохраняют отдельные стенды и здесь не переаттестуются. Локальные Windows test/vet подтвердили компиляцию и анализ; без тестовой БД локальный запуск не является приёмкой сетевых гонок.

[Исходные журналы и метаданные](p1-results/2026-11-06-delivery-tls/) сохранены без изменения байтов; [SHA256SUMS](p1-results/2026-11-06-delivery-tls/SHA256SUMS) фиксирует их целостность. Изменения рабочей логики барьера не потребовались; изменены тесты и обязательные проверки workflow.

Гарантия остаётся прежней: фиксация отзыва упорядочена относительно защищённой записи/Flush. Уже отправленные байты не отзываются, Flush не означает обработку результата приложением. Медленные получатели, отмена HTTP/2-потока, отключение соединения во время записи и влияние внешнего middleware не считаются отдельно принятыми этой матрицей.

Автоматическое подключение к рабочему серверу, старый gRPC-мост, нативный LPAC-транспорт и клиентская интеграция остаются открытыми. P1/E03 целиком не закрыты.
