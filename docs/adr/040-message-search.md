# ADR-040: поиск в выбранном канале

Статус: реализован срез v0.5.

## Решение

Обычная история ищется через `ContentService.SearchContent`. Запрос содержит
`channel_id`, `query` и необязательный `before_sequence`; ответ — `contents`
и `next_before_sequence`. HTTP GET:
`/api/v1/channels/{channel_id}/content/search`.

Сеанс и права видимости/чтения проверяются для каждой страницы. Поиск в MLS
через этот RPC возвращает отказ. Удалённые записи исключаются, правки берутся
из актуального содержимого. Условия поиска параметризованы; шаблонных
операторов и SQL-синтаксиса в запросе нет.

Пределы: 2–128 Unicode-символов и 512 байт запроса, 50 записей на страницу,
три секунды на серверную операцию. Буквальный поиск подстроки не зависит от
локали PostgreSQL. Результат упорядочен по убыванию sequence; следующий курсор
равен последнему номеру страницы и задаёт строгую верхнюю границу. Клиент
проверяет канал, порядок, уникальность и корректность курсора.

В MLS запрос остаётся на устройстве. Источник — защищённый документ уже
присоединённой группы, включая импортированную доступную историю. Присоединение,
сетевое обновление группы, доверие ключам и перенос ratchet не выполняются.
При откате, несоответствии группы или ожидающем отзыве поиск останавливается.

Панель привязана к пространству, личности, сеансу и каналу. Устаревшие ответы
отбрасываются; отзыв прав или смена канала закрывают выдачу. Поисковая строка
и отдельный индекс на диске не сохраняются. Интерфейс ограничен 200 совпадениями.

## Границы

Это поиск исходного текста в одном канале, без морфологии, содержимого файлов
и отдельного индекса больших архивов. Новый RPC требует обновлённого runtime;
версия схемы остаётся 20, новых миграций не требуется. Самостоятельный офлайн-
каталог закрытых каналов без сеанса остаётся следующим этапом.
