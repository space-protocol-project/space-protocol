# ADR-026: первый успешный вход назначает владельца

Дата: 9 октября 2026 года. Статус: экспериментальная реализация.

На новом сервере с PostgreSQL код первоначальной настройки больше не обязателен.
Первый успешный auth.login после проверки подписи устройства назначает его principal
владельцем. Открытие /space, discovery или создание registration challenge владельца
не назначает. Регистрация ключа без входа также не назначает владельца.

Выбран owner вместо обычного admin: первый пользователь получает полный набор прав,
включая назначение администраторов. Значение owner_id фиксируется один раз. Остальные
входящие получают обычные права членства; даже space.manage само по себе не даёт роль.

## Реализация

Миграция 9 добавляет owner_claim_policy. Существующие базы сохраняют manual, а только
новая инициализация базы включает first_login. Ранее назначенный владелец не меняется.
Поэтому обновление не превращает старую базу без owner в открытый bootstrap.

Во время bootstrap registry lock берётся перед grant/membership/settings. Назначение,
создание сессии, потребление challenge и owner.first-login audit выполняются в одной
транзакции. Неверная подпись, блокировка, истёкший grant или неуспешная транзакция
не назначают владельца. Recovery grants не используются для этого; нужен рабочий ключ.
Конкурентные входы могут создать несколько сессий, но назначают ровно одного владельца.
Потеря ответа после commit не открывает выбор заново: principal уже закреплён в базе.

GetSetupStatus публикует initialized и first_login_owner. Новый Flutter-клиент при
открытом bootstrap запрашивает административный device grant с подписью собственного
root, чтобы первый владелец сразу мог настраивать сервер. Для сохранённого root-record
без административного scope создаётся новый подписанный grant; старый grant сервер
не расширяет. Ключи device-only не получают новые scopes без root/recovery полномочий.
Браузерная панель уже запрашивает административное разрешение при регистрации.

Пока автоматический bootstrap открыт, первоначальная регистрация возможна даже при
closed policy. После назначения владельца обычная политика регистрации применяется
снова. Саму политику first login не переключает; в новой базе она по умолчанию open.

## Управление режимом

```powershell
# Новая база: обычного запуска достаточно.
.\space-server-windows.exe

# Явно включить first login в старой ненастроенной базе, затем запустить сервер.
.\space-server-windows.exe -first-owner
.\space-server-windows.exe

# При необходимости сохранить ручной режим с кодом.
.\space-server-windows.exe -setup-code
.\space-server-windows.exe
```

first-owner и setup-code не совмещаются. После назначения владельца обе команды
отказываются открывать настройку повторно. Режим сохраняется при перезапуске.
Обе команды требуют SPACE_DATABASE_URL. Demo не реализует постоянное владение.

Как и запрошено пользователем, при first_login полномочия получает первый клиент,
способный выполнить регистрацию и подписанный вход через доступный ему API.
В текущем прототипе API доступен только через loopback/SSH-туннель. Режим не следует
незаметно переносить в старые установки или автоматически открывать после потери owner.

Проверки: metadata/registration без назначения, неверная подпись, блокировка,
восемь конкурентных входов с одним владельцем, scopes/roles остальных пользователей,
audit и restart. Ручные bootstrap-тесты выполняются в явном manual режиме.
