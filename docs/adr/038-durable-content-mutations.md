# ADR-038: постоянная очередь изменений обычных сообщений

Статус: реализовано локально 17 октября 2026, не выпущено. Требуется runtime со схемой PostgreSQL 19.

## Причина

Постоянная очередь создания сообщений уже сохраняет ключ запроса. Прежние RPC правок, удаления и реакций использовали только expected_revision. После потерянного подтверждения нельзя безопасно решить, был ли запрос применён или другая версия появилась независимо. Автоматическое повторение с новой версией может перезаписать действие второго устройства.

## Решение

1. Хранить изменения в том же защищённом слоте, с прежней областью origin/server/principal/grant и общими пределами 100 записей / 1 МиБ. Документ с mutation имеет версию 2; прежняя версия 1 остаётся только для создания сообщений. Это запрещает старому клиенту интерпретировать текст правки как новое сообщение после отката приложения.
2. Отправлять очередь через отдельный ApplyContentMutation с одним из трёх действий и обязательным ключом. Старый runtime отклоняет новый RPC до изменения данных; запрещён автоматический переход к прежним методам без квитанций.
3. В одной транзакции сохранять действие, событие и квитанцию: канал, principal, ключ, ID сообщения, SHA-256 канонических полей и применённая версия. Не хранить в квитанциях старые тексты. Повтор не создаёт событие; другой запрос с тем же ключом отвергается.
4. Квитанция возвращает applied_revision именно действия и текущее сообщение. Это не обязательно одна версия. Повтор после правки или удаления другим устройством возвращает актуальное состояние и не восстанавливает прежнее. No-op реакции тоже получают постоянную квитанцию.
5. Проверять действующий grant, ACL и обычный режим канала также при повторе. Идемпотентность привязана к principal, поэтому прежняя очередь может явно восстанавливаться на новом grant по ADR-037.
6. Зависимые операции ждут подтверждения предыдущей. Атомарное удаление записи из очереди задаёт ожидаемую версию следующей по applied_revision. Более новая версия тела ответа не становится неявным разрешением перезаписать чужую правку.
7. Конфликт версии останавливает операцию с сохранением локального запроса. Отмена родителя останавливает зависимые действия. Перед повторным действием пользователь проверяет актуальное состояние; автоматического разрешения конфликтов нет.
8. UI проецирует ожидаемые действия отдельно от подтверждённой истории и очищает редактор только после записи на диск. История сохраняется до очистки очереди; поздние ответы старой сессии/области не удаляют ожидающие записи.

## Проверки и границы

Модульные и интерфейсные тесты приложения, отдельные процессы Windows, Go/PostgreSQL и настоящие ConnectRPC-клиенты покрывают перезапуск, потерю ответа, no-op, конкурентные повторы, сохранность ввода и конфликт двух сопряжённых устройств. Документация: space-app/docs/OUTBOX-ACTIONS.md. MLS-правки и удаление не входят в этот срез; закрытые реакции используют прежний защищённый журнал. Физический Android отложен пользователем.
