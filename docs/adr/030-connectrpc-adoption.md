# ADR-030: Переход на ConnectRPC

Статус: архитектурное решение принято; реализация ещё не выполнена.
Дата: 11 октября 2026 года. Основание: пользователь выбрал ConnectRPC.

## Решение

Использовать Connect-Go на сервере и Connect-Dart во Flutter с существующими Protobuf-сервисами и Buf. Сохранить бизнес-логику, PostgreSQL, формат идентичности, подписи, grants, токены, ACL, идемпотентность и курсоры. Выбор библиотеки не означает, что транспорт уже заменён.

Connect-Go поддерживает Connect, gRPC и gRPC-Web; обработчики работают через net/http. Connect-Dart поддерживает эти три протокола и заменяемый HTTP-клиент. Эти возможности позволяют организовать постепенный переход с проверкой старого gRPC-клиента. Старые HTTP REST-маршруты grpc-gateway сохраняются до отдельного решения о совместимости; Connect JSON сам по себе не повторяет их URL.

## Порядок внедрения

1. Закрепить версии Connect-Go, генератора и Connect-Dart; проверить совместимость с используемыми Go/Dart и генерацией Protobuf. Не обновлять остальные зависимости без необходимости.
2. Прототип: GetManifest, вход по ключу и защищённая подписка событий из Dart. Проверить бинарный и JSON Connect, работу по HTTPS и отмену подписки.
3. Перенести аутентификацию в Connect-interceptors. Отдельно подтвердить deadlines, metadata, коды ошибок, ограничения размера, слоты потоков и отзыв grants/ACL для уже открытого потока. Простое подключение новых обработчиков не должно обходить текущие gRPC-interceptors.
4. Проверить самоподписанный сертификат домашнего сервера: доверенный отпечаток, срок действия, имя/IP и отказ при подмене. Не отключать проверку сертификата. Проверить отсутствие повторов авторизованных запросов на неподтверждённом адресе.
5. После сквозных проверок перевести приложение: история, отправка, события и WatchChannels, затем управление, recovery и pairing. Сохранить текущие коды пользовательских ошибок и изоляцию сессий/черновиков разных серверов.
6. CI на трёх ОС: старый gRPC-клиент против нового сервера, Dart/Go Connect, повтор запросов, разрыв и восстановление потока, HTTP JSON, ACL и миграции. Удаление прежнего транспорта — отдельный завершающий срез после приёмки.

Новый домашний runtime требует отдельного выпуска; закреплённый v0.1.0 не заменяется автоматически. Перенос бинарных вложений и медиапотоков не следует из выбора RPC: их ограничения и способ передачи проектируются отдельно.
