# ADR-039. Ответы на сообщения

Статус: рабочий срез v0.5, не включён в v0.4.1. Дата: 17 октября 2026 года.

## Решение

Обычное сообщение содержит необязательный `reply_to_id`: идентификатор уже
принятого сообщения того же канала. Сервер не принимает текст, имя автора или
файлы «цитаты» от отправителя ответа и не хранит дополнительную копию исходника.
Предпросмотр строится из доступной истории и обновляется при её изменении.
Удалённый или отсутствующий исходник показывается как недоступный.

`CreateContentRequest.reply_to_id` входит в отпечаток запроса. Повтор с прежним
ключом возвращает прежнее сообщение; замена цели с тем же ключом отклоняется.
Ссылка неизменна при редактировании ответа и передаётся в истории, событиях,
реакциях и квитанциях изменений. Удаление исходного сообщения сохраняет связь,
но не сохраняет его текст. Новая PostgreSQL-миграция 20 добавляет составной
внешний ключ внутри канала; существующие сообщения получают пустую ссылку.

Для создания ответа нужны права записи и чтения канала. Сначала проверяются
права, затем существование цели. Идентификатор из другого канала не разрешается
через глобальный поиск. Повтор ранее принятого ответа работает и после удаления
исходника. Ответ на уже удалённый исходник допустим и показывает его заглушку.

Сервер объявляет `ordinary_replies_supported` в manifest. Клиент обязан проверить
признак перед отправкой: прежний runtime может проигнорировать незнакомое поле
protobuf и создать обычное сообщение. Без подтверждённой поддержки отправка
ответа должна остановиться до RPC, сохранив очередь.

## Последовательность реализации

1. Контракт, миграция и сервер: сохранение ссылки, изоляция каналов, повтор,
   история, события, правки, удаление. Этот рабочий срез реализован локально.
2. Приложение: «Ответить» в меню удержания/правого клика, компактный блок над
   вводом, отмена без потери черновика, предпросмотр в сообщении и переход к цели.
   Выбор ответа хранится отдельно для каждого пространства и канала.
3. Постоянная очередь: сохранять цель до RPC и при переносе на новый grant,
   проверять цель в подтверждении; защита старого клиента от чтения нового
   формата. Первоначально отвечать только на принятые сообщения, без ссылок на
   временный локальный ID. Потерянный ответ и перезапуск не создают дубль.
4. MLS: цель и предпросмотр находятся внутри аутентифицированного шифротекста,
   сервер не получает открытых ссылок закрытого канала. Формат и приёмка
   согласуются отдельным срезом; открытый `reply_to_id` для MLS не используется.
5. Затем системные уведомления и серверный поиск с ACL. Поиск закрытых каналов
   выполняется только локально по доступной расшифрованной истории.

## Приёмка

- Серверные тесты на реальной PostgreSQL: сохранение ссылки, повтор, подмена
  цели с прежним ключом, история и события после удаления, отсутствие побочного
  сообщения при неверной цели или отказе ACL.
- Приложение: две сессии, потерянная квитанция, офлайн/перезапуск, восстановление
  очереди, удаление и правка исходника, поздний результат другого пространства.
- Интерфейс: русский/английский/китайский, узкий экран и увеличенный текст,
  клавиатура, контекстное меню, доступность для экранного диктора.
- MLS: подмена ссылки не принимается; сервер не видит цель или текст цитаты;
  доступность истории определяется членством и сохранёнными локальными данными.

Локально реализованы сервер, интерфейс обычного канала и постоянная очередь
ответов с файлами. Формат очереди 3 защищает от отправки без ссылки старым
приложением; `reply_to_id` проверяется в квитанции для любой ревизии сообщения.
Проверены потерянное подтверждение, два перезапуска, второе сопряжённое устройство
и удаление исходника после принятого ответа.

Локальный срез MLS использует `reply: {message_id: [u8; 16], grant_id: string}`
внутри application-сообщения. Предпросмотр разрешается только по доступной
истории текущего канала, без копии текста. Rust запрещает сочетание ссылки
с реакцией или передачей управления; шифртекст аутентифицирует её вместе
с содержимым. Ссылка сохраняется в защищённом outbox, при повторном шифровании
после смены эпохи и в архиве истории. Новый leaf без исходника видит заглушку.
MLS не использует открытое `reply_to_id` и не требует новой миграции сервера;
получателям нужен новый клиент, прежний отвергает неизвестные поля.

Для отображения авторов и реакций обычный `Content` содержит
`participant_names`: имена только видимых авторов и участников реакций, без
подмены идентификаторов и без раскрытия полного каталога пространства. Эти имена
обновляются при чтении; копия исходного сообщения для ответа не создаётся.
