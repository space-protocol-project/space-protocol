# ADR-046: лента публикаций и раздельные права

Дата: 24 октября 2026. Статус: первый срез реализован и проверен локально; готовится пара клиента v0.7.19 / runtime v0.7.15, миграция 31. Новая пара ещё не опубликована. Опубликованная исходная пара — клиент v0.7.18 / runtime v0.7.14, схема 30; она ещё не содержит ленту. [Результаты проверки и ограничения](../../../space-app/docs/FEED.md).

## Сценарий и границы

Администратор создаёт раздел ленты, разрешает выбранному участнику публикацию и отдельно задаёт комментирование. Участник публикует запись с файлом; другой участник читает и при наличии права комментирует. Модератор скрывает запись с причиной; клиенты заменяют её заглушкой, сервер прекращает выдавать связанные файлы.

Лента — отдельный Channel с единственным View.type=feed, без MLS и публичного превью. Существующий тип канала не меняется. Chat, forum и feed используют отдельные таблицы и RPC. Несколько collections внутри одного канала, personas, поиск, уведомления, редактирование, экспорт и MLS/E2EE остаются отдельными срезами. Тексты доступны серверу.

Контракт описан в `protocol/proto/space/v1/feed.proto`. Локальная реализация объявляет `core.feed.v1` и содержит файлы, политику, жалобы и модерацию. Наличие файла proto само по себе не означает доступность функции в опубликованном runtime. Старый runtime не получает запросы нового сервиса; клиент показывает отсутствие поддержки и сохраняет черновик.

## Права

Базовые ACL канала visible/read/manage и действующие проверки сессии, устройства, членства и блокировки сохраняются. Политика ленты не предоставляет доступ к скрытому разделу и не расширяет полномочия устройства.

Отдельная таблица `feed_access` содержит правила role=member/reader либо principal_id, ровно один субъект на строку, и два независимых флага publish/comment. Индивидуальное правило целиком заменяет правило роли; объединения флагов из нескольких правил нет. Отсутствующее правило означает запрет обоих действий. После создания раздела разрешены только действия владельца/администратора; публикация обычным участником требует явного правила.

| Действие | Обязательные условия |
| --- | --- |
| Читать список, запись и комментарии | visible/read и scope chat.read |
| Публиковать | read, scope chat.write, effective publish; роль reader публиковать не может |
| Комментировать | read, scope chat.write, effective comment; reader может комментировать только при явном разрешении политикой |
| Читать/менять политику | read/manage и scope space.manage |
| Скрывать/восстанавливать и рассматривать жалобы | read/manage и scope space.manage |
| Жаловаться | read и видимость объекта; publish/comment не нужны |

Владелец и администратор получают publish/comment по роли, но остаются ограничены scope устройства, блокировкой, read и архивом. Право manage само по себе не выдаёт publish/comment обычному участнику. Поле ChannelPermissions.write не служит разрешением на операции FeedService: клиент использует эффективные FeedPermissions из ответов ленты. Прежний глобальный запрет записи reader для чата и форума сохраняется; исключение комментирования применяется только внутри FeedService и только с явным правилом.

GetFeedAccess/UpdateFeedAccess возвращают правила только модератору; обычный читатель получает лишь собственные эффективные флаги. Изменение политики использует актуальную revision канала, увеличивает её и атомарно записывает аудит. Создание и изменение правил сериализованы с публикацией, комментированием, архивированием и отзывом ACL. Канал берётся под FOR UPDATE для мутаций, FOR SHARE для чтения; порядок блокировок сохраняется: grant → membership → settings → channel. Сначала проверяются полномочия, затем содержимое запроса.

## Порядок, страницы и повторы

Публикации имеют монотонный sequence внутри раздела. Список идёт от новых к старым по sequence DESC, независимо от совпавшего времени или новых комментариев. before_sequence=0 начинает с последних; следующая страница использует исключительную верхнюю границу next_before_sequence. После конца next=0. Новая запись между запросами не смещает уже начатую пагинацию; обновление списка начинается отдельно с 0.

Комментарии идут по sequence ASC внутри записи. after_sequence=0 начинает с первого комментария. Скрытые объекты сохраняют позиции и счётчики; модерация не сдвигает курсоры. Размер страницы 1..50, 0 означает 50; отрицательные значения недопустимы. Скрытая родительская запись возвращается заглушкой без комментариев и без курсора продолжения.

CreateFeedPost и CommentFeedPost требуют ключ 1..128 байт UTF-8. Уникальность — раздел, автор и ключ отдельно для публикаций и комментариев. Для комментария квитанция также связывает родительскую запись. Повтор с тем же ключом и другим текстом, родителем или упорядоченным списком файлов получает конфликт. Идентичный повтор возвращает прежний объект с учётом текущей видимости; повтор не обходит актуальные ACL, политику, scope или архив. Потерянный ответ не приводит к второй записи. Клиент сохраняет текст, файлы и ключ до успешного подтверждения, повторяет с тем же ключом и игнорирует ответы прежнего раздела/сеанса.

Каждая публикация и комментарий имеют собственную revision. Комментарий и его модерация также увеличивают revision родительской записи. Изменение модерации требует expected_revision; устаревшая версия получает Aborted. Счётчик комментариев включает скрытые комментарии, чтобы скрытие не меняло последовательность. Количество и текст скрытых дочерних объектов при скрытой родительской записи не выдаются.

## Текст и файлы

Публикация и комментарий: текст до 8192 байт UTF-8; пустой допустим только с вложением. Заголовок не требуется. До пяти файлов с действующими лимитами сервера. Отдельный безопасный Markdown-профиль в этот контракт не добавляется; базовый текст отображается без исполнения HTML.

Файлы проходят существующий AssetService. Для раздела feed загрузка требует read, scope chat.write и хотя бы одно эффективное publish/comment, с повторной проверкой на каждой операции. Право на загрузку не заменяет проверку конкретного действия: CreateFeedPost требует publish, CommentFeedPost — comment и доступность родителя. Файл принадлежит автору, тому же разделу, готов и ещё не привязан; привязка и публикация выполняются одной транзакцией. Один asset принадлежит ровно одному объекту chat/MLS/forum/feed. Отмена загрузки не удаляет опубликованный файл; очистка незавершённых загрузок не удаляет опубликованные файлы ленты.

Каталоги файлов, список авторов, повтор загрузки и DownloadChunk проверяют текущие ACL и видимость feed-родителей, включая каждую следующую часть скачивания. Скрытие записи блокирует файлы записи и всех комментариев, скрытие комментария — только его файлы. Восстановление записи не снимает отдельное скрытие комментария. Уже полученные клиентом байты сервер отозвать не может.

## Модерация и жалобы

ModerateFeedPost/ModerateFeedComment принимают hidden, причину 1..1024 байт UTF-8 и expected_revision. Скрытый объект возвращается заглушкой без текста, автора и вложений всем клиентам, включая автора и модератора. Скрытая запись запрещает новые комментарии. Оригинал остаётся в БД для восстановления. Изменение, revision и feed_moderation/admin_audit записываются атомарно; ошибка аудита откатывает мутацию.

Жалоба разрешена читателю видимого неархивного объекта без права публикации/комментирования. Поле comment_id пусто для самой записи. Один principal может оставить одну жалобу на объект, повтор не меняет причину. Лимит — 30 новых жалоб в час на principal для всех его устройств и разделов ленты вместе. Существующий отдельный лимит форума сохраняется. Заявитель берётся из сессии и не включается в публичную модель FeedReport; копии текста и файлов не сохраняются в жалобе.

Очередь разделена на ожидающие и рассмотренные, страницы идут по id ASC. Решение dismiss/hide требует причину; hide также требует текущую revision объекта. Решение, скрытие, revision и аудит сохраняются одной транзакцией. Конкурентное/повторное решение возвращает Aborted. Другие жалобы на тот же объект не закрываются автоматически. Журнал связывает report_id с решением и не содержит исходный текст. Политика и ACL заново проверяются при открытии очереди, получении страницы и подтверждении решения.

## Хранение и совместимость

Миграция 31 после схемы 30 добавляет тип feed, ограничения без MLS/превью, таблицы feed_posts, feed_comments, feed_access, feed_reports и feed_moderation, привязки файлов и индексы пагинации. Существующие пространство, ключи, каналы, файлы и голосовой лимит сохраняются. Добавление feed не превращает прежние форумы в ленты. Удаление канала каскадно удаляет его записи, комментарии, правила, жалобы, аудит и файлы в соответствии с действующей политикой удаления.

В таблицах раздельные внешние ключи для публикации и комментария обеспечивают принадлежность разделу и родителю. Квоты и длины дополнительно ограничиваются БД. Для sequence используются существующие сериализованные счётчики под блокировкой раздела/публикации; MAX без блокировки недопустим. Миграция проверяется на копии схемы 30 с прежними данными и повторным запуском. Откат бинарника после новой миграции без отдельной проверки совместимости не обещается; перед обновлением нужна резервная копия.

Клиент сначала обновляет список каналов/права и данные активной ленты, затем отображает подтверждённый снимок. Опрос активной страницы обновляет уже загруженную часть без возврата скрытых данных из старого запроса; отзыв read очищает содержимое и закрывает недоступные действия. Серверные события для ленты пока не заявляются. Фокус и локальные контроллеры ввода остаются в виджетах, прикладные операции и гонки запросов — в Cubit; повторяющиеся состояния генерируются Freezed.

## Приёмка

- Реальная PostgreSQL, gRPC и Connect: публикация запрещена комментатору, комментарий разрешён читателю только явной политикой, отсутствие chat.write запрещает мутации, manage не расширяет publish; отзыв прав и смена политики действуют при повторе и загрузке частей файла.
- Повторы, конкурентные комментарии/политика/скрытие, revision, откат аудита, изоляция разделов, страницы без дублей при новых записях, конфликт ключа и перестановки файлов.
- Нельзя прикрепить чужой, неготовый, уже привязанный файл, файл другого раздела или файл сверх квоты; скрытие закрывает все пути выдачи, восстановление родителя сохраняет скрытие дочернего объекта.
- Миграция схемы 30, перезапуск и удаление раздела сохраняют ожидаемые данные/идентичность и не оставляют доступных сиротских файлов.
- Flutter: Cubit, устаревшие ответы, смена раздела, сохранение черновика/ключа, старый runtime, состояния читателя/комментатора/автора/модератора и узкая компоновка. COG ≤15, анализ собственных пакетов и подходящие тесты.
- Работающие Windows-клиенты с двумя участниками и модератором проходят исходный сценарий, обрыв, повтор и отзыв доступа при открытом диалоге. Физическая проверка Android отложена по решению пользователя; Windows и CI не считаются её подтверждением.
