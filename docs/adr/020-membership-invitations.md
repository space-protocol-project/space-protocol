# ADR-020: членство и приглашения локального пространства

Дата: 8 октября 2026. Статус: реализован первый срез для одного общего чата. Полный ACL и публичный deployment не заявляются.

## Решение

Криптографическая аутентификация доказывает principal и действующий device grant. Членство отдельно определяет серверные права. Владелец берётся из неизменяемого этим API owner_id; остальные роли — admin/member/reader. Blocked закрывает чтение, запись и управление независимо от device scopes. Management API требует и роль owner/admin, и root-signed scope space.manage; изменение чужих ролей и блокировка доступны только owner.

Миграция 4 добавляет memberships с revision и backfill существующих principals как member. Открытая регистрация создаёт member для нового principal. Закрытая регистрация требует приглашение для нового root. Известный незаблокированный root может регистрировать устройства; роль сохраняется. Регистрация заблокированного root отклоняется.

Приглашение содержит независимый ID, SHA-256 случайного 32-byte bearer token, роль member/reader, expires_at, max_uses, uses и revoked. Токен iv_ возвращается создателю только один раз. Администратора назначает owner, а не bearer ссылка. Выдача/отзыв требуют management permission и записывают audit; в audit нет secret token. Диапазоны: 60–604800 секунд, 1–100 вступлений, 100 одновременно активных приглашений.

## Вступление

Перед вступлением клиент получает публичный PreviewInvite через POST JSON. Секрет не передаётся в query. Ответ показывает роль, срок, title и server_id; клиент проверяет соответствие discovery. Preview не резервирует место, доступность повторно проверяется в транзакции.

Для нового устройства CompleteChallengeRequest содержит invitation_token при device.register. Root подписывает обычный transcript регистрации устройства; отдельный bearer код разрешает именно членство от имени выдавшего приглашение. Приглашение не является подписью владельца и не связывает заранее конкретного получателя: любой обладатель кода может использовать своё подтверждённое root. Изменение/утечка кода вредит приглашению, поэтому он требует защищённого транспорта и явного согласия получателя. Будущий профиль адресного приглашения потребует отдельного подписанного назначения.

Создание principal, членство, регистрация grant, расход места и потребление challenge фиксируются одной транзакцией. Ошибка любого шага откатывает все изменения. В приглашении блокируется строка FOR UPDATE; одновременное использование последнего места даёт одного победителя. Отдельная таблица invitation_redemptions обеспечивает идемпотентность для пары invitation/principal. Principal блокируется до вступления; членство не может быть изменено приглашением, если уже существует, и blocked никогда не снимается.

Для уже вошедшего устройства AcceptInvite требует действующую сессию. Повтор принятого приглашения не расходует дополнительное место, в том числе после исчерпания max_uses, но отзыв или истечение срока всё равно запрещают принятие. Отзыв приглашения не удаляет ранее созданное членство.

## Проверки доступа

CreateContent берёт shared lock членства на транзакцию записи: блокировка/понижение ждут ранее начатой записи, а после commit изменения новые записи отклоняются. ListContent/ListEvents проверяют актуальные роли перед чтением. Subscribe повторяет проверки при чтении batch и перед отправкой событий; блокировка завершает поток PermissionDenied. Разрешённые до изменения и уже отправленные кадры не отзываются.

UpdateMember требует expected_revision и возвращает Aborted/HTTP 409 при конфликте. Владелец не может понизить/блокировать себя; admin не меняет членство. GetMembership доступен аутентифицированному пользователю даже при блокировке, чтобы показать её причину; Logout также остаётся доступен. Аутентификация сама по себе не открывает content API.

## API-пример

```http
POST /api/v1/space/invites
Authorization: Bearer OWNER_TOKEN
Content-Type: application/json

{"role":"reader","ttlSeconds":86400,"maxUses":1}
```

```json
{"invite":{"id":"in_…","role":"reader","expiresAt":"1791504000","maxUses":1},"token":"iv_…"}
```

```http
PATCH /api/v1/space/members/u_…
Authorization: Bearer OWNER_TOKEN
Content-Type: application/json

{"role":"reader","blocked":true,"expectedRevision":"1"}
```

Это иллюстрации, не готовые секреты или тестовые векторы. Int64 в gateway JSON передаются строками.

## Границы и проверка

Пока роли общие для единственного general chat. Нет отдельных каналов/ACL, moderator, pending approvals, leave, QR приглашения, root pairing и публичного HTTPS. Browser и Flutter используют разные roots; одноразовую ссылку следует использовать в выбранном клиенте. Fragment скрывает код от HTTP request/referrer, но не от копирования ссылки, буфера обмена, расширений и доступа к браузеру.

PostgreSQL-тесты проверяют закрытую регистрацию, гонку шести получателей за одно место, повтор, read/write права, назначение admin, запрет изменения owner, revision conflict, live block и запрет обхода приглашением, отзыв и срок. WebCrypto/Go HTTP interoperability проверяет reader enrollment в closed режиме и HTTP 403. Flutter проверяет интерфейс читателя и общий сценарий SDK. Полноценный браузерный сценарий с IndexedDB между перезапусками ещё предстоит.
