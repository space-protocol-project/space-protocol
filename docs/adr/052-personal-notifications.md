# ADR-052: персональный список уведомлений

25 октября 2026. Опубликовано в приложении v0.7.24 / runtime v0.7.19, схема 36.

## Контракт

`core.personal.notifications.v1` объявляет PersonalNotificationService через
gRPC и Connect. ListPersonalNotifications принимает выбранный channel_id,
after_sequence, through_sequence, unread_only, limit и baseline_only.
Principal берётся только из проверенной сессии. Права проверяются заново
для каждого запроса: сессия, grant, scope, членство, visible/read ACL;
архивный, MLS или неподдерживаемый раздел отклоняется. Оба RPC ограничены
тремя секундами; страница и пакет отметок — 50 записями.

MarkPersonalNotificationsRead принимает либо `ids` уведомлений, либо
`chat_content_ids` фактически видимых сообщений обычного чата. Смешивание
запрещено. Во втором случае сервер разрешает только собственные уведомления
выбранного получателя с видом chat message; неизвестная, чужая или недоступная
цель отклоняет весь пакет. Повторная отметка безопасна. Это позволяет
подтвердить видимое обращение без просмотра пропущенных сообщений и без
сканирования всего персонального списка на клиенте.

Цель различает сообщение обычного чата, тему/ответ форума и публикацию/
комментарий ленты. В записи есть стабильный ID, причина и точные ID цели,
родителя и последовательность перехода. Биты reasons: 1 — выбранное
упоминание, 2 — ответ автору темы/публикации. Обе причины в одном содержимом
одному получателю объединяются. unread_reasons — непросмотренное подмножество.
Собственный автор, свободный @текст и скрытое/удалённое содержимое исключены.
Текст и имя берутся из текущего доступного содержимого; фрагмент ограничен
240 Unicode code points. MLS-пакеты и их формат не меняются.

## Порядок страниц

Миграция 35→36 добавляет personal_notifications и отдельный счётчик для пары
раздел/получатель. Создание записи выполняется триггером в транзакции
содержимого. Блокировка раздела и строки счётчика держится до её завершения:
транзакция с большим номером не фиксируется раньше меньшего. PostgreSQL
MVCC скрывает незавершённый счётчик. Откат откатывает также номер уведомления.

При through_sequence=0 сервер захватывает текущую верхнюю границу этого
получателя. Следующая страница передаёт through_sequence и next_sequence
предыдущего ответа, сохраняя unread_only. События, появившиеся позже, читаются
отдельным следующим циклом после прежней границы. На последней странице
next_sequence равен through_sequence, даже если промежуточные записи стали
недоступны. Клиент не застревает на скрытом или снятом упоминании.
Отрицательный или будущий курсор отклоняется. После восстановления более
старой резервной копии будущий локальный курсор нужно заново согласовать
через начальную границу, а не переносить в восстановленную историю.

baseline_only с обоими курсорами 0 возвращает только текущую границу,
без содержимого и без отметки просмотра. Это подготовка к последующей
системной доставке без лавины старой истории. Новый RPC пока не показывает
карточки ОС самостоятельно. Курсор не служит полномочием: при любых его
значениях запрос ограничен текущим principal и доступным разделом.

## Просмотр, правки и ограничения

MarkPersonalNotificationsRead принимает ID уведомлений. Все ID пакета должны
принадлежать текущему получателю и иметь доступную цель. Ошибка откатывает
весь пакет; повторы сохраняют результат. Отметка общая для устройств.
Она не двигает курсор сообщений, тем или комментариев. Для упоминаний форума
и ленты синхронизируется прежняя отдельная community_mentions.read_at.

Прежние отметки упоминаний отражаются в unread_reasons; общий курсор форума/
ленты снимает только причину «ответ», сохраняя невидимое упоминание.
Правка с новым адресатом создаёт новую запись. Снятие и повторное добавление
того же адресата сохраняют ID, последовательность и просмотр; восстановление
скрытого содержимого также не создаёт нового события доставки. Удалённая
личность в старой аннотации не препятствует обновлению базы.

Бюджет выбранных адресатов — 100 в час на автора по всем разделам и устройствам,
включая обычные чаты и новые адреса при правке. Совпадающие адресаты одного
сообщения считаются один раз. Отклонённая операция не оставляет сообщение,
уведомление или продвижение счётчика; принятый повтор не расходует бюджет.

Миграция сохраняет community_mentions и их просмотр. Прежние структурированные
упоминания чата становятся непросмотренными: отдельной отметки для них в
схеме 35 не было. Старые ответы остаются в прежней сводке; отдельные записи
ответов создаются после миграции. Новые серверные записи не хранят копии текста.
Сохранённый просмотр позволяет подавлять повторное добавление адресата.

Серверная выдача, Dart API, наблюдение Bloc/Cubit, персональный список
и системные карточки работающего приложения с точным переходом реализованы
в совместимом выпуске v0.7.24 / v0.7.19. Доставка нового источника при закрытом процессе Android и ручная
приёмка нативных карточек остаются отдельными шагами. Старый runtime не получает новые RPC:
клиент проверяет capability. Каталог опубликованного runtime не обновляется.
Откат после схемы 36 требует восстановления копии, совместимой с целевым runtime.
