# ADR-024: каналы и права доступа

Дата: 8 октября 2026 года. Статус: экспериментальная реализация сервера.

## Область реализации

PostgreSQL остаётся источником истины. Go-сервер предоставляет один контракт
через gRPC и HTTP/JSON grpc-gateway. Hasura, GraphQL и дополнительные системы
авторизации не используются. Миграция 8 расширяет существующие `channels`;
`contents` и `events` уже привязаны к каналу и продолжают использовать эту связь.

Рабочий тип представления сейчас `chat`. Запрос создания `forum`, `feed`,
`live_stream`, `voice_room`, `video_room` или `stage` отклоняется: эти обработчики
предстоит реализовать отдельно. Смена типа существующего канала пока отсутствует,
чтобы не менять смысл уже записанного контента.

Формы управления каналами и ACL в `/space`, список и переключение каналов во Flutter реализованы следующим срезом. Новый клиент загружает авторизованный список после входа и не требует публичного `general`. Старые сборки клиента остаются привязанными к general; обновляйте сервер и клиент вместе.

## Модель канала

| Поле | Значение |
|---|---|
| `id` | Неизменяемый уникальный адрес: `[a-z][a-z0-9_-]{0,63}` |
| `title` | Непустое название, максимум 320 байт UTF-8 |
| `view_type` | Сейчас только `chat`; manifest содержит `views: [{id: "chat", type: "chat"}]` |
| `position` | 0–100000; сортировка по position, затем id; одинаковые значения допустимы |
| `archived` | История сохранена, новые сообщения запрещены, в обычных списках канал отсутствует |
| `public_preview` | Явное разрешение публиковать метаданные канала в manifest без входа |
| `revision` | Общая версия метаданных и ACL; начинается с 1 |
| `next_sequence` | Следующий номер сообщения/события внутри этого канала |

Лимит прототипа: 100 каналов, включая архивированные, и 1000 сообщений в каждом.
Удаление канала и сообщений этим API не предусмотрено. Повтор создания с тем же
id возвращает `AlreadyExists`, независимо от совпадения названия.

При обновлении метаданных клиент передаёт все поля и `expected_revision`.
Несовпадение версии возвращает `Aborted` / HTTP 409. ACL имеет ту же revision:
изменение доступа делает устаревшую форму названия недействительной и наоборот.

При миграции `general` получает прежнее `space_settings.chat_title`, публичный
preview и обычные права member/reader. Identity, сообщения, их авторы и курсоры
не меняются. Старый API настройки `chat_title` и новый API названия `general`
синхронизированы; оба увеличивают соответствующую revision при изменении названия.
`chat_enabled=false` остаётся общим выключателем всех чат-каналов: manifest пустой,
чтение/отправка/подписка недоступны. ListChannels сохраняет доступные метаданные с read/write=false, чтобы каналы можно было настраивать. Управление метаданными и ACL остаётся доступным
уполномоченным пользователям, чтобы можно было исправить настройки.

## Права

Каждое правило содержит четыре логических значения:

| Право | Разрешённое действие |
|---|---|
| `visible` | Видеть метаданные канала в авторизованном manifest и списке |
| `read` | Читать историю, журнал событий и подписываться |
| `write` | Создавать сообщения |
| `manage` | Менять название, порядок, архивировать и возвращать из архива |

Обязательные зависимости: `write ⇒ read ⇒ visible`; `manage ⇒ visible`.
Разрешено показывать название без доступа к истории и делегировать управление
метаданными без чтения сообщений. Непоследовательные правила отклоняются.

Субъект правила — ровно одно из:

- роль пространства `member` или `reader`;
- `principal_id` существующего участника пространства.

Алгоритм проверки:

1. Проверить действующую сессию, устройство и его цепочку полномочий.
2. Проверить членство и блокировку в пространстве.
3. Для owner/admin использовать все права канала. Они сохраняют возможность
   исправить ошибочный ACL; ACL не ограничивает администраторов пространства.
4. Для остальных выбрать индивидуальное правило, если оно существует.
   Оно **полностью заменяет** правило роли, даже если все значения false.
5. Иначе использовать правило текущей роли. Если правила нет — все права false.
6. Ограничить результат scopes устройства: `chat.read`, `chat.write`, `space.manage`.
   Роль пространства `reader` никогда не получает write, даже через индивидуальный ACL.
7. Запретить запись в архив; проверить общий выключатель chat_enabled для контента.

Новый канал по умолчанию доступен участникам: member читает и пишет, reader читает.
Public preview по умолчанию выключен. Для закрытого канала замените ACL целиком,
оставив только индивидуальные правила нужных участников.

Создание канала, чтение и изменение ACL требуют owner/admin **и** device scope
`space.manage`. Делегированный `manage` не даёт создавать другие каналы, менять
ACL, роли пространства или публичность preview. Индивидуальные правила для
owner/admin отклоняются, поскольку они не влияют на их полномочия.

## API

Все приведённые операции, кроме анонимного manifest, требуют
`Authorization: Bearer <действующая сессия>`; ключ администратора в клиент не передаётся.
В HTTP поля используют camelCase; большие целые protobuf представлены строками.

| HTTP | gRPC | Назначение |
|---|---|---|
| `GET /api/v1/channels` | `ListChannels` | Видимые активные каналы, эффективные permissions |
| `GET /api/v1/channels?includeArchived=true` | `ListChannels` | Также доступные архивы |
| `POST /api/v1/channels` | `CreateChannel` | Создание канала |
| `PATCH /api/v1/channels/{id}` | `UpdateChannel` | Все метаданные с проверкой revision |
| `GET /api/v1/channels/{id}/access` | `GetChannelAccess` | Настроенные правила и revision |
| `PUT /api/v1/channels/{id}/access` | `UpdateChannelAccess` | Полная замена правил |
| `GET /api/v1/manifest` | `GetManifest` | После входа — видимые каналы; без входа — только public preview |

Создание:

```json
{
  "channelId": "team",
  "title": "Рабочая группа",
  "viewType": "chat",
  "position": 10,
  "publicPreview": false
}
```

Ответ содержит `channel` с `revision: "1"`, views и эффективными permissions
вызывающего пользователя. Архивирование или восстановление:

```json
{
  "title": "Рабочая группа",
  "position": 10,
  "archived": true,
  "publicPreview": false,
  "expectedRevision": "1"
}
```

Полная замена ACL для закрытой группы, где указанный участник читает и пишет:

```json
{
  "expectedRevision": "2",
  "rules": [
    {
      "principalId": "u_ПОДСТАВЬТЕ_РЕАЛЬНЫЙ_PRINCIPAL_ID",
      "permissions": {"visible": true, "read": true, "write": true, "manage": false}
    }
  ]
}
```

Пустой `rules: []` закрывает канал для member/reader. Owner/admin сохраняют доступ.
Ответ ACL перечисляет настроенные правила, а не ограничения scopes каждого устройства.
Эффективные разрешения конкретного пользователя возвращаются в ListChannels/manifest.

Контент использует существующие endpoints с новым id:

```text
POST /api/v1/channels/team/content
GET  /api/v1/channels/team/content?after=message-1
GET  /api/v1/channels/team/events?after=event-1
GET  /api/v1/channels/team/events/subscribe?after=event-1
```

`message-1` и `event-1` — курсоры внутри канала. Приложение обязано хранить их
вместе с server_id и channel_id. Один ключ идемпотентности можно использовать
в разных каналах; в пределах канала он привязан к автору и тексту.

## Закрытые данные и подписки

Скрытый канал возвращает `NotFound` / 404, независимо от переданного курсора.
Видимый канал без нужного разрешения возвращает `PermissionDenied` / 403.
Анонимное чтение контента запрещено даже при public_preview=true.
Некорректный или отозванный токен в manifest возвращает ошибку, а не откат
к анонимному результату.

Public preview — отдельное явно выбранное раскрытие названия, id, типа и версии
канала для посетителей. Оно не зависит от ACL чтения. Для полностью скрытой группы
выключите public_preview. Анонимному посетителю permissions не выдаются.

Чтение истории и событий выполняется под транзакционными блокировками сессии,
членства, настроек и канала. Запись и замена ACL используют блокировку канала.
Проверка разрешений и операция не разделены независимыми запросами без блокировки.

Subscribe проверяет доступ до первой выдачи, каждые 500 ms при чтении журнала
и перед **каждым** событием/heartbeat, включая уже загруженную пачку. Во время
отправки удерживаются блокировки; отзыв ждёт завершения текущей отправки, для
которой действует таймаут 5 секунд. После завершения изменения ACL новая отправка
по старым правам не начинается. Уже переданные клиенту данные отозвать невозможно.
Проверка не означает точного времени доставки байтов по сети.

Отзыв только write оставляет читающую подписку открытой. Отзыв read/visible,
блокировка, выключение чата и отзыв устройства завершают поток с ошибкой.
Архивирование оставляет чтение истории и подписку доступными, но запрещает запись.

Журнал admin_audit фиксирует создание, изменение метаданных и замену ACL с id
канала и новой revision. Полные предыдущие ACL в нём пока не сохраняются.

## Проверки и следующий срез

Тесты охватывают изоляцию истории/идемпотентности каналов, фильтрацию manifest,
индивидуальные запреты, верхние ограничения ролей и scopes, архив, повторное
открытие базы, обновление старой схемы, конфликты revision и отзыв уже открытых
gRPC/HTTP подписок. Тесты PostgreSQL требуют SPACE_TEST_DATABASE_URL; без неё
пропускаются явно. CI запускает их на настоящей PostgreSQL.

Далее: события обновления списка каналов, затем forum/feed и отдельный этап медиа. Группы, moderator, наследование
ACL, приглашения конкретного канала и событие изменения списка каналов пока отсутствуют.
