# ADR-037: постоянная очередь обычных сообщений

Статус: принято, выпущено в приложении v0.4.0 от 16 октября 2026; совместимый runtime v0.3.6.

## Причина

Сервер хранит ключ идемпотентности CreateContent в PostgreSQL, но клиент раньше сохранял его только в памяти. При потере подтверждения и перезапуске повтор мог создать второе сообщение. Простой перенос черновика этого не исправляет.

## Решение

1. До первого RPC атомарно сохранить неизменяемые текст, ID канала, ID готовых вложений, ключ запроса и время постановки в защищённое хранилище ОС. Очищать ввод только после успешного сохранения. Для двух намеренно отправленных одинаковых текстов создавать разные ключи.
2. Область очереди — постоянный origin, server ID, principal ID и grant ID. Изменение маршрута не меняет область. Смена разрешения устройства не разрешает автоматическую отправку старой очереди от нового grant.
3. Все изменения читают актуальную запись под блокировкой области. Файл блокировки не содержит сообщений. При повреждении/ошибке записи не стирать документ и не подменять его пустым.
4. Отправлять по сохранённому ID канала независимо от выбранного экрана. Внутри канала сохранять порядок; остановленный первый запрос не мешает другому каналу. При временной сетевой ошибке повторять прежний ключ с ограниченной экспоненциальной задержкой до 32 секунд. Ошибки доступа, данных и некорректные ответы останавливать для ручного решения.
5. Проверить область и ответ, сохранить историю, затем удалить подтверждённый запрос. Не считать отсутствие ответа доказательством неотправки. Сбой локальной записи после ответа оставляет прежний ключ для безопасного повтора. Поздние результаты старой области не меняют текущую.
6. Ограничить документ 100 записями и 1 МиБ; при заполнении отказывать новому запросу без вытеснения прежних. Не применять 14-дневное сокращение кеша истории к ожидающим сообщениям.
7. Ошибка доступа прекращает отправку и скрывает содержимое, но не удаляет очередь. Явная очистка локальных данных удаляет соответствующую очередь. Удаление отдельного запроса требует предупреждения: сервер мог уже принять его, а локальная отмена не удаляет сообщение у участников.

## Границы

Это очередь создания сообщений обычных каналов, а не новая схема E2EE. MLS продолжает использовать собственные ключи, ratchet и ciphertext outbox. Обычные правки/удаления/реакции остаются онлайн. Содержимое обычного канала по-прежнему доступно серверу.

Ссылки на готовые вложения сохраняются, локальные файлы и незавершённые загрузки — пока нет. Сервер очищает неиспользованные файлы через 24 часа; недействительные ссылки приводят к остановленной записи, а не потере текста. Перенос ожидающих сообщений на другой grant требует отдельного решения о доверии. Приложение не отправляет сообщения, когда процесс закрыт; восстановление выполняется при следующем подключении.

Контракт и миграции сервера не меняются; подходит runtime v0.3.6 со схемой 18. Проверки реализации и фактический результат перечислены в `space-app/docs/OUTBOX.md`: ошибки сети/диска/прав, поздние ответы, несколько областей, настоящий ConnectRPC/PostgreSQL с потерянным ответом и настоящий Windows secure storage в разных процессах.


## Дополнение: локальные файлы после v0.4.0

В следующем рабочем срезе файловая копия сохраняется AES-GCM до первого RPC. Ключ в системном защищённом хранилище, AAD связывает область и описание файла; исходный путь не сохраняется. Подготовка копий и запись очереди используют общую блокировку между процессами. Только после чтения исправных метаданных допускается удаление аварийных копий без ссылок. Ограничение копий — 200 МиБ на пространство и выдачу устройства.

Ключи BeginUpload сохраняются, загрузка продолжается с подтверждённого сервером смещения. ID готовых файлов записываются до CreateContent; повтор принятого сообщения использует прежний ключ и прежние ID. Серверный контракт и схема 18 не меняются. Выбранные файлы до нажатия «Отправить» и перенос на новый grant не включены. Подробности и ограничения — `space-app/docs/QUEUED-FILES.md`.
