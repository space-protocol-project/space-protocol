# ADR-023: перезапуск клиента и безопасная ротация root

Статус: **экспериментальные серверная ротация, Flutter journal/UI, root history и recovery v2 реализованы; /space UI ротации и pairing после ротации ещё предстоят**.
Дата: 8 октября 2026 года.

## Проблема

Сегодня principal имеет вид `u_ + SHA-256(root_public_key)`. Это правило повторяется в Go, WebCrypto и Dart и проверяется получателем pairing proof. Поэтому замена root в одной строке базы недостаточна: старый ID больше не соответствует новому ключу, а клиенты отвергнут доказательство. Создание нового principal потеряет связь с прежним членством, ролью owner, авторами сообщений и устройствами.

Отзыв device grant не обезвреживает копию root: этот ключ вправе зарегистрировать новый device. Текущий UI не должен обещать устранить компрометацию root обычным отзывом устройства.

## Что уже проверяется

`server/tools/browser-restart.mjs` запускает отдельный Chromium в GitHub CI с временными профилями и одноразовой базой. Он использует настоящую панель `/space` и её IndexedDB:

1. Новая идентичность входит в тестовое пространство и сохраняет неэкспортируемые CryptoKey.
2. Скачиваются JSON и QR PNG зашифрованной recovery-карточки.
3. Браузер полностью закрывается и запускается с тем же профилем.
4. Проверяются прежний root public key, grant ID и успешный повторный вход.
5. В новом пустом профиле неверный пароль PNG не создаёт запись идентичности.
6. Правильный пароль восстанавливает прежний root public key с новым рабочим grant.
7. В записанном рабочем профиле отсутствует recoveryPrivate.
8. После второго закрытия/запуска восстановленный профиль снова входит с тем же рабочим grant.

`client/tool/recovery_interoperability.dart` дополнительно запускает новый процесс Dart. Он читает сериализованную тестовую запись device-only, входит с прежними principal/owner/grant и читает сообщения. Это проверка процесса и формата vault, **не проверка плагина Windows secure storage**: для последней нужен отдельный нативный integration runner. Временная запись с device seed существует только внутри каталога одноразового теста и удаляется вместе с ним; это не новый способ хранения ключей в приложении.

CI не использует пользовательский браузер, его профиль, настоящие аккаунты или рабочую базу. На локальном компьютере браузерный скрипт отказывается запускаться вне CI. Сам `CI=true` не является защитной границей; изоляцию обеспечивает среда workflow.

Механизм сохранения тестового профиля: [Playwright launchPersistentContext](https://playwright.dev/docs/api/class-browsertype#browser-type-launch-persistent-context).

## Предлагаемая модель ротации

Principal становится **неизменяемым идентификатором**, а root — меняемым управляющим ключом. Для существующей идентичности ID сохраняется полностью. Для новой первая регистрация ещё может выдавать `u_hash(genesis_root)`, но после неё ID нельзя пересчитывать по текущему root.

```text
principal_id (не меняется)
    ├─ membership / owner / authorship
    ├─ root_epoch = N
    └─ current_root_public_key
               │
               └─ rotation: подписи старого и нового root
                         ↓
               root_epoch = N + 1
               новый device grant
               прежние grants / sessions / recovery / pairings закрыты
```

Двойная подпись доказывает разрешение прежнего root и владение новым секретом. Она не решает гонку с атакующим, который уже знает старый root: при компрометации нужен отдельный явно описанный режим восстановления/заморозки. Пока такой режим не спроектирован, нельзя обещать гарантированный возврат контроля.

### Серверные данные

Новая миграция добавляет историю root, например:

| Поле | Назначение |
|---|---|
| principal_id | Прежний постоянный ID |
| root_epoch | Монотонная версия root |
| public_key | Управляющий ключ данной версии |
| activated_at / retired_at | Аудит перехода |
| rotation_id | Идемпотентная ссылка на операцию |
| transcript / signatures | Старое и новое подписанное доказательство |

Все использованные root keys должны оставаться уникальными, включая выведенные из употребления. Нельзя позволять украденному старому root пройти открытую регистрацию как «новая» идентичность: для этого необходима проверка исторических ключей, а не только UNIQUE на current root.

`auth_epoch` повышается транзакционно. Сессии, challenges, старые recovery grants и сопряжения должны проверять новую эпоху и перестать работать. Membership, author_id и история сообщений сохраняются.

### Первоначальный проект API

Ниже исходный проект контракта. Действующий RPC/HTTP контракт описан в разделе серверного перехода:

```json
{
  "principal_id": "u_existing_identity",
  "expected_root_epoch": 1,
  "new_root_public_key": "BASE64URL_32_BYTES",
  "new_device_public_key": "BASE64URL_32_BYTES",
  "requested_scopes": ["chat.read", "chat.write", "space.manage"],
  "operation_id": "CLIENT_RANDOM_ID"
}
```

Сервер выдаёт одноразовый challenge с canonical transcript. Подписываются все поля: server ID, origin, principal ID, прежний root и epoch, новый root/device, scopes, сроки, nonce, challenge ID и operation ID. Старый и новый root подписывают одни и те же canonical bytes с разделением ролей подписи: `space/root.rotate/old/v1` и `space/root.rotate/new/v1`, затем NUL и canonical JSON.

Завершение принимает обе подписи. Предлагается требовать также активную сессию исходной идентичности с отдельным правом ротации; device-only и recovery-card не должны неявно получать этот доступ.

В одной транзакции сервер:

1. Блокирует principal и проверяет expected epoch, обе подписи и одноразовый challenge.
2. Проверяет, что новый ключ не использован другим или историческим principal.
3. Сохраняет rotation proof и выводит старый root из употребления.
4. Повышает auth_epoch и отзывает старые grants/sessions/recovery/pairings.
5. Создаёт новое рабочее разрешение в новой эпохе.
6. Возвращает receipt с прежним principal и новой эпохой.

Scope нового устройства не может повысить роль пространства. Получатель должен проверять receipt и связь root с неизменным principal, а не доверять неподписанному полю из ответа.

### Совместимость и криптографическая связь

Все три реализации сейчас выводят principal из root. Нужен новый согласованный профиль и recovery envelope v2 с explicit principal/epoch и доказательством перехода. Старые клиенты должны ясно отклонять новый профиль, а не создавать другую идентичность автоматически.

Перед реализацией необходимо выбрать способ проверки root-history:

- Полная цепочка старых/новых root signatures: сохраняет доказуемую связь с genesis, но растёт при каждом переходе.
- Подписанный сервером checkpoint, привязанный к ранее доверенному server key: компактнее, но явно добавляет доверие серверу к утверждению current root.

Это остаётся открытым решением. Нельзя незаметно заменить пользовательское доказательство неподписанным серверным lookup. Pairing, recovery и ротация должны использовать один согласованный способ проверки.

### Сбой между сервером и vault

Перед отправкой commit клиент сохраняет новый секрет и operation ID в защищённый журнал ожидания. Старый root остаётся доступным до подтверждения серверного состояния. Потеря ответа после commit не должна уничтожить единственный новый root: повтор с operation ID возвращает прежний результат, а клиент умеет завершить операцию новым ключом.

После подтверждения клиент активирует новую запись, создаёт и проверяет новую карточку. Старые карточки помечаются недействительными. Удаление временной записи — только после сохранения нового рабочего состояния. Обновление родительской карточки и производных устройств должно быть явным действием пользователя.

## Критерии допуска реализации

- [ ] Согласован профиль неизменного principal и проверка root-history.
- [ ] Новая миграция; исторический root нельзя зарегистрировать заново.
- [ ] Canonical contract, доменное разделение, двойная подпись, replay protection.
- [ ] Проверка нового root possession и scope/role ограничений.
- [ ] Атомарный переход и отказ старым root/device/recovery/pairing/session.
- [ ] Сохранение owner, membership и авторства сообщений.
- [ ] Crash-safe pending journal и потерянный ответ после commit.
- [ ] Конкурентная ротация, чужой principal, прежняя эпоха и повтор operation ID.
- [ ] v1/v2 compatibility и отказ старых клиентов без потери vault.
- [ ] Go/WebCrypto/Dart interoperability и ручная нативная проверка secure storage.

## Порядок следующего среза

Сначала утвердить криптографическую связь stable principal/current root в контракте, затем добавить migration и серверную транзакцию, потом обновить оба клиента и карточки. Кнопка «Сменить root» появится только после проверки восстановления после сбоя. Текущая реализация и ограничения описаны в разделах ниже.


## Проверяемый прототип подписей

Добавлен Go-пакет `server/internal/identityrotation`: фиксированный canonical transcript, проверка ожидаемого principal/epoch/server/origin/target/scopes, challenge до 120 секунд и независимые подписи старого/нового root. Тесты отвергают подмену полей, перепутанные домены, истечение и отсутствие possession нового ключа.

Формат используется серверным AuthService; реализация транзакции, истории ключей и клиентского журнала описана ниже. Проверяемый формат сам по себе не заменяет полный сценарий клиента.

## Серверный переход — реализован 8 октября 2026 года

Миграция 7 добавляет `principal_roots` и `root_rotations`. ID существующего principal сохраняется. Регистрация ищет root в истории: текущий ключ получает прежний principal, retired root отклоняется. Genesis остаётся `u_hash(root)`, дальнейшие переходы ID не пересчитывают.

Экспериментальные RPC `CreateRootRotation` и `CompleteRootRotation` доступны через gRPC и grpc-gateway:

```json
{
  "profile": "root-rotation-v1",
  "operationId": "ro_BASE64URL_32_RANDOM_BYTES",
  "expectedAuthEpoch": "1",
  "newRootPublicKey": "BASE64_32_BYTES",
  "newDevicePublicKey": "BASE64_32_BYTES"
}
```

Это HTTP/ProtoJSON-запрос к `POST /api/v1/auth/root-rotations`. Его входные keys кодируются стандартным base64, а внутри canonical transcript — base64url без padding. Создание требует Bearer-сессию активного не-recovery устройства и текущую эпоху. Рабочее устройство само по себе не может завершить переход: нужны подписи обоих root. Scopes нового grant наследуются от исходного, роль не повышается.

Ответ содержит `challengeId` и `transcript` (bytes в ProtoJSON — base64). Клиент проверяет поля и подписывает canonical transcript в двух разных доменах. Затем вызывает `POST /api/v1/auth/root-rotations/complete`:

```json
{
  "challengeId": "rc_BASE64URL_32_RANDOM_BYTES",
  "oldSignature": "BASE64_64_BYTES",
  "newSignature": "BASE64_64_BYTES"
}
```

Завершение не требует старую Bearer-сессию: после commit она отозвана, а повтор нужен для восстановления потерянного ответа. Авторизация здесь — две проверенные подписи на одноразовом серверном challenge. Повтор того же завершённого proof возвращает прежние principal/epoch/grant даже после истечения challenge; неподписанный запрос не выдаёт receipt. Повтор не создаёт новый grant.

В одной транзакции изменяются current root/auth_epoch, сохраняется история перехода, отзываются прежние grants и сессии, отменяются pending/approved pairings с прежним root и создаётся новый 30-дневный working grant. Старые challenges закрываются проверкой эпохи/активности grant, а не удалением их строк. Прежние recovery keys и их дочерние устройства также закрываются. Membership и author_id не изменяются.

Реализованы интеграционные проверки PostgreSQL: две подписи, ошибочная подпись, параллельный повтор commit, тот же principal/owner, сохранённое авторство сообщения, отказ старым root/session/challenge/recovery, отмена pending pairing, новый вход, регистрация нового root с прежним ID и reopen базы.

**Граница:** серверный API ещё не подключён к пользовательским клиентам. Старые Flutter/WebCrypto проверки выводят principal из root и отвергают proof после ротации. Нельзя вручную вызывать этот API для единственной рабочей идентичности. Следующие задачи — root-history proof для клиентов, recovery envelope v2, защищённый pending journal, интерфейс подтверждения и полная interoperability проверка. Изолированный Go-тест использует собственные ключи и тестовую базу.

Новый root и новый device должны различаться между собой и с прежним root. Сервер дополнительно отвергает повторное использование прежних device keys этой идентичности в роли нового root/device. Это предотвращает перенос скомпрометированного рабочего ключа в новую эпоху по ошибке клиента.

## Клиентский журнал и root history — 8 октября 2026 года

Flutter vault v3 сохраняет полную цепочку сертификатов с отдельными old/new domains. Verifier начинает с hash(genesis root), проверяет подписи, порядок эпох, origin/server и конечный root. Auth challenge проверяется по verified principal/epoch, а не hash(current root). WebCrypto использует тот же контракт; recovery payload v2 сохраняет историю. Старые vault v1/v2 и карточки v1 читаются без изменения identity.

Перед commit новый root/device и обе подписи помещаются в отдельный защищённый slot `.rotation`, затем запись читается обратно. Active slot заменяется только после проверки receipt. При сбое записи, частично повреждённом active slot или сбое очистки журнал остаётся для повторного завершения. Отсутствующий/повреждённый active slot восстанавливается только из криптографически проверенного журнала и после успешного соответствующего серверного receipt; другая целая активная идентичность автоматически не заменяется.

Истёкший незавершённый challenge можно обновить с прежними новыми ключами и operation ID после входа исходным устройством. Завершённые receipts не удаляются и повторяются независимо от срока challenge.

Flutter UI содержит начало, завершение и обновление запроса. `/space` поддерживает восстановление карточки v2, но собственный UI ротации ещё не реализован. Передача root history через pairing — следующий пункт; до неё используется recovery v2. Полная цепочка ограничена 16 переходами, proof 2048 байт, protected journal 64 KiB; размеры encrypted recovery ограничены прежним envelope. QR: до 2800 байт, M до 2048, L выше; для более длинной истории нужен JSON.

Проверки: Dart/Go с ошибкой записи после server commit, частичной записью active slot, ошибкой cleanup, повторным receipt, прежним ID/ролью и новым входом. Новая карточка v2 проходит восстановление в Dart и WebCrypto; две подписи проверяются независимо, роль не повышается. Windows integration runner дополнительно сохраняет journal slot и проверяет его после отдельного запуска процесса.
