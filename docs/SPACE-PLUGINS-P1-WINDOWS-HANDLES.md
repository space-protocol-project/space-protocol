# P1/E03: наследование handles и разделение Windows LPAC-профилей

Продолжение [матрицы ресурсов](SPACE-PLUGINS-P1-WINDOWS-RESOURCES.md), 6 ноября 2026 года. Проверяется существующий launcher; его политика, capabilities и квоты не расширяются. Рабочее приложение и сервер пока не переключены на LPAC.

## Наследование файлового handle

Supervisor открывает отдельный временный файл и явно устанавливает `HANDLE_FLAG_INHERIT`. Worker получает числовое значение handle и идентификатор файла: номер тома и обе части file index. Сначала `GetHandleInformation` проверяет наличие handle; затем `GetFileInformationByHandle` отличает нужный объект от случайного повторного использования того же числового значения.

Создаются три последовательных LPAC-процесса: обычный список handles, положительный контроль, снова обычный список. При обычном списке файловый handle не входит в `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`: до ResumeThread supervisor вызывает DuplicateHandle с дочерним процессом как источником и требует ERROR_INVALID_HANDLE (6). Такой отрицательный процесс завершается без исполнения; отрицательный JSON в тестовом журнале формирует supervisor после проверки кода, а не worker. В положительном контроле тест заменяет разрешённый stderr файловым handle и требует успешного совпадения идентификатора. После каждого запуска Job пуст, активные вызовы и резервирование равны нулю.

Это намеренно демонстрирует значимость списка наследования: уже открытый разрешённый handle нельзя считать защищённым только ограничениями доступа по имени. По [документации Windows](https://learn.microsoft.com/en-us/windows/win32/procthread/inheritance) унаследованный handle сохраняет значение и объект; [HANDLE_LIST](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute) задаёт передаваемый список. Положительный контроль существует только в тесте, обычный launcher передаёт три канала обмена.

## Два отдельных профиля

Создаются два одновременно живущих `NewWindowsRestrictedHost` с различными package SID. Через `GetAppContainerFolderPath` находятся настоящие частные каталоги профилей. В каждом создаётся контрольный файл.

Для своего профиля worker обязан успешно прочитать исходное содержимое, записать файл и создать соседний файл прямыми `CreateFile`/`ReadFile`/`WriteFile`. После возврата контрольного состояния выполняются A → B и B → A: все три операции должны вернуть `ERROR_ACCESS_DENIED (5)`. Проверяются неизменность чужого файла и отсутствие созданного файла. Затем A закрывается: его каталог должен исчезнуть, а B должен повторно успешно выполнить операции в своём каталоге.

Проверяется файловая граница двух профилей одного пользователя и одной сессии Windows CI. Межпрофильные IPC/реестр, конкурентные запуски, переход между сессиями и перезагрузка этим тестом не покрыты.

## Приёмка

[CI 42172080051](https://github.com/space-protocol-project/space-server/actions/runs/42172080051) полностью успешен для `a2e603d6974987a8a699efc36f3698cd96b2a348`: все **9 заданий**. Go test/vet/mod verify/govulncheck и race-проверки трёх ОС успешны. Windows: **30 результатов pass LPAC**, **18 результатов прежнего Job-профиля**, два ожидаемых helper-пропуска; числа включают родительские и дочерние записи.

- Без включения файлового handle в список наследования supervisor дважды получил ERROR_INVALID_HANDLE (6) до ResumeThread. В положительном контроле настоящий LPAC worker получил тот же файл: query=0, same_file=true.
- Оба профиля успешно выполнили чтение/запись/создание своих файлов. Все шесть межпрофильных операций вернули ERROR_ACCESS_DENIED (5), чужие файлы не изменены. После удаления A профиль B повторно выполнил три операции.
- Сохранены [исходные результаты и метаданные](p1-results/2026-11-06-windows-lpac-handles/) с [SHA256SUMS](p1-results/2026-11-06-windows-lpac-handles/SHA256SUMS), включая журнал предыдущего сбоя восстановления. Байты артефактов не преобразованы.

На том же коммите [42171769928](https://github.com/space-protocol-project/space-server/actions/runs/42171769928) прошёл новые тесты, но упал в прежнем `Recovery/running`: OpenProcess по PID вернул ERROR_INVALID_PARAMETER (87). Повторена **вся матрица**, не отдельное задание. Причина исчезновения/недоступности PID ещё не установлена; этот сбой остаётся отдельным открытым пунктом, а повторный успех не доказывает его устранение.

## Исправления по результатам первых прогонов

[42170554194](https://github.com/space-protocol-project/space-server/actions/runs/42170554194) не прошёл: стандартные файловые операции Go в LPAC вернули Winsock 10093, а запрос идентичности отсутствующего handle завершил worker. Файловый probe переведён на прямые Win32-вызовы без ослабления ACL/capabilities. [42170993928](https://github.com/space-protocol-project/space-server/actions/runs/42170993928) подтвердил файловые сценарии, но ещё не handles. Ограниченный вывод stderr в [42171246796](https://github.com/space-protocol-project/space-server/actions/runs/42171246796) показал `STATUS_INVALID_HANDLE (0xc0000008)` непосредственно в `GetFileInformationByHandle`. Предварительная проверка GetHandleInformation внутри worker также вызвала исключение в [42171463734](https://github.com/space-protocol-project/space-server/actions/runs/42171463734). Итоговый отрицательный сценарий проверяет отсутствие handle из supervisor до ResumeThread; положительный сохраняет проверку идентичности внутри worker. Ни один из этих неполных прогонов не считается приёмкой блока.
