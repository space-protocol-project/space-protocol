# P1/E03: прототип Windows LPAC

Продолжение [ресурсного профиля Windows](SPACE-PLUGINS-P1-WINDOWS.md), 6 ноября 2026 года. Новый `NewWindowsRestrictedHost` в `space-server/experiments/extensions` проверяет ограничение прав нативного worker отдельно от Job Objects. Это явно выбираемый исследовательский конструктор; рабочие сервер и приложение пока используют прежние пути. E03/P1 остаются открытыми, выпуск отложен.

## Граница прав

Используется [LPAC из Windows API](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer): AppContainer с `PROC_THREAD_ATTRIBUTE_ALL_APPLICATION_PACKAGES_POLICY` / `PROCESS_CREATION_ALL_APPLICATION_PACKAGES_OPT_OUT`. Не выдаются сетевые или иные capability SID. Обычные широкие разрешения `ALL APPLICATION PACKAGES` не включаются в доступ контейнера.

Для каждого хоста создаётся отдельный AppContainer profile с криптографически случайным именем. В новом каталоге создаётся копия доверенного executable, ограниченная 64 МиБ. DACL каталога защищён от наследования: текущий пользователь и SYSTEM имеют полный доступ, SID данного контейнера — только read/execute с наследованием на копию worker. Исходный executable и ACL чужих каталогов не изменяются. Корень и путь executable задаёт доверенный supervisor, не пакет расширения.

`SECURITY_CAPABILITIES`, LPAC policy, список двух Job и список трёх разрешённых handles передаются в одном `CreateProcess` с `CREATE_SUSPENDED`. До `ResumeThread` хост читает [токен процесса](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ne-winnt-token_information_class) и требует AppContainer, точный SID своего профиля и нулевое число capabilities. Затем на impersonation-копии токена через [AccessCheck](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-accesscheck) выполняются две проверки искусственного ACL: доступ через собственный package SID должен быть разрешён, а через `ALL APPLICATION PACKAGES` — запрещён. Отказ API отличается от успешного запрета доступа; ошибка любого шага запрещает запуск.

Это проверка поведения ACL, соответствующего выбранной политике, а не универсальный документированный API `IsLPAC`. Её применимость ограничена принятым стендом. CI отдельно создаёт обычный AppContainer и LPAC с одним package SID: первый получает доступ через `ALL APPLICATION PACKAGES` и отклоняется проверяющим кодом хоста, второй не получает этот доступ и принимается. Оба остаются приостановленными в момент проверки. При ошибке создания, чтения токена или несовпадении прав повторного запуска с обычными правами нет.

WASM и запрос поступают через stdin, результат и диагностика — через stdout/stderr. В явный список environment для LPAC добавлена необходимая Windows переменная `LOCALAPPDATA`; всё окружение родителя не наследуется. Сохраняются пределы выходных данных, общий Job 512 МиБ, Job вызова 256 МиБ, общий CPU cap и очистка дерева. Проверка прав не меняет ABI и сроки публичного вызова.

При штатном закрытии сначала останавливается Job, затем удаляются собственный профиль и каталог executable. Отказ удаления возвращается вызывающему; повторный `Close` повторяет очистку. Аварийная уборка профилей после SIGKILL supervisor ещё не реализована.

## Приёмка CI

Проверяются настоящий WASM compiler/interpreter, токен LPAC, запреты чтения/перезаписи файла и создания файла в каталоге родителя, сетевое соединение с доступным родителю loopback endpoint. Тот же probe предварительно выполняется обычным `NewProcessHost`: loopback-соединение должно установиться. В LPAC соединение не устанавливается; отдельно сохраняются результат прямого `WSAStartup`, ошибка соединения и признак `WSAEACCES`. На стенде Winsock не инициализируется, поэтому этот результат не принимается за доказательство WFP-фильтра или сетевой capability-политики после успешной инициализации стека. Родитель повторно читает контрольный файл после worker.

Отдельно выполняются отказ прямого `VirtualAlloc` при индивидуальной квоте, создание настоящего потомка с последующей отменой и пустым Job, а также авария, избыточный вывод и нагрузка памяти. Прежние проверки Job Objects повторяются в том же workflow; они не считаются доказательством LPAC для всех собственных сценариев.

## Результаты GitHub CI

[Полный CI 42166102804](https://github.com/space-protocol-project/space-server/actions/runs/42166102804) успешен для `396a049b96636f34d65947dbe6ddbe7e1316b408`: все **9 заданий**. Go test/vet/mod verify/govulncheck и race-проверки выполнены на Linux, Windows и macOS; прежние Linux cgroup/systemd и macOS probes также успешны.

В отдельном Windows-задании приняты **6 верхнеуровневых LPAC-тестов и 6 подслучаев**, без ошибок и пропусков. Прежний Windows-профиль: **18 результатов pass**, один ожидаемый пропуск helper в родительском процессе. Эти числа включают родительские и дочерние записи Go test и не являются числом независимых сценариев.

- Настоящий echo WASM выполнен в compiler и interpreter; после штатного закрытия копия executable удалена, повторный Close успешен.
- `AccessCheck` при policy=0 разрешил `ALL APPLICATION PACKAGES`; при policy=1 отказал. Проверка хоста приняла только второй процесс до ResumeThread.
- Чтение/перезапись контрольного файла и создание файла в каталоге родителя запрещены. После LPAC-вызова контрольный файл сохранился.
- Прямой `VirtualAlloc` выделил **251 658 240 байт (240 МиБ)** и получил отказ Windows с кодом **1455** до достижения 256 МиБ общей committed memory worker/его runtime. Это не лимит RSS.
- Подтверждены два PID (worker и настоящий потомок); после отмены Job пуст. Нагрузка памяти, переполнение вывода и авария также завершились отказом и очисткой.
- Контрольный probe без LPAC подключился к loopback. В LPAC `WSAStartup` вернул `A system call has failed.`, соединение не установилось, `network_denied=false`: ожидаемый `WSAEACCES` при соединении не получен. Это подтверждает недоступность сети для данного probe, **но не закрывает отдельную проверку сетевого фильтра**.

[Исходные результаты, предварительные отказы и метаданные](p1-results/2026-11-06-windows-lpac/) сохранены с [SHA256SUMS](p1-results/2026-11-06-windows-lpac/SHA256SUMS). Байты артефактов не преобразованы; метаданные API записаны в UTF-8. Предварительные ревизии `f414f30`, `7a94785`, `2dd988b`, `f9175ff`, `596eaa8` не засчитаны. Итоговая полная матрица выполнена на одной ревизии.

## Выявленные несовместимости

Первый прогон отклонил создание LPAC из-за отсутствия `LOCALAPPDATA` в ограниченном окружении (`ERROR_ENVVAR_NOT_FOUND`). Переменная добавлена только для LPAC. Нагрузочные тесты усилены: ошибка создания/изоляции больше не засчитывается за отказ квоты.

Следующий прогон обнаружил `ERROR_INVALID_PARAMETER` при Win32 `GetTokenInformation` класса 46; диагностический прогон подтвердил конкретный класс. Проверка через native `NtQueryInformationToken` также вернула `STATUS_INVALID_INFO_CLASS` (`0xc0000003`). Она не принята как доказательство LPAC и удалена из итогового пути. Вместо неё используется описанная выше проверка конкретной семантики ACL с положительным контролем собственного SID и сравнением обычного AppContainer с LPAC. Наконец, сетевой сценарий выявил отказ инициализации Winsock вместо ожидавшегося `WSAEACCES` при соединении. Добавлены прямой замер `WSAStartup` и положительный контроль тем же executable без LPAC; граница сетевой приёмки сужена явно. Предварительные прогоны не считаются приёмкой.

## Оставшиеся границы

- Этот срез не обещает запрет любого обращения к ОС: Windows оставляет системные ресурсы и собственное хранилище профиля AppContainer. Его дисковая квота, очистка после аварии и защита от накопления профилей требуют отдельной реализации.
- Отдельное доказательство сетевой политики после инициализации Winsock, запрет исходящего Интернета/других интерфейсов, реестр, именованные объекты, доступ к процессам и наследование прав потомками нуждаются в отдельной расширенной матрице. Проверка loopback не заменяет её.
- Проверяется Windows Server 2025 x64 в GitHub CI. Приёмка настольной Windows из установщика, других поддерживаемых версий и клиентского catalog IPC остаётся открытой.
- Подпись и безопасное обновление worker, постоянный реестр sandbox-профилей и их восстановление, общий служебный lifecycle и подключение к рабочему приложению ещё предстоят.
- Обычный `NewProcessHost` не становится LPAC автоматически. Нельзя на основании этого прототипа объявлять весь Windows runtime изолированным по правам.
