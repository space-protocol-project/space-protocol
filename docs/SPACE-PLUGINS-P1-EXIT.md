# P1: конечные критерии завершения

Статус: критерии зафиксированы в границах этапов 30 октября 2026 года; приёмка ещё не выполнена. Реестр выполнения — [TODO](../TODO.md). Этот документ уточняет P1 «контракты и прототипы» из [плана миграции](SPACE-PLUGINS.md#21-этапы-реализации-и-ответственность-репозиториев); он не объявляет готовыми рабочую систему расширений или выпуск 0.9.0.

## Результат P1

P1 завершается, когда выбраны и проверены runtime, границы изоляции, формат пакета, ABI, API и декларативный UI, а разработчик может воспроизводимо собрать демонстрационный пакет через прототип SDK. Решения должны позволять начать P2 без специальных обходов для Чатов, Комнат, Обсуждений или Ленты.

Фиксация кандидата контрактов для P2 не означает обещание стабильного публичного API. Экспериментальные space_plugin_p1 и space.ui.p1 не переименовываются в v1 автоматически. Любое изменение кандидата после приёмки получает новую версию, обновление схем и повтор затронутых проверок. Публичная политика совместимости и выпуск SDK проверяются в P3; критерии стабильности 1.0 сохраняются.

Все условия ниже открыты. Завершённые частные проверки остаются доказательствами внутри них, но не заменяют проверку оставшейся части.

Этот документ не разрешает исключить платформу или ослабить ограничения для закрытия P1. Изменение поддерживаемой матрицы требует отдельного явно принятого решения.

## Нагрузочная приёмка E07

Это конечная проверка прототипа, а не обещание производительности рабочего продукта и не многосуточное испытание.

- Три независимых прогона GitHub Linux CI по 15 минут с настоящими PostgreSQL, сессиями, dispatcher и изолированным WASM. Каждый прогон: три пятиминутные фазы с 1, 2 и 8 конкурентными клиентами; первая минута каждой фазы — прогрев, четыре остальные — измерение. Перегрузка должна приводить к предусмотренному отказу, а не увеличению квот.
- До запуска фиксируются SHA трёх репозиториев, версии, параметры runner, набор данных, seed, расписание запросов и ожидаемые ошибки. В смеси присутствуют queries, уникальные мутации, повторы с тем же ключом, конфликты payload/ревизий, отмены, изменения ACL/членства и независимые команды другого экземпляра. Отдельный контролируемый случай проверяет отзыв полномочий; случайный график не заменяет существующие детерминированные гонки.
- Гостевой план и операции ядра должны соответствовать объявленным capability. Запрещены специальное увеличение deadline/квот и отключение проверки прав. Измеряются p50/p95/p99, пропускная способность, ошибки по кодам, ожидание БД, RSS/пиковая память и cgroup, активные процессы и резервирование, размер данных/квитанций/outbox.
- Успех: нет необъяснённых ошибок, race-отчётов, зависаний, нарушения ACL, частичных записей или дубликатов. Все принятые команды завершаются в заданных бюджетах; перегрузка и конфликты имеют ожидаемые коды. После прекращения нагрузки активные вызовы и резервирование равны нулю, worker отсутствуют, группы вызовов очищены, пул не превышает настроенный максимум, новая контрольная команда успешна.
- Суммарный бюджет ProcessHost остаётся 512 МиБ, бюджет worker — 256 МиБ; процесс сервера измеряется отдельно. RSS сервера не объявляется ограниченным этими квотами. Необъяснимый рост ресурсов требует анализа и повторной приёмки, а не усреднения вместе с успешными рядами.
- Накопление состояния ограничивается заранее подготовленными экземплярами и короткими сериями в пределах квот. Ротация тестовых экземпляров и число записей сохраняются в журнале. При достижении лимита отдельно проверяются отказ без частичной записи и доступность другого экземпляра; скрытая очистка квитанций или увеличение лимитов запрещены.
- Численные распределения задержек публикуются как исходный профиль. Порог 20% из миграционной приёмки нельзя применять к несопоставимым путям: сравнение адаптеров со старым RPC относится к P2/P4/P5. Абсолютные продуктовые бюджеты фиксируются до соответствующей выпускной приёмки; успешный P1 не является SLA.

Длительные смешанные испытания рабочего транспорта, рассылки и lifecycle остаются обязательными для P3. Они не заменяются этим ограниченным профилем.

## Порядок оставшейся работы

1. E01/E02: полный набор контрактов, ошибки и повторы, жизненный цикл и правила хранения.
2. E03: закрыть техническую неопределённость macOS и границы прав Windows; зафиксировать платформенное решение до признания runtime готовым.
3. E04/E05: проверка доверия, SDK и каркасы четырёх репозиториев.
4. E06: формы и contributions, нативная матрица UI.
5. E07: ограниченная нагрузка на выбранном кандидате, сводный отчёт и финальная проверка всех семи условий.

Если новый тест обнаруживает нарушение обязательного контракта, исправление остаётся в P1. Новые продуктовые функции получают собственный пункт P2/P3, а не бесконечно расширяют аварийный стенд.
