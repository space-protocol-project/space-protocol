# P1: медленный HTTP/2-получатель и параллельные потоки

6 ноября 2026 года. Продолжение [отмены потока и сбоев записи](SPACE-PLUGINS-P1-DELIVERY-FAILURES.md) для прямого `ExtensionP1ManagedService.NewDeliveryHandler`.

## Настоящее управление потоком

Стенд открывает одно проверенное TLS-соединение с согласованным ALPN h2 и отправляет настоящие HTTP/2-кадры через Framer из уже используемого golang.org/x/net. SETTINGS_INITIAL_WINDOW_SIZE устанавливается в 0 либо 1. Клиент продолжает читать служебные кадры, но не выдаёт WINDOW_UPDATE медленному потоку. Ожидание возникает в штатном HTTP/2-транспорте Go; обёртка writer и искусственная ошибка записи не используются.

Runtime новых сценариев управляемый тестовый. Авторизация, снимок допуска, PostgreSQL, SQL-блокировки, сериализация ответа, TLS и HTTP/2 — настоящие. Версия x/net не изменена; зависимость стала прямой из-за использования в тестовом клиенте.

## Матрица

| Сценарий | Поведение медленного потока | Ожидаемый результат |
| --- | --- | --- |
| zero_window | Окно 0, ни один байт тела не разрешён | Штатный двухсекундный срок записи обрывает только этот поток, SQL-блокировки освобождаются |
| one_byte | Окно 1, получен только первый байт, дальнейшего WINDOW_UPDATE нет | Неполный ответ завершается сбросом потока, отзыв доступа получает блокировки |
| resume | Окно 0, затем WINDOW_UPDATE до истечения срока | Полный документ доставляется, транзакция отправки освобождается и отзыв завершается |

Во всех трёх сценариях поток 1 сначала достигает отправки заголовков. Поток 3 на том же TLS-соединении получает отдельное окно и должен вернуть полный корректный документ, пока обработчик потока 1 ещё не завершён. Затем изменение ACL наблюдается в pg_stat_activity как ожидающее SQL-блокировку потока 1. При тайм-ауте проверяются RST_STREAM, отсутствие полного тела и END_STREAM успешного ответа, завершение обработчика и ожидавшего отзыва. При возобновлении проверяется полный документ.

После освобождения блокировок поток 5 на том же соединении должен получить NotFound по обновлённому ACL. GOAWAY считается ошибкой теста: закрытие всего соединения не может заменить независимое завершение потока. Журнал содержит release_ms от начала запроса до завершения отзыва; это диагностическое время с работой БД и планированием runner, а не отдельный сетевой норматив.

## Приёмка

Три сценария обязательны по пять раз с race detector и повторяются в изолированном этапе; skip/fail в выбранных Delivery-тестах запрещены. Сохраняются прежние проверки TLS, отмены, COMMIT, квитанций, WASM и аварий PostgreSQL.

[Полный GitHub CI 42217041497](https://github.com/space-protocol-project/space-server/actions/runs/42217041497) успешен для `fc6d604a65e9e727732f7d55d356f3822e364f9c`: **2/2 задания**, core и database-faults. Все три новых сценария прошли по пять раз с race detector и по одному разу в изолированной выборке. Delivery — 201 запись pass без skip/fail; изолированный этап — 276 pass без skip/fail; общие test/race — по 818 pass и 83 ожидаемых skip специальных стендов. Worker-crash — 21 pass, аварии PostgreSQL — 26 pass. Числа включают родительские тесты и итоги пакетов, а не только независимые сценарии.

В пяти повторах release_ms составил 2022–2031 мс для нулевого окна, 2023–2024 мс после одного байта и 76–78 мс при возобновлении передачи. Это подтверждает штатное ограничение ожидания записи в двух первых случаях; результат не является нагрузочным нормативом или сетевой задержкой в отрыве от БД.

Прошли vet, mod verify и govulncheck; полный workflow успешен с первой попытки. Проблем рабочей логики в этой матрице не обнаружено, исправления не потребовались. Локальные Windows test/vet подтвердили компиляцию и анализ, но без тестовой БД не являются приёмкой сетевых сценариев. Group/Publish/Versions сохраняют отдельные стенды и здесь не переаттестуются.

[Исходные журналы и метаданные](p1-results/2026-11-06-delivery-flow/) сохранены без изменения байтов; [SHA256SUMS](p1-results/2026-11-06-delivery-flow/SHA256SUMS) фиксирует их целостность.

## Границы

Проверяется медленный получатель на уровне окна отдельного HTTP/2-потока. Исчерпание общего окна соединения, остановка чтения TCP со заполнением буферов ОС, нагрузка многими медленными клиентами, внешние прокси и глобальные квоты памяти не принимаются этим стендом. Параллельный запрос проверяется до постановки исключительного отзыва в очередь: после неё ожидание новых запросов к тому же ACL допустимо и не считается сетевой блокировкой.

Автоматическое подключение к рабочему серверу, прежний gRPC-мост и нативный LPAC-транспорт остаются открытыми. P1/E03 целиком не закрыты.
