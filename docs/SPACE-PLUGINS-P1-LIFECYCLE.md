# P1 / E01: кандидат жизненного цикла установки

Статус на 1 ноября 2026 года: контракт и изолированный прототип прошли GitHub CI. Это часть E01, а не рабочий реестр установок и не завершение P1.

## Область контракта

`space.lifecycle.p1` задаёт решения доверенного ядра для одной установки. Версия пакета общая для всех её экземпляров: закрытие входа и подсчёт активных вызовов относятся ко всей установке. В прототипе один `Coordinator` представляет такую область; автоматическая группировка экземпляров ещё не реализована.

Исходные материалы: [JSON Schema](extensions/p1/lifecycle.schema.json), [41 общий сценарий](extensions/p1/lifecycle.json), пакет `experiments/extensions/lifecycle` в сервере. Схема описывает наблюдение и решение, не публичный запрос управления. Расширение не может само заявить роль владельца, наличие разрешений или готовность резервной копии.

Наблюдение содержит состояние, действие, роль `owner`/`system`, результат проверки полномочий, текущую и ожидаемую ревизии, число активных вызовов и свидетельства проверки пакета, совместимости, согласованных разрешений, копии и миграции. Эти свидетельства должен формировать адаптер ядра для конкретных digest/плана/ревизии. Прототип не проверяет подпись пакета, сессию, права владельца или содержимое копии; это явные зависимости будущей интеграции E01/E04/P2/P3.

## Переходы

| Действие | Исходное состояние | Результат | Кто инициирует | Дополнительные условия |
| --- | --- | --- | --- | --- |
| verify | staged | verified | system | Пакет проверен, активных вызовов нет |
| install | verified | installed | owner | Пакет проверен, совместим, разрешения согласованы; активных вызовов нет |
| enable | installed, disabled | enabled | owner | Те же проверки, активных вызовов нет |
| disable | enabled | disabling | owner | Сразу закрыть вход и отменить активные вызовы |
| finish_disable | disabling | disabled | system | Каждый активный вызов фактически завершён |
| begin_upgrade | disabled | upgrading | owner | Целевой пакет проверен, совместим, разрешения согласованы, копия готова; активных вызовов нет |
| finish_upgrade | upgrading | disabled | system | Проверки целевого пакета действуют, миграция/checkpoint и проверка результата завершены; активных вызовов нет |
| fail_upgrade | upgrading | failed | system | Вход остаётся закрытым, активные вызовы отменяются |
| quarantine | Любое, кроме quarantined и removed | quarantined | system | Закрыть вход и отменить активные вызовы |
| recover | failed, quarantined | disabled | owner | Пакет/права/совместимость повторно проверены, восстановленный checkpoint подтверждён; активных вызовов нет |
| remove | installed, disabled, failed, quarantined | removed | owner | Активных вызовов нет; данные сохраняются |

Промежуточное `disabling` уточняет исходную последовательность из [спецификации](SPACE-PLUGINS.md#14-жизненный-цикл-и-обновления). Из `removed` нет обратного перехода: новая установка получает отдельную идентичность. После обновления или выхода из карантина установка остаётся выключенной; включение требует отдельного действия владельца. Восстановление резервной копии также не должно автоматически включать код; API restore этот прототип не вводит.

Успешный переход повышает ревизию на один. Разрешён диапазон 1…2147483646; на верхней границе переход отклоняется без переполнения. Повтор со старой ревизией возвращает `Aborted`, не считается новой командой и не изменяет состояние. Это optimistic concurrency, а не новый механизм идемпотентности административных RPC.

## Отказы и сохранность

Порядок проверок: корректность наблюдения → полномочия/роль → ожидаемая ревизия → допустимость перехода и свидетельства. Неверная версия, действие, состояние, диапазоны или число вызовов дают `InvalidArgument`; отсутствие полномочий — `PermissionDenied`; устаревшая ревизия — `Aborted`; неподходящий переход, незавершённый drain или недостающие свидетельства — `FailedPrecondition`.

При отказе состояние и ревизия не меняются, отмена не выполняется. `admission` и `cancel_active` в решении применяются только при `code=OK`; координатор проверяет это до изменения состояния. Отказавшемуся административному действию нельзя позволять выключить исправное расширение.

Все решения имеют `preserve_data=true`. Удаление здесь относится к состоянию установки/кода; прототип вообще не выполняет файловых или SQL-удалений. Очистка содержимого — отдельный подтверждаемый контракт. Журналы идемпотентности, квитанции, outbox и сохранённые данные не становятся доступными для очистки из-за disable/quarantine/remove.

## Прототип координатора

`Begin` допускает вызов только в `enabled`, при живом родительском контексте и числе вызовов менее 128. Предел ограничивает внутренний учёт прототипа и не увеличивает существующие квоты runtime/dispatcher. Он возвращает контекст отмены и однократно действующее освобождение вызова. `Apply` сериализует переход с выдачей допуска; состояние, ревизия и число активных вызовов берутся из координатора, а не из переданного наблюдения.

Disable и quarantine отменяют выданные контексты. Вызов остаётся активным до `release`, даже если отмена уже доставлена. Поэтому зависший worker не позволяет завершить выключение, обновление или удаление. После ограниченного ожидания управляющая оболочка должна оставить вход закрытым и сообщить отказ; прототип не вводит ожидание без срока, не повышает deadline runtime и не подменяет фактическое завершение обнулением счётчика.

Проверяются гонки допуска с карантином, два перехода с одной ожидаемой ревизией, отмена при выключении, запрет преждевременного завершения drain, повторный release, лимит вызовов, отменённый родитель и отсутствие побочных эффектов отказа в правах. 41 сценарий общего контракта проверяет разрешённые переходы и отрицательные условия. Отдельно схема отклоняет неизвестные поля, неверные типы, версии и диапазоны.

## Результаты CI

Оба workflow завершились с `conclusion=success`:

- [Контракты 41310698519](https://github.com/space-protocol-project/space-protocol/actions/runs/41310698519), ревизия `c141e2d95c84abce6470d37a30201322aa962d59`: шесть схем и их примеры, прежние отрицательные проверки, 41 общий сценарий lifecycle и отрицательные проверки вложенных полей/типов/пределов/сохранения данных.
- [Прототип 41310733329](https://github.com/space-protocol-project/space-server/actions/runs/41310733329), ревизия `ef2057d2dbadeb7b4e43d4066c55a755087872c5`: обычный и race-прогон экспериментального модуля — по 112 успешных результатов и 16 штатных пропусков сценариев изоляции/службы без отдельного привилегированного окружения. Ещё четыре пакета команд не содержат тестов. Эти пропуски не считаются новой приёмкой E03.
- Целевой lifecycle повторён 25 раз с `-race`: 1200 успешных результатов вместе с родительским тестом общих сценариев, без пропусков и ошибок.
- Форматирование, `go vet ./...`, `go mod verify` и `govulncheck ./lifecycle` успешны; уязвимостей в вызываемом коде нового пакета не найдено. Проверялся экспериментальный модуль, рабочее ядро не менялось.
- [Сводка, исходные журналы и метаданные](p1-results/2026-11-01-lifecycle/summary.json) сохранены с [SHA-256](p1-results/2026-11-01-lifecycle/SHA256SUMS). Последующие коммиты документации не меняют проверенные исходники. Локальные сборки и тесты не запускались.
