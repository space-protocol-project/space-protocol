# Система расширений Space и план перехода

Статус: проект спецификации от 27 октября 2026 года. Описывает целевую архитектуру, ещё не реализованную систему плагинов и критерии её выпуска. Реестр работ и milestones: [TODO](../TODO.md). Существующие API и данные остаются действующими до прохождения соответствующего этапа миграции.

Space предоставляет пустое пространство с идентичностью, участниками, правами и управлением. Чаты, Комнаты, Обсуждения и Лента подключаются как расширения. Разработчик может добавить собственный тип раздела, его страницы и элементы «Обзора» без изменения исходников сервера и приложения, если интерфейс укладывается в поддерживаемый набор компонентов.

## 1. Решение о последовательности выпусков

Рекомендуемый порядок: завершение выбранных исправлений 0.7.x → 0.8.0 «Сопряжение устройств и зашифрованные резервные копии» → 0.9.0 «Основа расширений» → 0.10.0 «Обсуждения и Лента как расширения» → 0.11.0 «Чаты и Комнаты как расширения» → 1.0 «Стабильное ядро и API расширений».

Это целевые версии приложения. Runtime выпускается независимо; для каждого выпуска фиксируется проверенная пара версий, схема БД, профиль голоса и версии API. Номера схем будущих выпусков не резервируются заранее. Переход 0.9 → 0.10 корректен для SemVer.

0.8.0 не следует перегружать WASM и массовой миграцией содержимого: одновременно изменять восстановление идентичности, хранение данных и способ исполнения прикладной логики слишком трудно проверять и откатывать. Надёжное восстановление должно предшествовать переносу существующих пространств. Ранее отложенное начало реализации 0.8.0 не считается автоматически возобновлённым этой спецификацией.

До 0.8.0 допустимы проектирование контрактов, инвентаризация и внутренние адаптеры под выключенным флагом. Они не добавляют публичную установку плагинов, не меняют формат пользовательских данных и не блокируют выпуск 0.8.0. Полный публичный ABI и его совместимость стабилизируются к 1.0, а не объявляются готовыми в экспериментальном 0.9.0.

| Этап | Обязательный результат | Условие выпуска |
| --- | --- | --- |
| 0.8.0 | Сопряжение и зашифрованные резервные копии в существующей архитектуре | Проверены восстановление, отзыв устройства, защита ключей и границы MLS; открытые ограничения названы явно |
| 0.9.0 | Реестр, встроенные адаптеры четырёх функций, серверный WASM и внешний плагин «Опросы» | Новый раздел и элемент обзора устанавливаются без пересборки клиента и сервера; пройдены изоляция и восстановление |
| 0.10.0 | Обсуждения, затем Лента используют общие контракты и WASM-обработчики | Сохранены все выпущенные функции, ссылки, ACL и данные; выполнен перенос существующего пространства |
| 0.11.0 | Чаты, затем управление Комнатами используют систему расширений | Очереди, MLS, голос и старые клиенты не регрессируют; проверена миграция каждого типа |
| 1.0 | Версионируемый публичный SDK и поддерживаемая матрица совместимости | Аудит границ доверия, нагрузка, восстановление и документированная политика поддержки |

## 2. Термины и идентификаторы

| Объект | Назначение |
| --- | --- |
| Package | Неизменяемый пакет: `plugin_id`, версия, издатель, digest, WASM, схемы и ресурсы |
| Installation | Разрешённая установка конкретного пакета в пространстве; версия и выданные разрешения |
| Instance | Экземпляр расширения с отдельными настройками, данными и состоянием |
| Section | Раздел навигации, связанный с экземпляром, channel и view |
| Contribution | Страница, действие, элемент обзора или провайдер поиска, объявленный расширением |
| Host capability | Разрешённая функция ядра; декларация в пакете сама по себе права не выдаёт |
| Adapter | Встроенная реализация тех же контрактов поверх существующего кода |

`plugin_id` имеет пространство имён издателя, например `org.example.polls`. Официальные пакеты используют зарезервированный префикс `space.*`. Идентичность издателя связывается с ключом; похожее имя не даёт право обновлять чужой пакет. Названия элементов локализуются и не являются идентификаторами.

Одна установка может иметь много экземпляров: «Поддержка» и «Идеи» используют один пакет Обсуждений, но разные ACL и данные. Пакет кешируется по digest, а состояние изолируется по `(space_id, installation_id, instance_id)`. Чужой `space_id` из тела команды никогда не меняет доверенный контекст вызова.

Существующий `Channel` остаётся контейнером доступа. У него уже есть несколько `View`; миграция не сводит их к одному разделу. Создаётся явное отображение `(channel_id, view_id) → instance_id`. Раздел навигации может представлять конкретный view, сохраняя исходный channel. Несколько коллекций внутри канала не считаются реализованными одним появлением экземпляров.

## 3. Границы ядра

| Ядро и специализированные службы | Плагин |
| --- | --- |
| Идентичность пространства, устройства, сессии, recovery, сопряжение | Прикладные правила своего раздела |
| Участники, роли, ACL, блокировки и аудит доступа | Собственные действия и дополнительные ограничения |
| Хранилище, транзакции, файлы, квоты, резервное копирование | Схемы своих объектов, индексы, правила хранения |
| Журнал событий, доставка, повтор, фоновые задания | Обработчики команд и разрешённых событий |
| Оболочка Flutter, навигация, рендерер, локализация | Декларации страниц, форм и элементов обзора |
| WebRTC, медиатранспорт, TURN, работа с устройствами | Политика комнат, приглашения в комнату, расписания |
| Клиентская криптография MLS и защищённое хранение ключей | Для MLS только разрешённые метаданные и зашифрованные конверты |

Ядро не зависит от наличия Чатов, Комнат, Обсуждений или Ленты. Управление пространством, установка расширений, восстановление и диагностика доступны при нуле установленных прикладных пакетов. Ошибка плагина не должна блокировать вход владельца и его отключение.

Официальные плагины используют публичные прикладные API. Временные адаптеры старых таблиц допускаются только как обозначенный механизм миграции с критериями удаления. Доступ к секретам и медиатранспорту не становится частью универсального SDK.

## 4. Модель исполнения WASM

Начальный кандидат — wazero в Go. До закрепления версии нужен прототип на всех платформах runtime с проверкой отмены бесконечного цикла, ограничений памяти, компиляции и вызовов хоста. Версию, лицензию и поддерживаемые цели компиляции фиксирует отдельное решение по результатам прототипа.

Первый профиль использует Core WebAssembly и собственный минимальный ABI `space_plugin_v1`. Он не обещает поддержку Component Model, WASI Preview 2 или произвольных бинарников WASM. WASI по умолчанию не предоставляется; необходимые функции времени, случайности и журналирования выдаёт хост. WASM стартовая функция также ограничивается бюджетом и не получает прикладных полномочий.

Модуль компилируется с кешированием по digest; память вызовов не разделяется между пространствами и пользователями. Безопасная начальная реализация создаёт отдельный экземпляр WASM на вызов, переиспользуя скомпилированный код. Пул экземпляров допустим только после доказанной очистки памяти и контекста. Источник истины — постоянное хранилище, не глобальные переменные WASM.

При первом внедрении обработчики вызываются синхронно в пределах короткого бюджета. Длительные операции выполняются пошаговыми заданиями с курсором. Прямые потоки, сокеты и собственные бесконечные циклы обслуживания запрещены.

## 5. Формат пакета и проверка установки

Пакет — архив с `manifest.json`, `server.wasm`, `schemas/`, `ui/`, `locales/`, `assets/`, лицензией и списком файлов с SHA-256. Подписанный индекс покрывает точные байты манифеста и файлов; подпись хранится отдельно от подписываемого индекса. Архивные метаданные не определяют доверие.

Установщик отвергает обход путей, абсолютные пути, ссылки, повторяющиеся имена, коллизии регистра, слишком большие распакованные файлы, недопустимые импорты WASM и несовместимые версии. Содержимое загружается по digest, а не по изменяемому URL `latest`.

Пример проектируемого манифеста:

```json
{
  "manifest_version": 1,
  "plugin_id": "org.example.polls",
  "version": "1.0.0",
  "host_api": "space.plugin.v1",
  "wasm_abi": "space_plugin_v1",
  "ui_api": "space.ui.v1",
  "entrypoint": "server.wasm",
  "data_schema": 1,
  "permissions": ["storage.own", "events.own"],
  "required_components": ["list.v1", "form.v1", "button.v1"],
  "commands": {"vote": "schemas/vote.json"},
  "queries": {"recent": "schemas/recent.json"},
  "contributions": {
    "sections": [{"id": "polls", "title_key": "polls.title", "view": "ui/polls.json"}],
    "overview": [{"id": "recent", "query": "recent", "view": "ui/recent.json"}]
  }
}
```

Обязательные свойства, допустимые типы и пределы манифеста фиксируются машиночитаемой схемой на этапе P1. Неизвестные обязательные версии отклоняются; неизвестное необязательное поле не даёт полномочий. Конфигурация экземпляра отделена от манифеста. Секретные настройки хранятся через хост и никогда не попадают в UI-описание.

Владелец может установить собственный пакет без публичного магазина. Для неизвестного ключа показываются издатель, digest и запрошенные права; доверие закрепляется явно. Локальный режим разработки с неподписанными пакетами отделён от обычной установки. Подпись подтверждает происхождение, но не безопасность поведения.

### Установка из Git репозитория

Дополнение от 29 октября 2026 года. Установка расширения по URL Git-репозитория входит в P3 и целевой выпуск 0.9.0. Магазин и привязка к GitHub не обязательны: поддерживаются совместимые публичные и приватные репозитории по HTTPS. SSH — отдельный последующий транспорт, не требование первой версии.

Владелец открывает «Расширения → Установить из Git», указывает URL, tag/branch/commit и путь расширения внутри репозитория. Путь позволяет размещать несколько расширений в одном репозитории. По умолчанию предлагается явно выбранный тег выпуска; ветка допустима, но устанавливается её конкретный commit. Перед подтверждением отображаются источник, полный commit ID, версия, издатель, разрешения, совместимость и способ получения пакета. Установка всегда выполняется на сервере выбранного пространства, а не на устройстве участника.

Предусмотрены два способа получения пакета:

| Способ | Поведение |
| --- | --- |
| Готовый пакет в репозитории | По выбранному commit и пути загружается готовый подписанный архив либо каталог пакета с подписанным индексом, WASM и ресурсами; это обязательный способ для 0.9.0 |
| Сборка исходников | Отдельный изолированный сборщик создаёт пакет из закреплённого commit; включается только при наличии проверенного профиля сборки. При отсутствии сборщика UI сообщает об этом, не запускает скрипты на рабочем сервере |

Репозиторий только с исходниками не считается устанавливаемым в первом способе. Автор может собирать пакет в своём CI и сохранять готовое содержимое в отдельной ветке или каталоге репозитория. Загрузка release assets через API конкретного Git-хостинга — последующее удобство, не обязательная зависимость Git-установки. Автоматического небезопасного перехода от готового пакета к сборке нет.

Каждая установка сохраняет `source.kind=git`, нормализованный URL без секретов, запрошенный ref, полный разрешённый commit ID с форматом object ID, относительный путь, способ получения пакета, digest пакета и ключ издателя. Ref нужен для проверки обновлений, commit — для фиксации исходного дерева, digest — для идентификации установленных байтов. Отдельный подписанный документ происхождения связывает пакет с commit и профилем сборки; одного совпадения версии в манифесте недостаточно. Подпись commit/tag не заменяет проверку пакета и доверие издателю.

Получение источника идёт в ограниченную временную область с отдельной конфигурацией Git: без пользовательских hooks, credential helpers, внешних фильтров, внешних transport helpers и выполнения файлов репозитория. Submodules и Git LFS в первом профиле отклоняются с понятной ошибкой; рекурсивная загрузка зависимостей не включается автоматически. Путь расширения проверяется относительно выбранного дерева; абсолютные пути, выход через `..` и ссылки за его пределы запрещены. Ограничиваются время, трафик, размер объектов, число файлов и распакованный объём; огромная история не скачивается без необходимости.

Публичный источник не получает доступ к loopback, link-local, metadata endpoints и внутренней сети через URL, DNS или redirect. Проверка адресата повторяется при разрешении адреса и каждом перенаправлении. Для собственного Git-сервера во внутренней сети администратор может явно разрешить конкретный адресат политикой пространства/сервера; это не снимает остальные ограничения и не разрешает весь диапазон адресов. Доступ транспортного загрузчика к сети не передаётся WASM-плагину.

Для приватного репозитория используются отдельные учётные данные только на чтение выбранного источника. Они хранятся в секретном хранилище ядра, не включаются в URL, аргументы журналируемых команд, манифест, UI и логи. При смене origin/redirect учётные данные не пересылаются автоматически. Плагин и сборщик их не получают: зависимости при необходимости загружает отдельный ограниченный посредник. После переноса пространства доступ к источнику можно настроить заново; уже сохранённый пакет остаётся пригоден для восстановления без Git.

Сборка из исходников требует отдельной границы изоляции: у неё нет базы пространства, ключей, сокета контейнерного движка, домашней папки владельца или рабочего каталога сервера. Toolchain и зависимости закреплены по версиям/digest, сеть по умолчанию выключена, заданы лимиты CPU, памяти, времени и диска. Результат повторно проходит обычную проверку пакета. Если пакет подписывает локальный сборщик, UI показывает именно его происхождение и доверие, а не выдаёт такую подпись за подпись автора. Воспроизводимость подтверждается повторной сборкой, а не самим наличием commit ID.

Проверка обновлений разрешает ref в новый commit и готовит предложение; работающая установка не делает `git pull` и не меняется молча. Даже перенос существующего тега считается новым кандидатом. До применения показываются старый/новый commit и digest, миграции и изменения разрешений. Для закреплённого commit переход на другой commit выбирается явно. Недоступный/удалённый источник, отказ авторизации или ошибка сборки не отключают текущий пакет. Смена URL или ключа издателя требует нового решения о доверии.

API дополняется операциями `ResolveGitSource`, `PrepareGitInstall`, `CheckGitUpdate` и `ApplyPreparedInstall`. Подготовка возвращает ограниченный по времени идентификатор с точными commit/digest, областью пространства и principal. Применение использует подготовленные проверенные байты и повторно проверяет права; перемещение ref между просмотром и установкой не подменяет пакет. Фоновая задача подготовки отменяема, имеет безопасный журнал и не активирует код. Далее используется общий lifecycle установки и обновления из раздела 14.

Критерии Git-установки дополняют A01–A26:

| ID | Сценарий | Проверяемый результат |
| --- | --- | --- |
| G01 | Публичный репозиторий и подкаталог | Раздел и обзор установлены по конкретному commit без пересборки Space |
| G02 | Приватный репозиторий | Учётные данные не доступны UI, WASM, сборщику и журналам |
| G03 | Перемещение branch/tag после предпросмотра | Применён только подготовленный commit/digest либо явный отказ |
| G04 | Redirect, внутренний адрес, submodule, LFS, обход пути | Действует политика источника, нет скрытых сетевых запросов и выхода за каталог |
| G05 | Источник только с исходниками | Без сборщика понятный отказ; со сборщиком проверена изоляция и результат |
| G06 | Обновление с новыми правами или неверной подписью | Нет тихого расширения полномочий и замены работающего пакета |
| G07 | Источник удалён, сеть недоступна, сборка прервана | Текущая версия работает, восстановление использует сохранённые байты |
| G08 | Чрезмерный размер или время загрузки/сборки | Операция отменена в бюджете, управление пространством доступно |

G01–G08 обязательны для доступных способов установки в 0.9.0; для G05 отсутствие сборщика проверяется как штатный отказ. Включение сборки исходников дополнительно требует проверки её изоляции и воспроизводимости на поддерживаемых платформах.

## 6. ABI и функции хоста

Предлагаемые экспорты: `space_alloc(length)`, `space_free(pointer,length)`, `space_handle(pointer,length)`. Последний возвращает упакованные указатель и длину ответа в `i64` (старшие 32 бита — указатель, младшие — длина). Хост проверяет переполнение, границы памяти и размер до каждого чтения. Вход выделяет модуль по вызову хоста; результат принадлежит модулю до `space_free`. Ошибка WASM уничтожает экземпляр, а не продолжает работу с повреждённым состоянием.

Сообщения ABI — UTF-8 JSON со схемой, без повторяющихся ключей, NaN и бесконечностей. 64-битные последовательности и ревизии передаются десятичными строками. Внешний транспорт остаётся protobuf/Connect; хост преобразует проверенный конверт в ABI. Конкретные сигнатуры импортов и тестовые бинарники фиксируются до публикации SDK, без угадывания ABI по языку компилятора.

| Группа | Доступные операции | Ограничение |
| --- | --- | --- |
| `storage` | get, query, put, delete, compare_revision | Только собственные коллекции и текущая транзакция |
| `events` | emit | Только объявленные типы; публикация после commit |
| `assets` | attach, metadata, request_download | Квоты, ACL объекта и проверяемые ссылки; без путей ФС |
| `notifications` | enqueue | Получатели проверяются ядром, текст не попадает в push по умолчанию |
| `jobs` | schedule, cancel | Квоты, ограниченный principal задания, дедупликация |
| `access` | check | Может сузить доступ, но не расширить права ядра |
| `clock`, `random`, `log` | now, bytes, structured_log | Бюджеты и исключение секретов из журналов |
| `media` | request_join, leave, read_presence | Только через медиаслужбу и с повторной проверкой ACL |

Функции сети и межплагинные вызовы в первой версии отсутствуют. Их добавление требует отдельной модели разрешений: адресаты, ограничения исходящих запросов и SSRF, сроки, циклы зависимостей и предотвращение повышения привилегий через посредника.

## 7. Внешний API и обработка команды

Проектируемые методы: `ListInstallations`, `GetInstallation`, `InstallPackage`, `CreateInstance`, `UpdateInstance`, `SetEnabled`, `PlanUpgrade`, `ApplyUpgrade`, `GetContributions`, `ExecuteCommand`, `ExecuteQuery`, `SubscribeInstance`. Управляющие методы требуют отдельных административных разрешений. Список пакетов владельца и список доступных пользователю разделов — разные ответы.

```json
{
  "instance_id": "opaque-instance-id",
  "action": "vote",
  "request_id": "opaque-request-id",
  "expected_revision": "12",
  "payload": {"poll_id": "opaque-poll-id", "option_id": "option-a"}
}
```

Хост строит контекст из проверенной сессии: пространство, principal, устройство, scope, экземпляр, действующие разрешения, версия пакета и deadline. Поля `actor`, `roles` или `space_id` из payload не заменяют контекст. Запрос проверяется по схеме команды до входа в WASM.

Порядок: проверка доступа → проверка дедупликации → транзакция → вызов плагина → проверка результата → commit данных, результата команды и outbox → ответ. `request_id` уникален в области пространства, principal, экземпляра и действия; повтор с другим хешем payload даёт конфликт. После отзыва прав даже повтор ранее успешной команды не раскрывает сохранённый результат.

Идемпотентность поддерживается минимум в пределах объявленного окна повторов; сервер возвращает его длительность. Клиент после истечения окна сначала сверяет состояние. Команды создания дополнительно используют стабильный ID создаваемого объекта, чтобы долгий offline не породил дубликат.

Ошибки имеют стабильные коды: `INVALID_ARGUMENT`, `PERMISSION_DENIED`, `NOT_FOUND`, `CONFLICT`, `PLUGIN_DISABLED`, `UNSUPPORTED_VERSION`, `RESOURCE_EXHAUSTED`, `DEADLINE_EXCEEDED`, `UNAVAILABLE`. Подробности ошибки не раскрывают чужие объекты или стек сервера. Для недоступного объекта применяется единая политика сокрытия существования.

## 8. Хранилище и целостность

Системные записи: packages, installations, instances, contributions, jobs, command_results и audit. Данные плагина хранятся в именованных коллекциях с версией схемы, ID объекта, ревизией, областью видимости и объявленными индексами. Произвольный SQL, DDL, DSN и доступ к таблицам других расширений запрещены.

Запросы используют ограниченный язык фильтров и индексов, keyset-пагинацию и максимальный размер страницы. Неиндексированный запрос не превращается в неограниченный обход базы. Объект может быть видим всему разделу, конкретному principal или модераторам; метку доступа проверяет хост. Для личного избранного и жалоб обязательны отдельные области приватности.

Одна команда выполняется в одной транзакции хоста. Сетевые операции и необратимые эффекты внутри транзакции запрещены. При тайм-ауте, trap, конфликте ревизии или ошибке проверки результата изменения откатываются. Уведомления и задания публикуются из outbox после commit; доставка повторная, обработчики идемпотентны.

Плагин может читать только то, что доступно его контексту вызова. Фоновые задания используют явно ограниченную служебную идентичность, а не owner. Расширение, имеющее право обрабатывать незашифрованный текст своего раздела, может его видеть: установка такого кода является доверием к его издателю. E2EE не обещается для этих данных.

## 9. События и синхронизация

Конверт события содержит `event_id`, `instance_id`, тип, версию схемы payload, последовательность, ревизию объекта и время. Порядок гарантируется в пределах экземпляра; общего порядка между экземплярами нет. Subscribe использует курсор и ограниченный журнал; при истёкшем курсоре сервер требует snapshot и последующее продолжение.

Чтение snapshot и граница журнала согласованы. Отзыв доступа проверяется при подписке, выдаче каждой порции, replay, поиске, скачивании файла и построении обзора. Не разрешается отправить секретное событие только потому, что подписчик имел права при открытии соединения.

Клиент хранит очереди команд по идентичности пространства, principal, экземпляру и версии схемы команды. При несовместимом обновлении очередь не отбрасывается и не переинтерпретируется: требуется объявленный преобразователь либо явная ошибка с сохранением черновика. Поздние ответы старой сессии не применяются к новой.

## 10. Разрешения и изоляция

Эффективные полномочия — пересечение политики сервера, выданных установке возможностей, текущих прав пользователя, ACL раздела/объекта и scope устройства. Плагин может добавить ограничение, но не отменить любой из этих уровней. Идентификаторы и данные UI недоверенные.

В первой версии установка доступна владельцу или явно назначенному администратору расширений. Пользователь не может установить серверный код через сообщение, вложение или открытие ссылки. Дополнительные разрешения при обновлении требуют отдельного согласия; существующая версия продолжает работать до решения владельца.

Исходные бюджеты прототипа: память 64 МиБ на вызов; вход/выход до 1 МиБ; UI до 256 КиБ и 1 000 узлов; обычный вызов до 2 секунд; элемент обзора до 500 мс; до 4 параллельных вызовов одного экземпляра. Это стартовые параметры испытаний, не измеренные гарантии производительности. Общие квоты сервера и пространства ограничивают сумму вызовов. Клиент имеет собственные пределы, которые сервер не может повысить.

Ограничиваются также компиляция, число функций и импортов, host calls, запросы БД, логи, задания, глубина UI и размер архивов. Отмена должна завершать и WASM, и операции хоста. Повторяющиеся сбои переводят экземпляр в карантин; владелец видит причину и может отключить его. Сбой всего процесса и уязвимости среды исполнения остаются отдельными рисками: изоляция WASM не является абсолютной защитой от всех ошибок хоста.

## 11. Декларативный интерфейс Flutter

Плагин предоставляет проверяемое дерево компонентов и привязки к именованным queries/commands. В версии 1 разрешены ограниченные привязки к полям и простые условия; нет eval, JavaScript, Dart, произвольного HTML и универсального языка программирования в UI. Строки отображаются как текст либо через существующий безопасный Markdown.

Базовые компоненты: страница, секция, текст, список с пагинацией, карточка, форма, поле, выбор, кнопка, вложение, состояние загрузки/ошибки. Предметные компоненты: история сообщений, редактор сообщения, ветка обсуждения, публикация, список участников комнаты. Их доступность и версии объявляет клиент. Рендерер не выбирает привилегии по `plugin_id`.

Каждое действие ссылается на зарегистрированную команду и схему аргументов. Переходы используют типизированные внутренние ссылки, внешние ссылки проходят проверку и открываются по правилам клиента. Запрещено имитировать системные окна входа, выдачи ключей и управления разрешениями внутри плагина. Системная оболочка показывает происхождение раздела.

Тема, локализация, клавиатура, масштаб текста, доступность и адаптивность контролируются клиентом. Изображения идут через проверенные assets с лимитами декодирования; SVG санитизируется или растеризуется. Недоступный обязательный компонент даёт понятное сообщение о несовместимости. Для необязательного элемента допускается объявленный безопасный fallback.

Реестр и загрузка состояния реализуются через Bloc/Cubit; повторяющиеся состояния — Freezed. Рендеринг отделяется от разрешения команд и данных. Сохраняются COG ≤15, цель ≤10, анализ и подходящие проверки; создание универсального «мегавиджета» не допускается.

Произвольные веб-приложения, клиентский WASM и загружаемый Dart-код исключены из первой версии. Это отдельные профили со своей изоляцией, совместимостью платформ и моделью доступа к данным. Декларативный интерфейс не даёт обещания реализовать любой мыслимый визуальный редактор без обновления клиента. Ранее отложенный GenUI этим планом не возобновляется: здесь речь о фиксированной схеме и проверяемом рендерере, без генерации интерфейса моделью.

## 12. Навигация и Обзор

Плагин объявляет страницы, действия и элементы обзора. Для элемента задаются ID, заголовок, query, представление, допустимые размеры, настройки и способ перехода. Пакет не определяет окончательный порядок страницы.

Администратор включает элементы и задаёт раскладку пространства. Личные настройки пользователя могут менять порядок и скрывать элементы в пределах разрешённого набора. Новая версия не возвращает скрытый элемент автоматически и не сбрасывает настройки. Удалённый элемент оставляет запись раскладки, которую можно восстановить при возврате совместимой версии.

| Расширение | Примеры элементов |
| --- | --- |
| Чаты | Непрочитанное, упоминания, последние доступные сообщения |
| Комнаты | Активные комнаты и доступные участники |
| Обсуждения | Новые темы, ответы мне, доступная очередь модерации |
| Лента | Новые публикации, подписки, ответы и упоминания |
| Сторонний пакет | Опросы, задачи, события по собственной схеме |

У каждого элемента независимые deadline, ошибка, повтор и кеш. Ключ кеша включает пространство, principal, экземпляр, конфигурацию, версию пакета и ревизию доступа. Отзыв прав инвалидирует кеш; устаревший ответ не показывается. Скрытые данные не должны проявляться через счётчики, заголовки, аватары и размеры результатов.

Общая сводка нескольких пространств собирается клиентом из отдельных разрешённых ответов. Плагин одного пространства не получает список или содержимое других пространств. В первой версии нет произвольной фоновой загрузки всех элементов: видимые элементы запрашиваются с ограниченной параллельностью.

## 13. Общие функции содержимого

Единая ссылка на объект: идентичность пространства, instance, тип объекта, ID и при необходимости ID/sequence ответа. Сервер разрешает её только после проверки доступа. Старые ссылки на channel и content продолжают работать через таблицу соответствий.

Поиск, избранное, уведомления и экспорт используют провайдеры расширений, но ядро повторно проверяет доступ к возвращённым объектам. Поисковый индекс — производное представление, не источник прав. После скрытия оригинала репост и цитата не должны раскрывать его прежний текст.

Экспорт собственного содержимого сохраняет выпущенные ограничения ADR-060: только доступные собственные данные, без чужого текста, MLS и секретов. Административная резервная копия пространства — другая операция с другими правами. Глобальный пользовательский экспорт не превращается в вызов произвольного экспортёра с полномочиями владельца.

## 14. Жизненный цикл и обновления

Состояния установки: `staged → verified → installed → enabled`; дополнительные состояния `disabled`, `upgrading`, `failed`, `quarantined`, `removed`. Изменения состояния и разрешений аудируются. Выключение закрывает вход новым командам и подпискам, отменяет задания, дожидается ограниченного завершения текущих вызовов; данные сохраняются.

Обновление: загрузить и проверить пакет → сравнить совместимость/права → построить план миграции → получить пригодную резервную копию → остановить записи затронутых экземпляров → выполнить миграцию с checkpoint → проверить данные → атомарно переключить активную версию → выполнить smoke-проверки. При сбое экземпляр остаётся недоступным для записи, а не запускается на частично обновлённых данных.

Для v1 версия пакета закреплена на установку; все её экземпляры переключаются согласованно. Частичное тестирование другой версии возможно в отдельной тестовой установке с копией данных. Зависимости объявлены явно; автоматическая установка транзитивного кода и циклы зависимостей запрещены. В v1 предпочтительны зависимости от host API, а не прямые зависимости плагин → плагин.

Возврат старого бинарника разрешён только при совместимости схемы. Иначе выполняется восстановление согласованной копии: БД, файлов, пакетов, конфигурации и журнала миграции. Возможная потеря записей после точки копии показывается владельцу до восстановления. «Откат одним кликом без потери данных» не обещается.

Удаление кода не удаляет содержимое. Очистка данных — отдельное подтверждаемое действие с описанием объёма, зависимостей и возможности экспорта. Retention и правовые удаления не должны зависеть от того, запускается ли старый WASM: хост умеет очистить область экземпляра по своему каталогу объектов и файлов.

## 15. Резервные копии и восстановление

В снимок входят digest и точные версии пакетов, разрешения, конфигурации, экземпляры, схемы, данные, assets, раскладки и отображение старых ID. Пакеты сохраняются вместе с копией либо в проверяемом локальном хранилище восстановления; недоступность магазина не должна делать копию бесполезной.

Восстановленный пакет сначала проверяется и остаётся выключенным до проверки доверия и совместимости. При отсутствии разрешённой версии данные сохраняются в режиме недоступного расширения; установка случайной новой версии запрещена. Секреты повторно шифруются средствами ядра при допустимом переносе.

MLS-ключи устройств и рабочий ratchet не включаются в серверную копию плагина. Восстановление идентичности, архива истории и рабочего MLS-состояния следует существующему криптографическому профилю. Возврат копии плагина не должен возвращать устройство в старую эпоху MLS или повторно использовать ключи.

## 16. Совместимость и старые клиенты

Независимо версионируются host API, ABI, UI API, схема данных и схемы команд/событий. Версия приложения сама по себе не определяет совместимость. Discovery объявляет поддержку механизма расширений, а авторизованный запрос возвращает разрешённые разделы и требования компонентов.

| Комбинация | Поведение |
| --- | --- |
| Старый сервер и новый клиент | Существующие API и встроенные представления |
| Новый сервер и старый клиент | Старые API четырёх функций обслуживаются адаптерами совместимости |
| Новый тип раздела и старый клиент | Не выдаётся за чат; требуется новый клиент, данные не теряются |
| Выключенный плагин | Понятный статус, отказ записи, сохранённые данные |
| Несовместимый пакет | Отказ активации до миграции/обновления, действующая версия сохранена |

Существующие `core.*` capabilities не переименовываются в идентификаторы пакетов. Например, `core.community.overview.v1` продолжает означать конкретный контракт, а не наличие произвольного плагина обзора. Внешний пакет не может объявить себя реализацией официального API без проверяемого профиля совместимости.

Удаление legacy API допускается только после опубликованного периода поддержки и проверки пар клиент/runtime. В 0.9–0.11 оно не является обязательной целью. Старый API и новый command dispatcher используют одну реализацию записи и один источник истины.

Исходная база плана — текущие исходники и документы: приложение v0.7.29, runtime v0.7.23, схема 41. Это не новая проверка публичных релизных файлов; отчёты выпуска остаются в своих документах.

| `protocol/proto/space/v1/community_overview.proto` | Сохранить старый контракт, добавить универсальные contributions и провайдеры |
| `space-app/client/lib/src/community_overview.dart` | Заменить фиксированные направления forum/feed реестром переходов с legacy-адаптерами |
| `space-app/client/lib/src/community_overview_rpc.dart` | Универсальный клиент данных расширений и совместимый старый путь |
| `space-app/client/lib/ui/space_frame.dart` и оболочка | Встраивание реестра разделов без переноса асинхронного состояния в виджеты |
| `space-server/internal/postgres/community_overview.go` | Провайдер старого обзора за общим интерфейсом |
| `space-server/internal/transport` | Проверяемый dispatcher и сохранённые Connect/gRPC API |

Перед каждым переносом составляется полный перечень фактических RPC, таблиц, индексов, фоновых задач, UI и тестов данного раздела. Таблица выше обозначает точки начала, а не исчерпывающий список файлов. Изменение `.proto` сопровождается совместимой генерацией Go/Dart/OpenAPI; сгенерированные файлы вручную не редактируются.

## 18. Порядок миграции существующих функций

### Общий алгоритм

1. Зафиксировать исходный снимок и перечень функций, включая скрытые зависимости поиска, уведомлений, файлов и экспорта.
2. Обернуть старую реализацию внутренним адаптером; сохранить существующие таблицы, RPC и ID.
3. Создать установку и экземпляры официального пакета идемпотентной миграцией. Уникальность отображения старого view исключает дубли при повторном запуске.
4. Перевести навигацию и обзор на contributions; сравнить результаты старого и нового чтения без двойных побочных эффектов.
5. Внедрить WASM-обработчики на тестовой копии. При необходимости физического переноса выполнить backfill, контрольные суммы и сверку графа ссылок.
6. На короткое время остановить запись выбранного экземпляра, дочитать хвост изменений и атомарно переключить единственного writer. Длительное независимое двойное сохранение запрещено.
7. Проверить старый и новый клиент, перезапуск, replay и восстановление. Открыть запись и наблюдать ошибки, задержки и расхождения.
8. Удалять временный адаптер только после выполнения критериев; исходные данные не уничтожать автоматически при первом успешном запуске.

Физическое перемещение таблиц не требуется для первого этапа модульности. Если общий storage API не выражает необходимые транзакции и индексы, перенос останавливается до расширения контракта; привилегированный SQL в WASM не используется как обход.

### Обсуждения первыми

Официальный пакет `space.discussions`: темы, ответы, закрытие/закрепление, редактирование, вложения, реакции, личное избранное, отметки чтения, упоминания, жалобы, модерация и аудит. Сохраняются ID тем/ответов, последовательности, авторство, временные метки, удаления, ACL и ссылки на файлы.

Особое условие: идентичность заявителя жалобы не раскрывается модератору; очередь и её счётчик доступны только по правам. Закрытая тема, скрытый ответ и отозванный доступ проверяются через все пути — обзор, поиск, уведомления, избранное и экспорт. Старые forum RPC вызывают тот же обработчик записи.

### Лента после Обсуждений

Официальный пакет `space.feed`: публикации, комментарии и ответы на них, реакции, избранное, чтение, упоминания, жалобы, модерация, репосты, цитирование, подписки и персональная хронология. Переиспользуются компоненты и контракты, но данные разных экземпляров не объединяются.

Сохраняются ссылки на оригинал, запрет циклов, поведение скрытого оригинала и область подписок внутри пространства. Подписки участников остаются в общей службе отношений пространства; плагин получает разрешённое представление для текущего principal, без копирования полного социального графа. Персональная лента повторно проверяет доступ к каждому источнику.

### Чаты после проверки общего хранилища и событий

Официальный пакет `space.chat`: обычная переписка, история, ответы, редактирование/удаление, вложения, реакции, избранное, непрочитанное и уведомления. Сохраняются server sequence, клиентские ID отправки, очереди offline, черновики и ссылки на сообщения. Проверяется одновременное использование старого RPC и нового API без дубликатов.

MLS-каналы получают тот же реестр и UI-адаптер, но клиентские шифрование, расшифрование, локальный поиск и ключи остаются в доверенном клиенте. Серверный WASM работает с разрешёнными метаданными и непрозрачными конвертами. Перенос не расшифровывает историю на сервере и не меняет MLS group ID/эпохи. Официальный пакет не получает исключение из этого правила.

### Комнаты последними

Официальный пакет `space.rooms` управляет сущностями комнат, разрешёнными настройками и UI. WebRTC/SFU, TURN credentials, Opus, audio slots, native audio, подавление шума, PTT и чувствительность остаются в соответствующих службах сервера и клиента.

На границе API сохраняются лимиты 2–32, исходное значение 8, правила старых клиентов и уменьшения вместимости без отключения действующих участников. Новая выдача join-ticket проверяет активность пакета и ACL. Выключение пакета запрещает новые входы и завершает текущие сессии через медиаслужбу с понятной причиной; обновление версии выполняется после освобождения комнат либо с явно объявленным прерыванием. Переиспользование старых билетов запрещено.

Критерии включают реальные два клиента, переподключение и внешний TURN. Стенд 32 peers и 992 направлений RTP подтверждает транспортную проверку, но не заменяет приёмку разговора людей и устройств. Открытые аппаратные ограничения не закрываются миграцией на плагины.

## 19. SDK и работа стороннего разработчика

Первый SDK включает шаблон «Опросы», сборку под точный ABI, схему манифеста, типизированные обёртки host calls, локальный тестовый хост, проверку UI, упаковку и подпись. Сначала подтверждается одна цепочка компиляции, например Rust; другие языки получают статус поддержки только после тех же контрактных тестов.

Разработчик создаёт схему данных, команды/queries, страницы и элемент обзора; запускает тесты с несколькими пользователями и двумя экземплярами; собирает пакет; устанавливает в тестовое пространство; экспортирует проверенный пакет владельцу. Публикация в централизованном каталоге необязательна.

Документация SDK содержит список разрешений, гарантии транзакций, ошибки, пределы, правила миграции, совместимость UI и примеры небезопасных решений. Отладчик не получает пользовательские токены и текст сообщений по умолчанию. Журналы содержат request ID, экземпляр, версию и код ошибки, без секретов и payload.

Для миграций сравниваются не только количества строк, но и содержимое, граф ссылок, ACL, последовательности и результаты пользовательских сценариев. Предварительная цель: не более 20% ухудшения p95 относительно исходного пути на одном стенде и наборе данных; абсолютные бюджеты задаются по измерениям до выпуска. Это критерий исследования, не обещание скорости.

Каждый этап включает Go tests/vet/race и проверку зависимостей, совместимость protobuf и генерацию, Dart COG/analyze, необходимые unit/widget/integration-тесты, целевые сборки и реальный клиент → сервер → PostgreSQL с перезапуском. Размещение проверок в CI и действующие исключения физической приёмки сохраняются по актуальным инструкциям проекта; исключение не превращается в успешную проверку.

## 22. Альтернативы и оставшиеся решения

Встроенные Go-модули проще для первого выделения обязанностей, но требуют пересборки сервера; поэтому они используются как миграционные адаптеры. Отдельные сервисы дают независимое масштабирование, но усложняют домашнюю установку и доверие к RPC. WASM выбран как направление для переносимой серверной логики; он не заменяет медиаслужбы и криптографию.

Extism остаётся альтернативой самостоятельному ABI: предоставляет host functions и инструменты плагинов. Component Model/WIT подходит для типизированных импортов и экспортов, но требует отдельного подтверждения поддержки во всей выбранной цепочке. Нельзя объявлять Core WASM-пакет автоматически совместимым с Component Model.

Перед P3 требуется закрыть: точную версию runtime и поддерживаемый компилятор; машиночитаемые схемы ABI/UI; протокол подписи и ротации ключей издателя; формат миграционных checkpoint; границы поддержки старых клиентов; измеренные общие квоты. До этого пакетный формат экспериментальный. Магазин, платежи, межплагинная сеть, произвольные веб-поверхности и клиентский WASM остаются отдельными будущими решениями.

Источники для выбора технологии: [wazero](https://wazero.io/docs/), [host functions Extism](https://extism.org/docs/concepts/host-functions/), [WIT](https://component-model.bytecodealliance.org/design/wit.html). Эти документы описывают технологии исполнения; API Space, сроки и релизные этапы выше являются проектными решениями этой спецификации.
