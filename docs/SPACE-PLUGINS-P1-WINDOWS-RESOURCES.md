# P1/E03: реестр, IPC и сетевая матрица Windows LPAC

Продолжение [LPAC-прототипа](SPACE-PLUGINS-P1-WINDOWS-LPAC.md) и [аварийного восстановления](SPACE-PLUGINS-P1-WINDOWS-RECOVERY.md), 6 ноября 2026 года. Срез расширяет проверки прав настоящего нативного worker. Политика запуска, capabilities, квоты и рабочая интеграция не меняются; E03/P1 остаются открытыми, выпуск отложен.

## Контрольные ресурсы

Отдельный исполняемый файл `p1-rights` получает пути/имена через существующие stdin/stdout каналы. Сначала тот же probe выполняется обычным `NewProcessHost`, затем — `NewWindowsRestrictedHost`. Все ресурсы создаются только тестом GitHub CI с уникальными именами. Нельзя засчитать отказ LPAC, если обычный процесс не подтвердил доступ.

| Проверка | Действие probe | Проверка после LPAC |
| --- | --- | --- |
| Чтение реестра | Открыть ключ и прочитать контрольное значение | Исходное значение сохранилось |
| Запись реестра | Открыть ключ с SET_VALUE и заменить значение | Исходное значение сохранилось |
| Создание ключа | Создать дочерний ключ | Дочерний ключ отсутствует |
| Событие | OpenEvent с EVENT_MODIFY_STATE, затем SetEvent | Событие не сигнализировано |
| Именованный канал | Открыть существующий duplex pipe на чтение/запись | Handle не получен |
| Чтение памяти supervisor | OpenProcess с PROCESS_VM_READ | Handle не получен; память не читается |
| Дублирование handles supervisor | OpenProcess с PROCESS_DUP_HANDLE | Handle не получен; handles не дублируются |
| Завершение supervisor | OpenProcess с PROCESS_TERMINATE | Handle не получен; TerminateProcess не вызывается |

Ключ создаётся под `HKEY_CURRENT_USER\Software\SpaceP1Rights-<nonce>`, а probe обращается к нему через полный `HKEY_USERS\<SID пользователя>\Software\...`. Это отделяет доступ к исходному пользовательскому ключу от возможного перенаправления `HKCU` в частное хранилище AppContainer. Проверяется только созданный тестом ключ, не произвольные разделы реестра или секреты пользователя.

Для обычного процесса обязательны восемь успешных операций. Перед LPAC возвращаются контрольное значение, отсутствие дочернего ключа и несигнализированное состояние события. Инстанция named pipe пересоздаётся с тем же именем после закрытия контрольного клиента. Для LPAC требуются точные коды отказа: `ERROR_ACCESS_DENIED`; только для события допускается `ERROR_FILE_NOT_FOUND` как недоступность имени в изолированном пространстве. Ошибка отсутствующего объекта не объявляется проверкой его DACL. Тайм-ауты, занятый pipe и произвольные ошибки не засчитываются.

Модель основана на [изоляции ресурсов AppContainer](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation), конкретные операции используют [OpenEvent](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-openeventw) и [CreateNamedPipe](https://learn.microsoft.com/en-us/windows/win32/api/namedpipeapi/nf-namedpipeapi-createnamedpipew). Результат ограничен измеренными операциями и ОС; это не аудит всех Windows API.

## TCP/UDP и IPv4/IPv6

Проверяются четыре режима: `tcp4`, `tcp6`, `udp4`, `udp6`. Для каждого на loopback поднимается настоящий echo endpoint. Обычный worker обязан успешно выполнить `WSAStartup`, обменяться двумя контрольными байтами и открыть собственный listener/socket на динамическом порту. UDP проверяется ответом, а не одним успешным `Dial`.

LPAC отдельно сообщает результат и числовой код `WSAStartup`, обмена и bind. При успешной инициализации Winsock сетевые операции должны вернуть `WSAEACCES` (10013). При отказе инициализации принимается только явно измеренная комбинация `WSASYSCALLFAILURE` (10107) и `WSANOTINITIALISED` (10093) для последующих операций. Такие результаты хранятся отдельно и **не считаются доказательством WFP-фильтра или запрета сети после успешной инициализации Winsock**. Не добавляются capabilities или исключения loopback ради прохождения тестов.

Исходящий Интернет, внешний узел локальной сети, DNS, сетевые credentials и альтернативные нативные сетевые API не входят в этот срез. Возможность использовать уже открытые переданные handles также требует отдельной проверки; стандартный launcher передаёт только три handles обмена.

## Приёмка GitHub CI

[CI 42169392405](https://github.com/space-protocol-project/space-server/actions/runs/42169392405) полностью успешен для `b87dff257e7f34d4c202a2ddca5b4b1336a3a390`: все **9 заданий**. Go test/vet/mod verify/govulncheck и race-проверки трёх ОС успешны; Linux isolation/systemd и macOS probes также прошли.

- Все **8 операций** обычного процесса успешны. В LPAC все восемь отклонены с **ERROR_ACCESS_DENIED (5)**. Код отсутствующего события в этом прогоне не понадобился. Контрольное значение реестра осталось исходным, дочерний ключ не появился, событие не сигнализировано.
- Все **4 сетевых режима** прошли положительный контроль: startup, двусторонний echo и bind успешны без LPAC. В LPAC во всех случаях startup вернул **10107**, обмен и bind — **10093**. Отказ именно сетевого фильтра (`WSAEACCES`) не получен и не объявляется принятым.
- В артефакте Windows — **28 результатов pass для LPAC** и **18 для прежнего Job-профиля**; по одному ожидаемому helper-пропуску в основном процессе. Числа включают родительские и дочерние записи Go test. Прежние пять аварийных сценариев восстановления профилей также успешны.

[Исходные результаты и метаданные](p1-results/2026-11-06-windows-lpac-resources/) сохранены вместе с [SHA256SUMS](p1-results/2026-11-06-windows-lpac-resources/SHA256SUMS). Байты артефактов не преобразованы, метаданные GitHub записаны в UTF-8. Приёмка выполнена одной полной матрицей без повторного запуска отдельных упавших заданий.

Сетевой профиль с отдельно доказанным запретом после инициализации стека, остальные виды handles и межпрофильных ресурсов (файловый handle и частные файлы проверены [следующим срезом](SPACE-PLUGINS-P1-WINDOWS-HANDLES.md)), дисковая квота временного профиля, рабочий broker IPC/catalog API и приёмка настольной Windows из установщика.
