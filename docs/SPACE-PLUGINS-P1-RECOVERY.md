# P1: восстановление Linux ProcessHost после аварии supervisor

Продолжение от 30 октября 2026 года к [Linux-профилю](SPACE-PLUGINS-P1-ISOLATION.md), [Windows-профилю](SPACE-PLUGINS-P1-WINDOWS.md) и [общему P1](SPACE-PLUGINS-P1.md). Изменён только экспериментальный модуль `space-server/experiments/extensions`; рабочая служба сервера пока не подключена.

## Проблема

Отмена вызова живым supervisor уже завершает всю cgroup. Но после `SIGKILL` supervisor его отложенная очистка не выполняется. `Pdeathsig` не гарантирует остановку произвольного дерева потомков. Поэтому после аварии могли оставаться процессы и каталоги cgroup, а новый ProcessHost создавал независимую группу без очистки старой.

## Владение и порядок восстановления

Конструктор Linux теперь получает исключительную неблокирующую `flock` на дескриптор выделенного корневого каталога cgroup. Проверяются принадлежность root и отсутствие права записи для группы/остальных. Дескриптор остаётся открытым на весь срок жизни хоста и не передаётся worker через exec. [Семантика flock](https://www.man7.org/linux/man-pages/man2/flock.2.html): блокировка связана с открытым описанием файла и снимается после закрытия всех соответствующих дескрипторов.

Порядок запуска:

1. Проверить абсолютные пути, root-права и cgroup v2.
2. Получить блокировку; если корнем уже владеет другой ProcessHost, вернуть `ErrIsolation` без очистки его ресурсов.
3. Найти оставшиеся непосредственные каталоги `space-p1-*`. Этот префикс зарезервирован за launcher в выделенном администратором корне.
4. Проверить структуру каждого такого каталога: допустимы только дочерние `call-*` без вложенных каталогов. Неизвестная структура отклоняется до уничтожения процессов этой группы. Уже очищенные предыдущие группы не восстанавливаются обратно.
5. Записать `1` в `cgroup.kill` общей группы; удалить дочерние группы, затем саму общую группу. [Документация ядра](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html) определяет `cgroup.kill` как завершение всех процессов группы и её потомков с учётом конкурентного fork.
6. Только после успешной очистки создать новую группу с прежними лимитами и разрешить вызовы.

Посторонние имена каталогов в корне игнорируются. Произвольного обхода файловой системы или удаления обычных каталогов нет: конструктор требует cgroup v2. При ошибке очистки новый хост не возвращается; блокировка освобождается, чтобы следующий запуск мог повторить восстановление. Доверенный root-процесс всё ещё способен изменить дерево или обойти advisory lock; это не граница защиты от администратора.

`Close` при активных вызовах по-прежнему возвращает `ErrQuota`, сохраняя блокировку. После удаления своей группы хост закрывает дескриптор. Повторный `Close` успешен. При принудительном завершении supervisor ОС освобождает его дескрипторы.

## Проверки GitHub CI

- Отдельный процесс supervisor создаёт worker и потомка. Стенд проверяет именно два процесса через `cgroup.procs`, а не число потоков.
- Пока supervisor жив, второй конструктор получает `ErrIsolation`.
- Supervisor принудительно завершается; стенд подтверждает `populated 1`, то есть для восстановления действительно остаётся живой процесс.
- Новый ProcessHost удаляет старую cgroup, после чего успешно исполняет настоящий echo WASM. После вызова дочерних групп не остаётся.
- Неизвестная структура прерывает запуск и сохраняется. После её явного удаления стендом повторный запуск очищает остаток прерванной инициализации. Посторонняя группа остаётся на месте.
- Весь прежний набор ограничений Linux и Windows, строгий worker-протокол, ABI, race detector, vet, mod verify и govulncheck повторяются в том же workflow.

Для аварийного стенда внутренний вызов имеет deadline 30 с, чтобы можно было убить supervisor. Публичный `CompileAndCall` сохраняет предел 2 с. Вспомогательный тест запускается отдельным процессом; его штатный пропуск при обычном обходе тестов не означает пропуска аварийного сценария.

[CI 40975174377](https://github.com/space-protocol-project/space-server/actions/runs/40975174377) завершился успешно для `9e91bdda7eef2722aa0c97174a8bcb82ab415d92`: все шесть заданий. `TestIsolationSupervisorRecovery` подтвердил живого потомка после убийства supervisor, удаление старой группы и успешный WASM; восстановление вместе с контрольным вызовом заняло 5,73093 мс в этом синтетическом прогоне (не производственная гарантия задержки). `TestIsolationRecoveryScope` подтвердил сохранность посторонней группы и отказ при неизвестной структуре. [Исходные журналы и метаданные](p1-results/2026-10-30-recovery), [SHA256SUMS](p1-results/2026-10-30-recovery/SHA256SUMS) сохранены. Локальные сборки и тесты не запускались; последующий документационный коммит не меняет проверенный код.

## Что этот шаг не закрывает

Восстановление выполняется **при следующем запуске**. Немедленное завершение всех потомков в момент смерти supervisor и автоматический перезапуск требуют управляющей службы. Производственная интеграция, отдельный служебный пользователь, файловые/сетевые ограничения, аварийные окна Windows и профиль macOS остаются открытыми. P1 целиком не завершён.
