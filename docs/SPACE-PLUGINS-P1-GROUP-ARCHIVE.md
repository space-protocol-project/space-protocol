# E01: архивы групповой истории нескольких экземпляров

11 ноября 2026 года. Продолжение [нескольких экземпляров](SPACE-PLUGINS-P1-MULTI-INSTANCE.md) и [сводной ревизии P1](SPACE-PLUGINS-P1-AUDIT.md).

## Состав стенда

Отдельный `plugin-p1-group-transfer.yml` использует общий архивный стенд с явным профилем SPACE_P1_ARCHIVE_GROUP=1. Старый workflow одного экземпляра сохраняется и проверяется отдельно на той же ревизии. Профиль записывается в эталон архива: несовпадение группового и одиночного профиля отклоняется.

Одна установка содержит demo и other. Первый экземпляр имеет исходную мутацию и квитанцию, второй — пустые исходные данные; оба проходят настоящую WASM-миграцию 1 → 2 и подготовку 2 → 3. Это фиксированный состав группы, не динамическое добавление экземпляров и не обновление нескольких установок.

Сохраняются четыре состояния второго обновления:

- pending — оба экземпляра ожидают шаг миграции;
- partial — demo уже выполнил шаг, other ещё нет;
- ready — оба результата готовы, публикация не выполнена;
- published — пакет, данные и групповая история опубликованы.

## Что проверяется

Linux готовит исходные ZIP с изолированным WASM. Каждая из трёх ОС импортирует их, затем создаёт собственные физические копии и ZIP. Проверяются все шесть направлений межплатформенного ZIP-переноса, четыре состояния и три повторения под race detector. Системные базы не используются: каждый сценарий работает с отдельной временной PostgreSQL.

Снимок сравнивает installations, lifecycle_audit, instances, data, receipts, outbox, одиночные таблицы миграций и обе групповые таблицы group_jobs/group_versions. Исключается только текущее поколение установки, которое обязано смениться при открытии. Число экземпляров, версии публикаций, состав и курсоры шагов проверяются отдельно через SQL и ReadGroupUpgrade. Старое поколение не может включить установку.

Сохраняются идентичность сервера, точные пакеты/схемы/данные/аудит, квитанции и курсор доставки. Физическая копия сохраняет сессии по прежнему контракту; ZIP исключает их, поэтому выполняется повторный вход временным тестовым ключом. Открытие архива не исполняет гостя. Контрольная сумма исходного архива после проверок не меняется.

На Linux отдельно возобновляются архивы Windows и macOS. Исполнитель читает сохранённый состав и планы, заново получает тестовые свидетельства доверия/согласия и запускает только недостающие шаги. Публикация вызывается повторно для проверки идемпотентности; в результате остаются две групповые версии, а квитанции и outbox не меняются. Эти свидетельства принадлежат тестовой оболочке, а не гостю; рабочий UI подтверждения не добавляется.

## Повреждения

Для физической копии и ZIP проверяются неверный digest истории, удалённая первая версия и подмена WASM-модуля второго экземпляра. В последнем случае пересчитывается внешний record_hash: отказ должен опираться на внутреннюю согласованность артефактов и плана. Контрольные суммы самого архива корректны. Восстановление обязано отказать до публикации каталога и убрать временные данные, сохранив исходный архив.

Итоговые workflows завершены полностью на серверной ревизии `7309f691e0acd9c30838a021e130cdf0330a5f66`:

Обычная и race-регрессия ядра дали по 808 успешных результатов и 78 штатных пропусков. Это число включает родительские тесты. Общий запуск не подменяет отдельные окружения: архивы проверены своей матрицей, реальные сессии/ACL/WASM — отдельным набором `isolated.jsonl` (277 успешных результатов без пропусков), завершение процесса исполнителя — `worker-crash.jsonl`, сбои PostgreSQL — `faults.jsonl`. Пропуски `lifecycle.jsonl` относятся к RealWASM; пропуски `mutations.jsonl` — к RealWASM и WorkerCrashRecovery, выполненным в отдельных шагах. Полные имена всех пропусков сохранены в сводке; остальные платформенные сценарии нельзя считать выполненными только по этому Linux-профилю.

`go vet`, `go mod verify` и `govulncheck` прошли. [Сводка](p1-results/2026-11-11-group-archive/summary.json), сведения о трёх запусках, исходные JSONL и [SHA256SUMS](p1-results/2026-11-11-group-archive/SHA256SUMS) сохранены побайтово. Приёмка основана на GitHub CI; локальная компиляция тестов не учитывается как исполнение архивных сценариев.

Проверка ядра [42977182072](https://github.com/space-protocol-project/space-server/actions/runs/42977182072) прошла обычные и race-тесты, но остановилась на `govulncheck`: стандартная библиотека Go 1.27.3 затронута [GO-2026-6859](https://pkg.go.dev/vuln/GO-2026-6859). Оба серверных модуля переведены на стабильный [Go 1.27.4](https://go.dev/dl/); CI получает версию из `go.mod`. Для приёмки заново выполнены все три workflows на одной ревизии. Старые опубликованные сборки этим изменением не пересобираются, клиентские нативные модули не входят в данный серверный прогон.

Передаются только синтетические тестовые ZIP и временные ключи/токены, ранее разрешённые пользователем для такого межплатформенного стенда; срок хранения этих артефактов — один день. В доказательства документации не включаются архивы с временными ключами и эталоны с приватными ключами.

## Оставшиеся границы

Первый запуск [42975928822](https://github.com/space-protocol-project/space-server/actions/runs/42975928822) выявил ошибку стенда: повтор публикации выполнялся через прежнюю управляющую службу, владение которой публикация уже завершила. Ядро правильно вернуло `Unavailable/lifecycle_failed`. Повтор перенесён на новое хранилище и управляющую службу, как после перезапуска; проверка владения не ослаблялась. При повторе сравнивается полный снимок, кроме нового поколения установки.

Возобновление WASM принимается на Linux, а Windows/macOS проверяют сохранность и восстановление данных без запуска гостя. Не добавлены автоматический откат, динамический состав установки, произвольный SQL, массовая нагрузка и глобальный бюджет истории. Политика хранения/очистки истории и единая матрица manifest/ABI/API остаются следующим блоком E01/E02. P1 и выпуск 0.9.0 целиком не закрыты.
