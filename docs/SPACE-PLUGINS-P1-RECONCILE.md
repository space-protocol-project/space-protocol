# P1 / E02: сверка неопределённой команды

Статус: следующий ограниченный блок [E02](SPACE-PLUGINS-P1-EXIT.md), после [политики решений о повторах](SPACE-PLUGINS-P1-RETRY.md). Генерация, серверный и клиентский GitHub CI успешны. Рабочая регистрация расширений и автоматический исполнитель повторов клиента не подключены.

## Контракт

Экспериментальный `ReconcileExtensionCommand` принимает вложенный исходный `ExecuteExtensionCommandRequest`: instance, command, effect, ключ, ожидаемую ревизию и точные байты payload. Клиент обязан сохранить исходный запрос и привязку сервера/пространства/principal. Пересборка JSON с другой раскладкой пробелов не считается тем же запросом. Доверенная установка и хеш пакета определяются серверным реестром, не клиентом.

Ответ содержит:

- `CONFIRMED` и `receipt`: сохранённый результат именно этой команды; `replayed=true`. Проверяются effect, ревизия и корректность JSON документа.
- `UNKNOWN` без квитанции: запись отсутствует в текущем состоянии хранилища. Это не доказывает отсутствие эффекта до восстановления старой копии, завершение конкурентной операции вне проверенного состояния или возможность безопасного повторного выполнения.
- `UNSPECIFIED` — недопустимое для подтверждения значение, зарезервированное нулевое состояние protobuf.
- `retry_window_known=false`, `retry_window_remaining_ms=0`: в этом прототипе срок выдачи квитанции и tombstone ещё не реализованы. Клиент не должен выводить срок из `created_at`, целевого срока хранения в спецификации или наличия ответа. Эти поля не превращают `UNKNOWN` в разрешение повтора.

Ошибки не раскрывают квитанцию. Изменённый запрос с тем же ключом получает `AlreadyExists`, неизвестная привязка и отозванные права — отказ доступа. Повреждённая декодируемая квитанция не подтверждает эффект: `DataLoss`. Ошибка декодирования/БД также не возвращает результат. Прежняя неопределённость клиента сохраняется при любом таком отказе.

## Проверка полномочий и ресурсов

Сверка требует текущую сессию и те же права записи, что исходная команда. Право чтения канала не разрешает получение результата мутации. Квитанции разделены по principal: даже владелец пространства не получает квитанцию другого пользователя по известному ключу. Новый токен того же principal может использоваться только после проверки прежней привязки клиентом.

Сервер использует общие с исполнителем два слота, пятисекундный бюджет, advisory lock команды, блокировки полномочий и экземпляра. Проверка сессии повторяется перед завершением транзакции. Сверка сериализуется с исполнением той же команды; SQL-блокировки и ожидание ограничены прежними бюджетами. Она не вызывает WASM, не изменяет ревизию, данные, квитанции или outbox, не создаёт аренду и не резервирует ключ.

Отдельный конструктор без хранилища мутаций возвращает `FailedPrecondition`. Основной сервер по-прежнему не включает экспериментальный сервис автоматически. Структура БД и формат резервных копий не меняются.

## Границы и дальнейшая работа

Этот RPC позволяет подтвердить сохранённый результат без риска повторного исполнения. Для `UNKNOWN` автоматические повторы остаются выключенными. Наличие read-only сверки не заменяет сохранённый снимок клиентской команды, Bloc/Cubit исполнителя, проверку отмены/смены пользователя и настоящую клиентскую интеграцию.

Следующий блок должен определить и реализовать жизненный цикл квитанции: сохранённое окно, выдачу доверенных метаданных до неоднозначного отказа, tombstone после удаления ответа, запрет повторного эффекта и смену поколения истории при restore. Одно только поле срока в успешном ответе недостаточно: именно этот ответ может потеряться. После этого возможна сквозная приёмка повторяющего клиента. E01/E02 и весь P1 остаются открытыми.

## Проверки
