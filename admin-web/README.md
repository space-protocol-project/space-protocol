# Веб-панель сервера

Первый работающий срез встроен в Go-сервер и открывается по `/space`. [Исходники](../server/internal/spaceweb/assets/) используют общий [контракт](../protocol/proto/space/v1/space.proto). Отдельный frontend-сервер не нужен. Оформление: Gruvbox, радиус областей 12 px, адаптивная компоновка.

Доступны назначение первого владельца, вход по подписи, выход с удалением сессии, название пространства и чата, включение чата и режим регистрации open/closed, приглашения и права участников. Изменения сохраняются в PostgreSQL с проверкой revision и аудитом. Отключение закрывает также API чата, но сохраняет сообщения. Closed допускает новые идентичности только по действующему приглашению; известные незаблокированные пользователи могут подключать устройства.

## Запуск без Docker

Нужны Go и доступная PostgreSQL. Из каталога `server`:

```powershell
$env:SPACE_DATABASE_URL = 'postgres://space:YOUR_PASSWORD@127.0.0.1:5432/space?sslmode=disable'
go run ./cmd/space-server
```

Откройте `http://127.0.0.1:8080/space` и войдите по ключу. На новой базе первый успешный вход автоматически назначает владельца. Для старых ненастроенных баз используйте -first-owner. Команда -setup-code остаётся явным выбором ручного режима с кодом на 15 минут.

Открыть страницу может любой процесс, имеющий доступ к локальному порту. Для управления сервер проверяет действующую сессию владельца или администратора и отдельное подписанное разрешение устройства `space.manage`. Адрес `/space` и локальное подключение сами по себе административных прав не дают.

## На сервере нет браузера

Настройте PostgreSQL и переменную SPACE_DATABASE_URL на сервере. Из каталога `server`:

```sh
go run ./cmd/space-server -setup-code
go run ./cmd/space-server -http 127.0.0.1:8080 -origin http://127.0.0.1:18080
```

На своём компьютере создайте туннель, заменив SSH-адрес:

```sh
ssh -N -L 127.0.0.1:18080:127.0.0.1:8080 user@your-server
```

Откройте `http://127.0.0.1:18080/space` в своём браузере. Браузер на сервере не нужен; соединение между компьютерами защищает SSH. Порт 18080 должен быть свободен. Сохраняйте выбранный origin: браузерные ключи привязаны к нему. При порте 8080 с обеих сторон отдельный `-origin` не нужен.

Текущий сервер разрешает только loopback IP и локальный HTTP origin. Публичный HTTPS и reverse proxy ещё предстоят. Этот экспериментальный профиль не предназначен для открытия в интернет.

## Приглашения и права — работающий первый срез

| Роль | Чат | Настройки и приглашения | Роли и блокировка |
|---|---|---|---|
| Читатель (`reader`) | Читать | Нет | Нет |
| Участник (`member`) | Читать и писать | Нет | Нет |
| Администратор (`admin`) | Читать и писать | Да, с grant `space.manage` | Нет |
| Владелец (`owner`) | Читать и писать | Да, с grant `space.manage` | Да, с grant `space.manage` |

Права пространства и разрешения устройства проверяются вместе. Даже владелец не управляет сервером через обычный chat-only grant Flutter. Для администратора браузер отдельно подтверждает выдачу management grant корневым ключом. Владельца нельзя понизить или заблокировать этим API; передачи владения пока нет.

1. Войдите в `/space`, откройте «Приглашения» и выберите читателя или участника, срок (до 7 дней) и число вступлений (1–100).
2. Сохраните показанные ссылку и код. Секрет возвращается только при создании; позднее список показывает срок, роль, счётчик и отзыв без секрета. Активных приглашений может быть до 100.
3. В Flutter откройте подключение к пространству, введите адрес сервера и код `iv_…`, нажмите «Проверить сервер». Клиент покажет роль; после подтверждения доверия зарегистрирует устройство и вступит одной серверной транзакцией.
4. Ссылку `/space#invite=…` можно открыть в браузере: fragment не отправляется HTTP-серверу, панель переносит код в поле и убирает fragment из адреса. «Проверить приглашение» показывает роль и срок. Вход использует приглашение для отдельной браузерной идентичности.
5. В «Участники и права» владелец может изменить роль или заблокировать пользователя. Изменение требует актуальной revision; конфликт не перезаписывает чужие изменения.

**Браузер и Flutter пока не разделяют идентичность.** Не расходуйте одноразовый код в браузере, если хотите вступить только через Flutter. Для двух независимых идентичностей нужны два приглашения либо два свободных места. Локальная ссылка доступна только там, где доступен соответствующий loopback/SSH-туннель; это ещё не публичная ссылка для интернет-развёртывания.

Повторное принятие действующего приглашения тем же principal не расходует место. Существующая роль не меняется от приглашения, поэтому оно не повышает права и не снимает блокировку. Если одно место одновременно используют разные пользователи, успешно вступает только один. Истёкший или отозванный код не принимается; отзыв ссылки сохраняет доступ уже вступивших участников. Для отзыва доступа используйте блокировку участника.

Проверки чтения, записи и событий находятся на сервере, а не только в интерфейсе. Блокировка прекращает активную подписку при следующей проверке (обычно до 500 ms; кадры, уже отправленные до изменения, отозвать нельзя). Понижение до читателя запрещает новые записи, но сохраняет чтение. Flutter обновляет отображение роли на heartbeat; сервер применяет запрет сразу после фиксации изменения.

Открытая регистрация создаёт нового участника автоматически. Закрытая допускает нового principal только при атомарном принятии приглашения. Миграция 4 сохраняет старым зарегистрированным идентичностям роль участника; owner_id имеет приоритет. Блокировка не снимается повторной регистрацией устройства.

Пока существует только общий чат: роли действуют на всё пространство. Отдельные ACL каналов, модераторы, приглашения с одобрением заявки, выход из членства, QR приглашения и pairing ещё предстоят.

## Хранение ключей

WebCrypto создаёт отдельные root/device Ed25519 CryptoKey. Неэкспортируемые приватные ключи хранятся в IndexedDB, токен — только в памяти страницы. Это не аппаратная защита и не passkey: XSS может использовать ключ для подписи. Панель поставляет свои статические скрипты, использует строгую CSP и проверку Host/Origin.

Первый вход без карточки создаёт отдельную идентичность. Зашифрованная JSON-карточка уже позволяет восстановить прежнюю идентичность в панели или Flutter; Root-подписанное сопряжение также работает, QR пока отсутствует. Без заранее созданной карточки очистка профиля или потеря компьютера могут лишить владельца доступа. Повторная выдача разрешения устройства требует отдельного подтверждения. Выход удаляет сессию, но сохраняет ключи и grant.

## Сохранить и восстановить владельца

1. После назначения владельца откройте «Восстановление и устройства». Укажите и повторите сильный пароль карточки (минимум 12 символов), нажмите «Создать и скачать карточку».
2. Сохраните `space-recovery.json` и пароль раздельно. Панель сохраняет зашифрованную копию для повторного скачивания; исходный root не экспортируется. Проверить скачанный файл на другом устройстве нужно до удаления исходного профиля.
3. В новом браузере откройте тот же origin `/space`, разверните «Восстановить прежнюю идентичность», выберите файл и введите пароль. Подтвердите замену локальной идентичности. Будет создан новый рабочий ключ с прежним principal/owner.
4. Либо во Flutter откройте «Идентичность» → «Восстановить из файла». Карточка проверяет discovery/key pin; после подтверждения сохраняется только новый device key. Root/recovery secret делегированной карточки в рабочем vault не сохраняется.
5. Обновите список устройств и отзовите потерянный grant. Для отзыва других устройств на восстановленном рабочем аппарате нужно снова открыть карточку; собственный текущий grant можно отозвать без неё.

Панельная карточка действует до 3650 суток; фактический срок виден у recovery grant в списке. Один активный recovery key на principal. Для выпуска нового исходный root должен отозвать предыдущий; вместе с ним перестанут работать все его дочерние devices. Сначала проверьте другой путь доступа. Заблокированное членство и отозванная/истёкшая карточка не обходятся восстановлением.

Flutter также может экспортировать зашифрованную **корневую** карточку своего исходного per-server root. Она восстанавливает управляющий root, поэтому имеет более широкие полномочия, чем рабочее устройство из карточки панели. В этом экспериментальном профиле отзыв grant не отзывает скопированный root secret; ротация скомпрометированного root ещё не реализована. [Формат, проверки и границы](../docs/adr/021-recovery-cards.md).

Для восстановления в Flutter через SSH нужны оба локальных порта, а HTTP origin должен совпасть с карточкой. Например, при сервере с `-origin http://127.0.0.1:18080` и gRPC на 9090:

```sh
ssh -N -L 127.0.0.1:18080:127.0.0.1:8080 -L 127.0.0.1:9090:127.0.0.1:9090 user@your-server
```

Порты на своём компьютере должны быть свободны. Это локальный SSH-профиль, не публичный TLS deployment. Карточка не заменяет резервную копию серверной PostgreSQL.

Далее: права отдельных разделов, модерация, одобрение заявок, произвольные каналы/views, forum/feed/media, квоты, retention, состояние служб, резервные копии БД, QR/delegated pairing и ротация root. Панель не получает Docker socket, не запускает shell-команды и не отправляет recovery seed на backend.

## Сопряжение без передачи карточки

Новое устройство создаёт только рабочий ключ. Подтверждает исходное устройство с root либо корневая карточка Flutter. Если у вас только делегированная recovery-карточка панели, продолжайте восстановление из файла: подтверждение pairing этой цепочкой ещё предстоит.

1. В новом Flutter-клиенте проверьте адрес/отпечаток и нажмите «Доверять серверу и начать сопряжение». В новом браузере откройте /space → «Войти через существующее устройство» → «Начать сопряжение браузера».
2. Передайте появившийся code pc_… на исходное устройство. Это секретный одноразовый код на пять минут; poll token остаётся только новому клиенту. Не вводите чужие запросы из сообщений, которым не доверяете.
3. На исходном Flutter откройте «Идентичность» → «Подтвердить устройство», введите code. В панели это раздел «Подтвердить новое устройство». Нажмите подготовку и проверьте имя/запрошенные права. Имя само по себе не доказывает принадлежность устройства.
4. На обоих экранах появятся четыре группы hex кода проверки. Введите код именно с нового устройства на управляющем, убедитесь в совпадении и подтвердите подпись. При несовпадении отмените запрос и начните заново. Сверка нужна до подписи.
5. Новый клиент проверит root-подпись и предложит завершить вход. После подтверждения target login/claim код больше не работает, а новый рабочий ключ сохраняется локально. Уже сохранённая здесь идентичность для данного адреса заменяется только после явного подтверждения; её карточку следует сохранить заранее.

В первом срезе Flutter requester просит chat.read/chat.write, браузерный — также space.manage. Серверные роли не повышаются: участник остаётся участником. Сопряжённый working device не содержит root/recovery private key. Для следующего pairing нужен исходный root/RootCard, а после истечения grant нет автоматической root-регистрации.

Отмена после подписи отзывает незавершённый grant. Если claim не завершён за пять минут, разрешение перестаёт работать даже при уже выданной сессии. После claim действует обычный 30-дневный grant с self/root revoke. [Протокол и проверки](../docs/adr/022-device-pairing.md).
Пошаговое руководство с иллюстрациями: [ADMIN-GUIDE.md](../docs/ADMIN-GUIDE.md). QR recovery PNG и сопряжение через delegated recovery chain реализованы; камера и root rotation ещё не включены.

## Перенос интерфейса

Управление будет частью общего приложения Space. Начат общий Flutter-модуль с браузерной оболочкой /space/flutter/. Текущая HTML-панель остаётся рабочей до полного переноса. [ADR-025](../docs/adr/025-unified-administration.md).

## Первый вход на новом сервере

Новый сервер с PostgreSQL по умолчанию назначает первого успешно вошедшего пользователя владельцем. Запустите сервер и войдите по ключу через приложение Space или /space; setup-code не нужен. Открытие страницы без авторизации прав не даёт. После входа доступны настройки и каналы, а остальные пользователи не становятся администраторами автоматически.

Назначенный владелец сохраняется при перезапуске. Старые базы без владельца остаются в прежнем режиме: для явного включения выполните `space-server -first-owner`, затем запустите сервер. Команда `-setup-code` по-прежнему позволяет явно выбрать ручной режим. Владельца уже настроенного сервера эти команды не заменяют.

Подробности и проверки: [ADR-026](../docs/adr/026-first-login-owner.md).
